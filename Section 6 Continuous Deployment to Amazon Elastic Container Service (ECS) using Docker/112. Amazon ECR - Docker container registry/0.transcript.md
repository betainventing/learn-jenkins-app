# Why Docker Images Must Be Stored in a Registry

The Docker image built inside Jenkins currently exists only:

* Temporarily
* Inside the build environment

After the job finishes:

* The image may disappear.



---

# Important Container Concept

A Docker image is NOT:

* Normal workspace file
* ZIP archive
* S3 object upload candidate

Docker images are managed through:

* Container registries

---

# Why Registries Exist

A container registry provides:

* Permanent image storage
* Version management
* Distribution source
* Deployment retrieval

Without a registry:

```text id="’wini186"
Build Artifact Exists Temporarily
↓
Eventually Lost
```

---

# Public vs Private Registries

Example public registry:

* Docker Hub

Public registries are suitable for:

* Open-source/public images

But enterprise applications usually require:

* Private storage

---

# Amazon ECR

AWS provides:
Amazon Elastic Container Registry

Purpose:

* Private Docker image registry

ECR integrates tightly with:

* ECS
* IAM
* AWS CLI
* AWS permissions



---

# Creating the ECR Repository

Inside ECR:

* Create repository

Important setting:

```text id="’wini187"
Private Repository
```

because:

* Application is assumed private

---

# Repository Naming

The repository name matches:

* Application name

Example:

```text id="’wini188"
learn-jenkins-app
```

This improves:

* Naming consistency
* Deployment clarity

---

# Resulting Registry Address

ECR generates a registry URI similar to:

```text id="’wini189"
<account-id>.dkr.ecr.<region>.amazonaws.com
```

This becomes:

* Registry endpoint

---

# Important Tagging Improvement

The image tag must now include:

1. Registry
2. Repository name
3. Version tag

---

# Full Docker Image Naming Structure

General structure:

```text id="’wini190"
registry/repository:tag
```

Example conceptually:

```text id="’wini191"
aws-registry/learn-jenkins-app:1.0.109
```

---

# Why Full Tagging Matters

Without full registry path:

* Docker does not know where to push the image

The tag itself defines:

* Image destination registry

---

# Updated Docker Build Tag

The build now creates:

```text id="’wini192"
$AWS_DOCKER_REGISTRY/$APP_NAME:$REACT_APP_VERSION
```

This produces:

* Fully qualified image reference

---

# Docker Push Command

After building:

```bash id="’wini193"
docker push
```

uploads the image to ECR.

Conceptually:

```text id="’wini194"
Local Docker Image
↓
Push To Remote Registry
```



---

# New Problem — Registry Authentication

Private registries require:

* Authentication

Docker cannot push anonymously.

---

# Docker Login Command

Docker uses:

```bash id="’wini195"
docker login
```

for registry authentication.

Normally requires:

* Username
* Password

---

# AWS ECR Authentication Difference

ECR does NOT provide:

* Permanent static Docker passwords

Instead:

* AWS CLI dynamically retrieves temporary authentication token

---

# ECR Login Password Retrieval

AWS CLI command:

```bash id="’wini196"
aws ecr get-login-password
```

This retrieves:

* Temporary registry password



---

# Piping Password Into Docker Login

The output gets piped into:

```bash id="’wini197"
docker login
```

using:

```bash id="’wini198"
--password-stdin
```

---

# Why `--password-stdin` Exists

This avoids:

* Password exposure in shell history
* Password visibility in process lists

More secure than:

* Passing password directly as argument

---

# Understanding the Pipe (`|`)

Conceptually:

```text id="’wini199"
Command 1 Output
↓
Becomes Input For Command 2
```

Very common Linux shell pattern.

---

# Full Authentication Flow

Conceptually:

```text id="’wini200"
AWS CLI
↓
Retrieve ECR Auth Token
↓
Pipe Token To Docker Login
↓
Authenticate Docker Client
```

---

# First Failure — Missing AWS Credentials

Initial error:

```text id="’wini201"
Unable to locate credentials
```

because:

* AWS CLI inside this stage lacked credentials

This problem already appeared earlier in ECS deployment stages.

---

# Fix — `withCredentials`

The Docker push stage must also use:

* Jenkins AWS credentials injection

Without credentials:

* AWS CLI cannot authenticate against AWS APIs

---

# Second Failure — Access Denied

New error:

```text id="’wini202"
AccessDeniedException
```

Specifically:

* `ecr:GetAuthorizationToken`

This introduces another IAM permissions issue.

---

# Root Cause

The Jenkins IAM user previously had permissions for:

* ECS
* S3

but NOT:

* ECR

AWS correctly denied registry operations.

---

# Fix — Add ECR Permissions

IAM policy attached:

```text id="’wini203"
AmazonEC2ContainerRegistryFullAccess
```

This grants:

* Push/pull access
* Authentication token access
* Repository management



---

# Important Security Observation

Again:

* FullAccess policies are broader than production best practice

But useful for:

* Learning
* Simpler setup

---

# Successful Push

After:

1. Adding credentials
2. Adding ECR permissions

the pipeline successfully:

* Authenticated to ECR
* Pushed Docker image

---

# Docker Push Internals

The logs show:

* Image layers uploaded individually

This is important because Docker images are:

* Layer-based filesystem structures

---

# Why Layer Uploads Matter

Docker can reuse unchanged layers later.

Benefits:

* Faster pushes
* Faster pulls
* Reduced bandwidth

This is one reason Docker is efficient.

---

# Verifying in ECR

Inside ECR repository:

* The pushed image tag becomes visible

Example:

```text id="’wini204"

```

Meaning:

* Registry storage successful
