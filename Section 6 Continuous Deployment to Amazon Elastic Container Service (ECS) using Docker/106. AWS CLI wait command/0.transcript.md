# Waiting for ECS Deployments to Finish Properly

The deployment pipeline was already functional, but it still had a major reliability issue:

```text id="’wini80"
The Pipeline Did Not Know When Deployment Was Actually Finished
```



---

# Important Observation

The commands:

```bash id="’wini81"
aws ecs register-task-definition
aws ecs update-service
```

execute very quickly.

But the actual ECS deployment process:

* Starting new containers
* Health checks
* Replacing old tasks

takes much longer.

---

# What Happens After `update-service`

After ECS receives the update request:

1. Pull new image
2. Start new task
3. Verify task health
4. Keep old task running temporarily
5. Remove old task
6. Reach stable state

This can take:

* Seconds
* Minutes

depending on the application.



---

# Why This Matters in CI/CD

Future pipeline stages may perform:

* Integration tests
* Health checks
* Smoke tests
* End-to-end testing

If tests start too early:

* Deployment may still be incomplete
* Containers may still be initializing
* Failures become unreliable/flaky

---

# Why `sleep 60` Is Bad

Naive solution:

```bash id="’wini82"
sleep 60
```

Problems:

* Too short sometimes
* Too long other times
* Environment dependent
* Non-deterministic
* Wastes pipeline time

This is considered poor CI/CD practice.

---

# AWS CLI Wait Commands

The lecture introduces an extremely important AWS CLI feature:

```text id="’wini83"
wait
```

Many AWS services implement:

* Waiter commands

These commands:

* Poll AWS internally
* Wait for desired state
* Exit only when operation stabilizes

---

# ECS Wait Command

The specific ECS waiter used:

```bash id="’wini84"
aws ecs wait services-stable
```

Purpose:

* Wait until ECS service deployment becomes stable



---

# What “Stable” Means

For ECS services, stable generally means:

* Desired number of tasks running
* Old tasks terminated
* New tasks healthy
* Deployment completed

---

# Command Structure

Example structure:

```bash id="’wini85"
aws ecs wait services-stable \
  --cluster <cluster-name> \
  --services <service-name>
```

Important:

* `--services` is plural

even when referencing only one service.

---

# Placement in Pipeline

The wait command is added AFTER:

```bash id="’wini86"
aws ecs update-service
```

Pipeline flow now becomes:

```text id="’wini87"
Register Task Definition
   ↓
Update ECS Service
   ↓
Wait Until Deployment Stable
   ↓
Continue Pipeline
```

---

# Important Behavioral Difference

Earlier pipeline:

```text id="’wini88"
Deployment Triggered
Pipeline Continues Immediately
```

New pipeline:

```text id="’wini89"
Deployment Triggered
↓
Pipeline Waits
↓
Deployment Verified Stable
↓
Pipeline Continues
```

This is significantly more reliable.

---

# Pipeline Duration Increased

Earlier:

```text id="’wini90"
~24 seconds
```

Now:

```text id="’wini91"
~4 minutes
```

The increase comes mostly from:

* Waiting for ECS stabilization

Not from AWS CLI execution itself.



---

# Why Longer Pipelines Are Sometimes Correct

Fast pipelines are NOT always better.

Reliable pipelines are better.

Waiting for infrastructure stabilization prevents:

* False positives
* Flaky tests
* Race conditions
* Broken deployments

---

# ECS Deployment Reality

During deployment ECS temporarily shows:

```text id="’wini92"
2/1 tasks running
```

because:

* Old container still alive
* New container starting

The waiter command waits until:

* ECS finishes reconciling desired state

---

# Timeout Behavior

Wait commands do not wait forever.

If stabilization takes too long:

* AWS CLI eventually times out
* Pipeline fails

This is good behavior because:

* It surfaces deployment problems automatically

# Refactoring Jenkins Configuration

The lecture then improves maintainability by reducing hardcoded values.

---

# The Problem with Hardcoded Configuration

Earlier commands repeatedly contained:

* Cluster names
* Service names
* Task definition names

Problems:

* Hard to maintain
* Difficult to reuse
* Error-prone during environment changes

---

# Solution — Environment Variables

Custom Jenkins environment variables introduced.

Examples:

```text id="’wini93"
AWS_ECS_CLUSTER
AWS_ECS_SERVICE_PROD
AWS_ECS_TD_PROD
```



---

# Why This Matters

Instead of changing multiple commands:

```text id="’wini94"
Change Configuration Once
Reuse Everywhere
```

This is standard CI/CD design practice.

---

# Variable Usage

Shell variable syntax:

```bash id="’wini95"
$VARIABLE_NAME
```

Variables dynamically resolve during execution.

---

# Resulting Improvement

Commands become:

```text id="’wini96"
Cleaner
Shorter
More Reusable
More Maintainable
```

---

# Environment Abstraction

This refactoring prepares for future scenarios like:

* Dev environment
* Test environment
* Production environment

Only variable values change.
Underlying deployment logic remains identical.

---

# Important DevOps Principle

This lecture demonstrates another major automation principle:

```text id="’wini97"

```

The deployment commands are:

* Logic

Cluster/service names are:

* Configuration
