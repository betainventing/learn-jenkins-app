# Why Docker Image Tagging Matters

Until now, the pipeline built Docker images like:

```text id="’wini166"
my-jenkins-app
```

The problem:

* Every new build overwrote the previous image.

This creates serious deployment and traceability problems.

---

# The Core Problem

Without proper tagging:

```text id="’wini167"
New Build
↓
Old Image Lost/Overwritten
```

You cannot reliably:

* Track versions
* Roll back deployments
* Identify builds
* Audit releases

---

# Why Containers Need Versioning

In CI/CD pipelines:

* Many builds are generated continuously

Each image should be:

* Uniquely identifiable

Very similar to:

* Application releases
* Git commits
* Software versions

---

# Docker Tag Concept

A Docker image tag acts like:

* Version identifier

General format:

```text id="’wini168"
image-name:tag
```

Example:

```text id="’wini169"
learn-jenkins-app:1.0.109
```

---

# Important Docker Terminology

| Part                | Meaning               |
| ------------------- | --------------------- |
| `learn-jenkins-app` | Repository/image name |
| `1.0.109`           | Tag/version           |

---

# Why Tags Matter Operationally

Tags help with:

| Capability   | Purpose                 |
| ------------ | ----------------------- |
| Rollbacks    | Redeploy older image    |
| Auditing     | Track deployment origin |
| Traceability | Identify exact build    |
| Stability    | Deploy known versions   |
| Debugging    | Reproduce issues        |

---

# Earlier Problematic Behavior

Earlier builds effectively behaved like:

```text id="’wini170"
learn-jenkins-app:latest
```

implicitly.

This is dangerous because:

* “latest” changes continuously
* Deployments become unpredictable

---

# Better Tagging Strategy

The lecture improves tagging by using:

* Application version variable

Example variable:

```text id="’wini171"
REACT_APP_VERSION
```

This gets appended to image tag.

---

# Resulting Build Command

Conceptually:

```bash id="’wini172"
docker build -t learn-jenkins-app:$REACT_APP_VERSION .
```

Now each image has:

* Explicit version identity

---

# Correlation Between Jenkins and Docker

The lecture demonstrates linking:

* Jenkins build number
  with
* Docker image version

Example:

```text id="’wini173"
Build #109
↓
Image Tag: 1.0.109
```

This creates strong deployment traceability.

---

# Why This Is Extremely Valuable

If production breaks:

```text id="’wini174"
Which Build Caused It?
```

becomes easy to answer.

You can immediately identify:

* Exact image
* Exact pipeline run
* Exact deployment artifact

---

# Rollback Example

Suppose:

```text id="’wini175"
1.0.110
```

introduces a bug.

You can redeploy:

```text id="’wini176"
1.0.109
```

immediately.

This is one of the biggest operational advantages of immutable container images.

---

# Refactoring Configuration into Variables

The lecture also improves maintainability.

Instead of hardcoding:

```text id="’wini177"
learn-jenkins-app
```

inside commands,
an environment variable is introduced:

```text id="’wini178"
APP_NAME
```

---

# Why This Matters

This follows another important DevOps principle:

```text id="’wini179"
Separate Configuration From Logic
```

Commands become reusable.
Configuration becomes centralized.

---

# Resulting Build Command Structure

Conceptually:

```bash id="’wini180"
docker build -t $APP_NAME:$REACT_APP_VERSION .
```

Cleaner and easier to maintain.

---

# Advantages of Environment Variables

Benefits:

| Benefit                   | Purpose                   |
| ------------------------- | ------------------------- |
| Centralized configuration | Easier maintenance        |
| Reusability               | Multiple environments     |
| Cleaner scripts           | Reduced duplication       |
| Scalability               | Easier pipeline evolution |

---

# Important CI/CD Principle

The image itself becomes:

* Deployment artifact

Meaning:

* The image uniquely represents a build result.

This is foundational in modern DevOps systems.

---

# Immutable Artifact Philosophy

Instead of:

* Modifying deployments in-place

modern systems create:

* New immutable artifacts

Examples:

```text id="’wini181"
learn-jenkins-app:1.0.107
learn-jenkins-app:1.0.108
learn-jenkins-app:1.0.109
```

Each image:

* Permanent
* Reproducible
* Independently deployable

---

# Relationship to ECS Deployments

Later ECS task definitions will reference:

```text id="’wini182"
specific-image:specific-tag
```

instead of:

* Ambiguous latest images

This improves:

* Deployment reliability
* Rollback safety
* Release management

---

# Why “latest” Is Often Discouraged

Using:

```text id="’wini183"
:latest
```

in production creates issues:

* Non-deterministic deployments
* Hard-to-debug failures
* Inconsistent environments

Explicit version tags are preferred.

---

# Pipeline Traceability Improvement

The pipeline now creates a full chain:

```text id="’wini184"
Git Commit
↓
Jenkins Build Number
↓
Docker Image Tag
↓
ECS Deployment
```

This traceability is extremely important in real production environments.
