This lecture explains the transition from:

# Time-based builds → Change-based builds

The goal is:

```text id="vww4ko"
Code changes
    ↓
Pipeline starts automatically
```

instead of manually clicking:

```text id="4u4lj0"
Build Now
```

or waiting for scheduled nightly builds. 

---

# The Real Problem

The instructor explains an important architectural separation:

| System  | Knows What         |
| ------- | ------------------ |
| GitHub  | code changed       |
| Jenkins | pipeline execution |

GitHub detects commits.

Jenkins does not automatically know those commits happened.

So some synchronization mechanism is required.

---

# Two Major Approaches

The lecture discusses two common CI/CD trigger models:

| Method   | Mechanism                             |
| -------- | ------------------------------------- |
| Webhooks | GitHub pushes notification to Jenkins |
| Poll SCM | Jenkins repeatedly checks GitHub      |

---

# 1. Webhooks (Best Approach)

The instructor calls this the more advanced option.

Architecture:

```text id="fw8x76"
Developer pushes code
        ↓
GitHub immediately sends HTTP request
        ↓
Jenkins receives webhook
        ↓
Pipeline starts instantly
```

This is:

# Event-driven CI/CD

---

# Why Webhooks Need Public Access

GitHub must reach Jenkins over HTTP/HTTPS.

Meaning Jenkins must be:

* publicly reachable
* DNS accessible
* firewall accessible
* webhook endpoint exposed

Example:

```text id="y9o39u"
https://jenkins.company.com/github-webhook/
```

GitHub sends POST requests there.

---

# Why This Is More Complex

Because now you must manage:

* HTTPS certificates
* reverse proxies
* firewall rules
* authentication
* webhook security
* public exposure risks

The instructor avoids this complexity for the course.

Reasonable for beginner/intermediate training.

---

# 2. Poll SCM (Git Polling)

Instead they use:

```text id="qzmp5l"
Poll SCM
```

This is:

# Pull-based synchronization

Instead of GitHub notifying Jenkins:

Jenkins repeatedly asks GitHub:

```text id="0nq07v"
"Did anything change?"
```

---

# Polling Flow

Conceptually:

```text id="q9f7zz"
Every minute:
    Jenkins checks GitHub
        ↓
If commit changed:
    trigger pipeline
Else:
    do nothing
```

---

# Important Difference

This is NOT:

```text id="zvsz8s"
build every minute
```

This is:

```text id="ymew7v"
check every minute
```

The build only runs if changes exist.

That distinction is extremely important.

---

# Why Polling Is Easier

Because:

* Jenkins initiates outbound connection
* GitHub does not need inbound access
* no public Jenkins exposure required
* easier firewall/networking
* simpler setup

This is why polling is common in internal/private infrastructure.

---

# Poll SCM Uses Cron Syntax Too

Just like periodic builds, Poll SCM also uses cron expressions.

Example:

```text id="uymweu"
H/15 * * * *
```

Meaning:

```text id="c3btjlwm"
Check every 15 minutes
```

---

# Important Jenkins Syntax Detail

The instructor explains a confusing edge case.

---

# Why `H/1` Does NOT Mean Every Minute

This surprises many Jenkins users.

Example:

```text id="6w5ttw"
H/1 * * * *
```

does not behave as expected.

Due to Jenkins cron hashing behavior, it effectively becomes hourly in this case.

---

# Correct "Every Minute" Syntax

To truly poll every minute:

```text id="jjlwm3"
* * * * *
```

Meaning:

| Field | Meaning       |
| ----- | ------------- |
| *     | every minute  |
| *     | every hour    |
| *     | every day     |
| *     | every month   |
| *     | every weekday |

---

# What Happens Internally During Polling

Conceptually Jenkins does something like:

```bash id="owec2c"
git ls-remote
```

or compares commit hashes.

It checks:

```text id="9l6z2d"
Has HEAD changed?
```

If current remote commit differs from last known commit:

trigger build.

---

# Important Optimization

Polling does NOT clone the entire repository every minute.

Usually Jenkins only:

* checks metadata
* compares refs/hashes
* detects new commit IDs

So polling is lighter than full builds.

---

# Git Polling Log

The instructor shows:

```text id="0u5qcy"
Git Polling Log
```

This is important operationally.

It helps diagnose:

* repository access problems
* authentication issues
* polling failures
* branch mismatch
* webhook/polling confusion

---

# Example Log Meaning

```text id="7jlwmv"
No changes
```

Means:

* polling worked
* repository reachable
* no new commit detected

---

# Triggered Build Reason

When a commit appears, Jenkins starts the build.

Then logs show:

```text id="5n0q9z"
Started by SCM change
```

Meaning:

# SCM-triggered pipeline

SCM = Source Code Management.

Usually Git.

---

# Difference From Manual Trigger

Manual build log:

```text id="yej0pi"
Started by user
```

Polling-triggered build:

```text id="2vz1pn"
Started by SCM change
```

This distinction matters operationally and for auditing.

# Important CI/CD Principle

This lecture introduces:

# Change Detection Automation

Modern CI/CD pipelines are reactive systems.

They respond to:

* commits
* pull requests
* tags
* merges
* releases

instead of relying on humans.

---

# Polling vs Webhooks Tradeoff

| Feature                 | Polling          | Webhooks     |
| ----------------------- | ---------------- | ------------ |
| Setup simplicity        | Easy             | Harder       |
| Real-time response      | Delayed          | Immediate    |
| Public Jenkins required | No               | Yes          |
| GitHub traffic          | Low              | Event-driven |
| Jenkins overhead        | Constant polling | Minimal      |
| Enterprise preference   | Sometimes        | Usually      |

---

# Why Polling Every Minute Can Become Expensive

Imagine:

* 2000 Jenkins jobs
* polling every minute

That becomes:

```text id="6ceiqj"
2000 Git checks/minute
```

This creates:

* API load
* network overhead
* GitHub rate limiting
* Jenkins scheduler pressure

Large organizations therefore prefer webhooks.

---

# Important Real-World Evolution

Typical CI/CD maturity progression:

```text id="jlwmic"
Manual builds
    ↓
Scheduled builds
    ↓
SCM polling
    ↓
Webhooks
    ↓
Event-driven pipelines
```

This lecture moves from stage 2 → stage 3.

---

# Biggest Conceptual Takeaway

This lecture teaches the core CI/CD automation idea:

# Pipelines should react automatically to source code changes.

And Poll SCM is an intermediate solution that simulates event-driven behavior by repeatedly checking the repository for updates.
