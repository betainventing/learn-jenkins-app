This lecture is teaching how CI/CD pipelines identify the **deployment target**.

Before Jenkins can deploy anything, Netlify CLI must know:

```text id="vdr0dr"
Which exact Netlify site should receive this deployment?
```

---

# Why the Site ID is required

Inside Netlify, each website/project has:

* site name
* URL
* internal unique identifier (Site ID)

Example:

```text id="m75cv1"
Site Name: my-react-app
```

can change later.

But:

```text id="akylza"
Site ID: 12345678-abcd-efgh-ijkl-987654321
```

is immutable and globally unique.

---

# Important DevOps principle

Automation should use:

* stable identifiers
* immutable references

NOT:

* display names
* labels
* UI text

Because names can change.

IDs usually do not.

This is true across almost all platforms:

| Platform   | Stable Identifier |
| ---------- | ----------------- |
| AWS        | ARN / resource ID |
| Kubernetes | UID               |
| GitHub     | repository ID     |
| Docker     | image digest      |
| Netlify    | Site ID           |

---

# What Jenkins is doing now

The pipeline now includes:

```groovy id="5qgk1t"
environment {
    NETLIFY_SITE_ID = "..."
}
```

This creates an environment variable available to:

* shell scripts
* npm commands
* Netlify CLI

---

# Important naming detail

The instructor emphasizes:

```text id="m9zfxz"
NETLIFY_SITE_ID
```

must be exact.

Because Netlify CLI automatically checks for this environment variable internally.

This is a very common CLI design pattern.

---

# How CLIs commonly work

Many tools automatically inspect environment variables.

Examples:

| Tool       | Environment Variable |
| ---------- | -------------------- |
| AWS CLI    | AWS_ACCESS_KEY_ID    |
| Docker     | DOCKER_HOST          |
| Kubernetes | KUBECONFIG           |
| Terraform  | TF_VAR_*             |
| Netlify    | NETLIFY_SITE_ID      |

This allows:

* automation
* scripting
* non-interactive execution

without manually passing arguments every time.

---

# What happens internally

When Jenkins runs:

```bash id="0sckbi"
netlify deploy
```

Netlify CLI internally does something conceptually like:

```javascript id="x57o62"
if (process.env.NETLIFY_SITE_ID) {
    deployToThatSite()
}
```

So the environment variable becomes deployment context.

---

# Why environment variables are heavily used in CI/CD

Because they:

* separate config from code
* avoid hardcoding
* work across environments
* are easy to inject dynamically
* are supported by almost every CI system

# Important Jenkins concept

The `environment` block in Jenkins declarative pipelines:

```groovy id="5oxhz8"
pipeline {
    environment {
        ...
    }
}
```

creates variables globally for all stages.

Variables become accessible:

* in shell commands
* in Groovy interpolation
* in subprocesses

---

# Important security consideration

This lecture uses a public/non-sensitive value:

```text id="yzzx0r"
NETLIFY_SITE_ID
```

This is generally okay.

But later authentication tokens should NOT be hardcoded.

Sensitive values should use:

* Jenkins Credentials Store
* secret injection
* credential bindings

NOT:

```groovy id="h0uk3y"
TOKEN = "my-secret-token"
```

inside Jenkinsfile.

# Why this matters in real-world DevOps

In enterprise environments you may deploy to:

* staging
* QA
* production
* development
* customer-specific environments

Environment variables help pipelines dynamically decide:

```text id="m4x3kh"
Which infrastructure should receive deployment?
```

Very common pattern:

```text id="ln31r8"
DEV_SITE_ID
STAGING_SITE_ID
PROD_SITE_ID
```

with deployment depending on:

* Git branch
* release tag
* approval workflow
