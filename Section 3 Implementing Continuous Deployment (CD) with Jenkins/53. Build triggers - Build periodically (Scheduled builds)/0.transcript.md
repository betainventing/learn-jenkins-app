This lecture explains one of the most important CI/CD concepts:

# Build Triggers

Meaning:

> What event should cause Jenkins to start a pipeline?

The instructor compares manual builds to a rotary phone because manual triggering does not scale for real CI/CD systems. 

---

# Manual Build vs Automated Trigger

So far the pipeline was triggered using:

```text id="z6ewzs"
Build Now
```

This is:

* useful for testing
* useful during setup
* useful for debugging

But not ideal for production CI/CD.

Real pipelines should trigger automatically.

---

# Build Periodically

The lecture focuses on this Jenkins trigger:

```text id="nsv3xu"
Build periodically
```

This allows Jenkins to execute jobs on a schedule.

Internally this is essentially Jenkins integrating cron scheduling into the CI/CD system.

---

# What Cron Is

The instructor mentions:

> cron comes from chronos

Cron is a Unix/Linux scheduling mechanism.

In Linux you may already know:

```bash id="7xw9pc"
crontab -e
```

Jenkins uses a cron-like syntax for scheduling jobs.

---

# Cron Expression Structure

Jenkins cron syntax has 5 fields:

```text id="0zvtbb"
MINUTE HOUR DAY_OF_MONTH MONTH DAY_OF_WEEK
```

Example:

```text id="5odx4h"
0 3 * * 1-5
```

means:

```text id="h7gn3i"
Run at 03:00 AM Monday-Friday
```

---

# Field Breakdown

## Minute

```text id="3aljz2"
0
```

Range:

```text id="wcehy9"
0-59
```

---

## Hour

```text id="3zvjlwm"
3
```

Range:

```text id="krq9br"
0-23
```

24-hour format.

---

## Day of Month

```text id="wd5wzi"
*
```

`*` means:

```text id="cw0x5m"
any value
```

So:

```text id="q1djlwm"
every day of month
```

---

## Month

```text id="q5fz7g"
*
```

Means:

```text id="0kexlf"
every month
```

---

## Day of Week

```text id="6w6fr0"
1-5
```

Means:

```text id="4k3m2x"
Monday through Friday
```

because:

| Value | Day    |
| ----- | ------ |
| 0     | Sunday |
| 1     | Monday |
| 5     | Friday |

---

# Final Meaning

So:

```text id="n1jwev"
0 3 * * 1-5
```

means:

```text id="ox1xk3"
Run every weekday at 3:00 AM
```

# Why Scheduled Builds Exist

The instructor gives several valid use cases.

---

# 1. Long Running Jobs

Some jobs take hours:

* integration tests
* security scans
* full regression suites
* large builds
* data pipelines

Running them overnight optimizes resource usage.

---

# 2. Maintenance Validation

Even inactive projects may break because dependencies change.

Examples:

* npm packages updated
* Docker base image changed
* SSL certificates expired
* external APIs changed
* package repositories unavailable

Periodic builds detect environmental drift.

This is a very important real-world DevOps problem.

---

# Important CI/CD Principle

A project can break even if source code never changes.

Because software depends on external systems.

---

# Why Polling Frequently Is Bad

The instructor explains:

running every minute wastes resources.

Correct.

Because if no code changed:

* CPU wasted
* agents wasted
* storage wasted
* queue congestion increases

This becomes serious at enterprise scale.

---

# Why Jenkins Warns About `0`

The lecture then explains this warning:

```text id="qfrhuj"
Use H instead of 0
```

This is a Jenkins-specific optimization.

---

# What `H` Means in Jenkins

This is NOT standard Linux cron.

In Jenkins:

```text id="v0u5hm"
H
```

means:

# Hash-based scheduling

Jenkins computes a deterministic value based on:

* job name
* internal hashing algorithm

So instead of:

```text id="0lv52p"
03:00
```

different jobs may run at:

```text id="n6n1gq"
03:12
03:37
03:56
03:04
```

---

# Why This Matters

Without `H`, imagine 500 pipelines:

```text id="87rjrh"
0 0 * * *
```

At midnight:

* all jobs start simultaneously
* CPU spikes
* disk IO spikes
* agent starvation occurs
* Jenkins may freeze

This is called:

# Thundering Herd Problem

Many systems acting simultaneously overload infrastructure.

---

# Jenkins Solves This Using Hash Distribution

Example:

```text id="z55gr7"
H 3 * * 1-5
```

Means:

```text id="dr5h8q"
Run sometime during 3 AM hour on weekdays
```

But each job gets a stable minute.

Example:

| Job            | Actual Time |
| -------------- | ----------- |
| frontend-build | 3:12        |
| backend-build  | 3:44        |
| security-scan  | 3:56        |

This distributes load.

---

# Important Detail

The hash is deterministic.

Meaning:

same job name → same scheduled minute.

So jobs remain predictable.

---

# Jenkins Is Solving Infrastructure Scaling Problems

This is an important lesson.

CI/CD systems are infrastructure systems themselves.

Large Jenkins installations may run:

* thousands of pipelines
* hundreds of agents
* millions of builds

Scheduling optimization becomes critical.

---

# Why Periodic Builds Are Still Not Ideal for CI

The instructor then says:

> this doesn't really help us

Meaning:

scheduled builds are still inferior for active development workflows.

Because developers want:

# Immediate Feedback

Example:

```text id="1jlwm6"
git push
    ↓
pipeline starts immediately
    ↓
tests fail quickly
```

Waiting until 3 AM defeats CI principles.

---

# Real CI/CD Goal

The ideal trigger is:

# Event-driven automation

Meaning:

```text id="p9km8r"
Code change
   ↓
Webhook
   ↓
Jenkins pipeline starts
```

not time-based scheduling.

---

# Periodic Builds vs Event-Based Builds

| Trigger Type  | Good For                 |
| ------------- | ------------------------ |
| Manual        | testing/debugging        |
| Scheduled     | maintenance/nightly jobs |
| Webhook/Event | real CI/CD               |

---

# Why Nightly Builds Still Exist

Even modern companies still use nightly jobs for:

* regression testing
* dependency scanning
* performance benchmarks
* backups
* reporting
* compliance scans

So scheduled builds remain important.

---

# Important Linux Connection

Since you work with Linux and DevOps:

Jenkins cron syntax is very close to Linux cron.

Example Linux cron:

```bash id="2srgn8"
0 3 * * 1-5 /opt/scripts/build.sh
```

Jenkins essentially embeds this scheduling model into CI/CD orchestration.
