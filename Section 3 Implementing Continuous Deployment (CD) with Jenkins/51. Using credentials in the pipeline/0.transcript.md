This section explains how Jenkins securely injects the Netlify token into the pipeline runtime so the Netlify CLI can authenticate automatically.

---

# Critical Concept

The Netlify CLI does not magically know your token.

It specifically looks for this environment variable:

```bash
NETLIFY_AUTH_TOKEN
```

This variable name is predefined by Netlify CLI itself.

That means:

* the name must match exactly
* wrong capitalization = failure
* typo = failure
* different variable name = ignored

Same idea as:

```bash
NETLIFY_SITE_ID
```

The CLI has internal logic like:

```javascript
process.env.NETLIFY_AUTH_TOKEN
```

If found:
use token.

If not:
authentication fails.

---

# What Jenkins Is Doing

Instead of hardcoding:

```groovy
environment {
    NETLIFY_AUTH_TOKEN = "my-secret-token"
}
```

they use:

```groovy
environment {
    NETLIFY_AUTH_TOKEN = credentials('netlify-token')
}
```

This is a Jenkins pipeline helper function.

---

# What `credentials()` Actually Does

This line:

```groovy
credentials('netlify-token')
```

means:

1. Go to Jenkins Credentials Store
2. Find credential whose ID is:

   ```text
   netlify-token
   ```
3. Retrieve secret securely
4. Inject it into runtime environment variable

So at runtime Jenkins effectively creates:

```bash
NETLIFY_AUTH_TOKEN=actual_secret_value
```

But without exposing it in source control.

---

# Very Important Detail

The credential ID:

```text
netlify-token
```

is NOT the secret itself.

It is only the lookup key inside Jenkins.

Think of it like:

| Item          | Purpose         |
| ------------- | --------------- |
| Credential ID | Label/reference |
| Secret Value  | Actual token    |

---

# Runtime Injection

The secret only exists temporarily during pipeline execution.

This is important security behavior.

Typical lifecycle:

```text
Pipeline starts
    ↓
Jenkins retrieves secret
    ↓
Injects into environment
    ↓
CLI uses token
    ↓
Pipeline ends
    ↓
Environment destroyed
```

This minimizes secret exposure duration.

---

# Why This Is Secure

The token is:

* not stored in Git
* not stored in Jenkinsfile
* not visible in UI
* masked in logs
* centrally managed

This is the standard enterprise CI/CD approach.

# Netlify Status Command

They then test authentication using:

```bash
netlify status
```

This is basically a verification command.

Instead of directly deploying immediately, they first validate:

* token works
* site ID works
* CLI authentication works
* Jenkins credential injection works

This is good pipeline engineering practice.

---

# Why Verification Stages Matter

In CI/CD, debugging deployment failures late is expensive.

So engineers commonly create validation stages like:

| Validation                  | Purpose            |
| --------------------------- | ------------------ |
| npm --version               | tool exists        |
| docker info                 | daemon reachable   |
| kubectl cluster-info        | cluster reachable  |
| aws sts get-caller-identity | AWS auth works     |
| netlify status              | Netlify auth works |

This isolates problems early.

# Important Security Observation

Notice something important:

The logs show metadata:

* username
* site URL
* site ID

But NOT the token itself.

This is intentional.

Jenkins masks credentials automatically.

Even if a command accidentally prints the token, Jenkins often replaces it with:

```text
****
```

This is credential masking.

# What Happens Internally During `netlify status`

Conceptually:

```text
Jenkins starts pipeline
        ↓
Injects NETLIFY_AUTH_TOKEN
        ↓
Injects NETLIFY_SITE_ID
        ↓

netlify status
        ↓

        ↓
Netlify validates token
        ↓
Netlify returns account/site info
        ↓
CLI prints status
```

# Important DevOps Pattern

This lecture demonstrates a very common pattern:

# CLI Tool + Environment Variables + CI/CD Secret Store

You will repeatedly see this with:

| Tool        | Auth Variable      |
| ----------- | ------------------ |
| AWS CLI     | AWS_ACCESS_KEY_ID  |
| Docker      | DOCKER_AUTH_CONFIG |
| GitHub CLI  | GITHUB_TOKEN       |
| Terraform   | TF_TOKEN           |
| npm         | NPM_TOKEN          |
| Kubernetes  | KUBECONFIG         |
| Netlify CLI | NETLIFY_AUTH_TOKEN |

This is foundational DevOps workflow design.

---

# Why Environment Variables Are Popular for Authentication

Because they:

* are easy for CLIs to read
* work across operating systems
* avoid interactive login
* integrate cleanly with CI/CD
* disappear after process termination

They are ideal for automation systems.

---

# Important Security Limitation

Environment variables are convenient, but not perfect security.

Inside the running process/container:

* privileged users may still read them
* process dumps may expose them
* accidental echo statements may leak them

So enterprise systems additionally use:

* secret managers
* temporary credentials
* IAM roles
* workload identity
* Vault integrations

But for Jenkins + Netlify CI/CD, this approach is standard and acceptable.
