This lecture explains a very important CI/CD optimization pattern:

> Separate infrastructure preparation from application execution.

The instructor is improving pipeline architecture by removing Docker image building from the main CI pipeline.

---

# The Problem With Current Design

Previously the pipeline did this:

```text id="d2q1mk"
Build Docker image
    ↓
Run tests
    ↓
Deploy
```

Problem:

Every pipeline execution spends time rebuilding the image.

Even if:

* Dockerfile did not change
* dependencies did not change
* tools did not change

This wastes:

* CPU
* storage I/O
* network bandwidth
* pipeline execution time

---

# Important CI/CD Principle

Your application pipeline should focus on:

* build
* test
* deploy

NOT on repeatedly preparing infrastructure.

---

# The Optimization

Instead of:

```text id="m0mlk7"
Build image every pipeline run
```

the instructor moves image creation into a separate scheduled pipeline.

---

# New Architecture

## Nightly Pipeline

Runs once daily:

```text id="19b6n9"
Build custom image
```

---

## Main Application Pipeline

Simply reuses image:

```text id="o9f2hl"
Use existing image
    ↓
Run tests
    ↓
Deploy
```

This is much more scalable.

---

# Extremely Important Enterprise Pattern

This is how large CI/CD systems are typically designed.

They separate:

| Pipeline Type           | Responsibility         |
| ----------------------- | ---------------------- |
| Infrastructure pipeline | Build CI images        |
| Application pipeline    | Build/test/deploy apps |

---

# Why This Is Better

Suppose:

* 100 developers trigger pipelines daily
* each image build takes 1 minute

Old design:

```text id="fq0sxa"
100 × 1 minute = 100 minutes/day
```

wasted rebuilding same image.

New design:

```text id="17hh1t"
1 nightly build
```

Huge resource savings.

---

# The New Jenkinsfile

The instructor creates:

```text id="65prqk"
Jenkinsfile-nightly
```

This is a separate pipeline definition.

Important detail:

Only:

```text id="w8yhrc"
Jenkinsfile
```

is special by default in Jenkins.

Any other filename requires explicit configuration.

---

# What the Nightly Pipeline Does

The nightly pipeline becomes extremely simple:

```text id="5a0m7f"
Build Docker image only
```

No:

* tests
* deployment
* application logic

---

# Important Architectural Shift

The image itself becomes a reusable platform artifact.

Example:

```text id="xgx71r"
my-playwright
```

is now treated similarly to:

* binaries
* libraries
* release artifacts

---

# Why Scheduled Builds Are Useful

Nightly builds can:

* refresh dependencies
* apply security updates
* rebuild against updated base images
* validate Dockerfile integrity

without slowing daytime developer workflows.

---

# Important Hidden Docker Detail

Base images themselves change over time.

Example:

```dockerfile id="o5ow6s"
FROM node:18-alpine
```

may receive:

* security patches
* updated Alpine packages
* bug fixes

Nightly rebuilds help keep derived images updated.

---

# Important Missing Production Step

The lecture simplifies one major real-world detail.

Currently the image is likely only stored locally on the Jenkins machine.

Enterprise systems usually:

```text id="n7bclo"
Build image
    ↓
Push to registry
```

Example:

```bash id="3p4z76"
docker push company/my-playwright:v1
```

Then pipelines pull image when needed.

---

# Why Registries Matter

Without a registry:

* images exist only locally
* scaling Jenkins agents becomes difficult
* distributed builds fail
* Kubernetes workers cannot access images

Registries solve this.

# Script Path Concept

Normally Jenkins looks for:

```text id="drgb4t"
Jenkinsfile
```

But for custom filenames:

```text id="4x6u40"
Jenkinsfile-nightly
```

you must configure:

```text id="r7a8ui"
Script Path
```

inside Jenkins job configuration.

Very important Jenkins detail.

---

# Scheduled Builds in Jenkins

The instructor enables:

```text id="24immb"
Build periodically
```

This uses Jenkins cron syntax.

Example:

```text id="q0gny5"
H 2 * * *
```

Meaning:

* once daily
* around 2 AM

Jenkins often uses `H` for load balancing scheduled jobs.

---

# Important Operational Reality Mentioned

If Jenkins runs on:

```text id="mkk10v"
local laptop
```

and laptop is powered off:

Scheduled jobs do not execute.

In production:

Jenkins typically runs on:

* dedicated servers
* VMs
* Kubernetes
* cloud infrastructure

which remain online continuously.

# Key Infrastructure Principle

The instructor is moving toward:

> persistent reusable infrastructure artifacts

instead of:

> ephemeral repeatedly rebuilt environments

This is mature CI/CD design.

---

# Another Important Benefit

Removing image builds from main pipelines also reduces:

* pipeline complexity
* failure surface area
* dependency instability
* external network dependency

Main pipelines become more deterministic.

---

# Hidden Security Benefit

Nightly image rebuilds help integrate:

* updated packages
* patched vulnerabilities
* refreshed dependencies

This is important for container security hygiene.

---

# Important Limitation of Current Design

Current setup still depends on:

```text id="lq4hvv"
latest local image
```

This can eventually cause:

* drift
* inconsistencies
* reproducibility problems

Production systems solve this using:

* immutable tags
* registries
* versioned images

Example:

```text id="a8f3bz"
my-playwright:v12
```

instead of:

```text id="c87o91"
my-playwright
```

---

# Most Important Lesson From This Lecture

The biggest takeaway is:

> Build reusable CI environments separately from application pipelines.

This creates:

* faster pipelines
* cleaner architecture
* reusable execution environments
* better scalability
* lower infrastructure cost

This separation is a hallmark of mature DevOps systems.
