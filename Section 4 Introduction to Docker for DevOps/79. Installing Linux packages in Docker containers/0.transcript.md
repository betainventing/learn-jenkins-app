This lecture explains how to install Linux packages inside Docker-based Jenkins agents without depending on Node.js tooling. It also introduces several extremely important Linux and container concepts. 

# The Main Lesson

The instructor is teaching:

> Docker images depend on their underlying Linux distribution.

Different Linux distributions use different:

* package managers
* package repositories
* installation commands

You must know which Linux distribution your container image uses.

---

# Initial Pipeline Setup

The pipeline uses:

```groovy id="1b7u6l"
image 'python:3-alpine'
```

Important detail:

This is NOT just Python.

It is:

```text id="7z7e4x"
Python + Alpine Linux
```

The underlying OS matters heavily.

---

# Goal

Install:

```text id="74jkf7"
jq
```

inside the container.

`jq` is a Linux CLI tool for JSON parsing.

Very common in DevOps pipelines.

---

# First Failure: `npm not found`

The instructor intentionally runs:

```bash id="zvdb0g"
npm install node-jq
```

inside a Python image.

Result:

```text id="lchwr4"
npm: not found
```

Why?

Because:

* Python image contains Python runtime
* it does NOT contain Node.js
* therefore npm is absent

This is expected.

---

# Important DevOps Principle

Do not install unnecessary runtimes just to obtain one utility.

Bad approach:

```text id="vf8f5x"
Install Node.js only to get jq
```

Better approach:

```text id="wwl1q5"
Use native Linux package manager
```

This is cleaner and lighter.

---

# Alpine Linux Package Manager

Alpine uses:

```text id="hwdchm"
apk
```

Package installation command:

```bash id="phb3lp"
apk add jq
```

---

# Important Linux Distribution Difference

Different Linux distributions use different package managers.

| Distribution  | Package Manager |
| ------------- | --------------- |
| Alpine        | `apk`           |
| Ubuntu/Debian | `apt`           |
| RHEL/CentOS   | `yum` / `dnf`   |
| SUSE          | `zypper`        |
| Arch          | `pacman`        |

This is foundational Linux administration knowledge.

---

# Second Failure: Permission Denied

After using:

```bash id="x81j5v"
apk add jq
```

the pipeline fails with:

```text id="y2rysv"
permission denied
```

Why?

Because container is NOT running as root.

---

# Extremely Important Container Security Concept

Modern containers often run as:

```text id="04a29t"
non-root users
```

for security reasons.

Why?

If application/container is compromised:

* attacker gets limited privileges
* damage is reduced

This is considered container security best practice.

---

# Why Installation Failed

Installing Linux packages modifies:

* system directories
* package databases
* executable paths

These operations require root privileges.

---

# Jenkins Docker Agent `args`

Instructor uses:

```groovy id="sbd0ca"
args '-u root'
```

Meaning:

```text id="a0zklm"
Run container as root user
```

---

# Docker `-u` Flag

Equivalent raw Docker command:

```bash id="n3zcr9"
docker run -u root ...
```

This overrides container runtime user.

---

# Why This Solves the Problem

Now package manager has permission to:

* modify filesystem
* install packages
* update package databases

So:

```bash id="4x1v7j"
apk add jq
```

works successfully.

---

# Important Warning About Root Containers

The instructor gives a very important operational warning.

If Jenkins workspace is shared and container runs as root:

Files created inside container may become owned by:

```text id="u1dr0w"
root
```

Then Jenkins (running as non-root user) may later fail to:

* delete files
* clean workspace
* archive artifacts

This is a very common CI/CD issue.

---

# Real-World Example

Suppose container creates:

```text id="stbjk8"
/workspace/build-output
```

owned by:

```text id="v5idui"
root:root
```

Later Jenkins cleanup step may fail:

```text id="dwb3px"
Permission denied
```

Very common operational problem.

---

# Why Running as Root Is Risky

Root containers can:

* modify mounted volumes
* alter workspace ownership
* increase security risk

Therefore many organizations avoid root containers entirely.

---

# Better Production Practice

Instead of installing packages dynamically:

Build custom image beforehand.

Example:

```dockerfile id="6vf7e9"
FROM python:3-alpine

RUN apk add --no-cache jq
```

Then pipeline simply uses prebuilt image.

This is cleaner and safer.

---

# Fourth Failure: `Unable to locate package jq`

This is extremely important Linux administration behavior.

Why?

Because package metadata is outdated or missing.

---

# Why `apt update` Is Required

Ubuntu/Debian package management works using local repository metadata cache.

Before installing packages:

```bash id="s8ndpg"
apt update
```

downloads latest package indexes.

Then:

```bash id="wm6j30"
apt install jq
```

can resolve packages properly.

---

# Important Linux Workflow

Typical Debian/Ubuntu flow:

```bash id="d80ozt"
apt update
apt install package-name
```

Very important operational habit.

---

# Fifth Failure: Interactive Prompt

During installation:

```text id="ktb7x3"
Do you want to continue? [Y/n]
```

appears.

Problem:

CI/CD pipelines are non-interactive.

Jenkins cannot manually answer prompts.

---

# Solution: `-y`

Command:

```bash id="jlwmnr"
apt install -y jq
```

Meaning:

```text id="b4wk9q"
Automatically answer "yes"
```

to prompts.

---

# Extremely Important Automation Principle

Automation scripts must be:

```text id="cy5hct"
non-interactive
```

Any command requiring human input can block pipelines indefinitely.

---

# Real-World CI/CD Practice

Production automation usually uses:

```bash id="mbq7rt"
apt-get update && apt-get install -y jq
```

or:

```bash id="uj2r90"
DEBIAN_FRONTEND=noninteractive
```

to fully suppress prompts.

---

# Hidden Important Difference: `apt` vs `apt-get`

The lecture uses:

```bash id="fqiw1k"
apt
```

In automation, many engineers prefer:

```bash id="c8xqg3"
apt-get
```

because:

* more stable scripting interface
* intended for automation
* less interactive behavior

Very common DevOps preference.
