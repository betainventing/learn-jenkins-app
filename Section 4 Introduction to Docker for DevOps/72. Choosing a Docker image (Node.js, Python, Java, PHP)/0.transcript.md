This lecture explains how to choose proper Docker images for Jenkins pipelines and how Docker image tags work. It also explains why lightweight images like Alpine are commonly used in CI/CD. 

# The Main Problem Being Solved

In Jenkins pipelines, builds need tools and runtimes.

Examples:

| Project Type | Required Runtime |
| ------------ | ---------------- |
| Node.js app  | Node.js          |
| Python app   | Python           |
| Java app     | JDK              |
| PHP app      | PHP              |

Instead of manually installing everything on Jenkins:

```text id="z5tt3r"
Install Node
Install Python
Install Java
Install PHP
```

we use Docker images that already contain those tools.

This creates:

* reproducible builds
* isolated environments
* easier maintenance
* cleaner Jenkins servers

The instructor’s project is a Node.js project.

* Node.js runtime

Without Node.js:


# What Is a Docker Tag?

A tag identifies a specific image version/variant.

Examples:

```text id="ezlqu8"
node:18
node:20
node:22
python:3.12
python:3-alpine
```

Without tags:

Docker would not know:

* version
* OS variant
* included tools

---

# Why Version Selection Matters

The transcript explains an important production concept:

> Applications are often built and tested against specific runtime versions.

Example:

Project developed using:

```text id="yqv0sn"
Node.js 18
```

Running it on:

```text id="0m1i0j"
Node.js 22
```

may introduce:

* dependency incompatibilities
* deprecated APIs
* build failures
* runtime errors

Therefore pipelines usually pin runtime versions.

# `node:18` vs `node:18-alpine`

## `node:18`

Regular full image.

Includes:

* Debian-based Linux
* many utilities
* larger filesystem

Size mentioned:

~400 MB

---

## `node:18-alpine`

Uses Alpine Linux.

Alpine is:

* minimal Linux distribution
* optimized for containers
* extremely lightweight

Size mentioned:

~42 MB

Huge difference.

# Why Smaller Images Matter

In CI/CD:

Every pipeline run may need to:

1. pull image
2. create container
3. start environment

Larger images mean:

* slower startup
* higher bandwidth usage
* slower scaling
* larger storage consumption

# Important Tradeoff With Alpine

The lecture simplifies Alpine a bit.

Real-world detail:

Alpine is small because it uses:

```text id="9h6a4o"
musl libc
```

instead of:

```text id="gmghsz"
glibc
```

Implications:

Some software or native binaries may fail or behave differently.

So Alpine is excellent for:

* simple CI pipelines
* lightweight applications

But sometimes problematic for:

* native dependencies
* compiled libraries
* enterprise software

This is why many companies also use:

```text id="h2r52y"
-slim
```

images instead.

# Version Pinning vs Floating Tags

This section briefly introduces an important concept.

## Floating Tag

```text id="ysvag3"
python:3
```

Means:

> latest Python 3.x version

Can change over time.

Risk:

Pipeline behavior may suddenly change after upstream updates.

---

## Fixed Tag

```text id="4s3x2f"
python:3.10.13
```

Fully deterministic.

Safer for production CI/CD.

---

# Why There Are So Many Tags

Tags may represent:

| Tag Component     | Meaning                      |
| ----------------- | ---------------------------- |
| version           | `18`, `22`, `3.12`           |
| OS variant        | `alpine`, `slim`, `bullseye` |
| included software | `apache`, `cli`              |
| architecture      | arm64/amd64                  |
| security patches  | updated rebuilds             |

| `php:8-apache` | includes Apache |
| `php:8-fpm`    | PHP-FPM mode    |

This demonstrates:

Docker images are often purpose-specific.

# Core CI/CD Principle Here

The pipeline environment should be:

* explicit
* versioned
* reproducible
* isolated

Instead of saying:

```text id="j61o0c"
"Use whatever Python is installed"
```

you define:

```groovy id="t3kg4i"
agent {
    docker {

```

This removes ambiguity.

# Real-World Best Practice

Typical production recommendations:

| Use Case              | Recommendation      |
| --------------------- | ------------------- |
| Fast CI               | Alpine/slim         |
| Production runtime    | slim/distroless     |
| Maximum compatibility | Debian/Ubuntu-based |
| Reproducibility       | fixed version tags  |
| Security              | minimal images      |
