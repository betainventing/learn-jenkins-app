# Deploying the Actual Website Build to Amazon S3

This lecture transitions from:

```text id="jlwm63"
Uploading a single test file
```

to:

```text id="jlwm11"
Deploying the real frontend build output
```

using Jenkins, AWS Command Line Interface, and Amazon S3. 

---

# Previous Approach vs Real Deployment

Earlier deployment:

```bash id="jlwm75"
aws s3 cp index.html s3://bucket/index.html
```

This uploads only one file.

Real frontend applications contain many files:

* HTML
* CSS
* JS bundles
* Images
* Source maps
* Fonts

Uploading file-by-file is not practical.

---

# AWS S3 `sync`

Correct production-oriented command:

```bash id="jlwm04"
aws s3 sync
```

Purpose:

```text id="jlwm92"
Synchronize local directory with S3 bucket
```



---

# What `sync` Actually Does

`sync` compares:

| Local Build Directory | S3 Bucket |
| --------------------- | --------- |

Then automatically:

* Uploads new files
* Updates changed files
* Skips unchanged files
* Optionally deletes removed files

This is far more suitable for CI/CD deployments.

---

# Build Output Directory

The frontend build stage already generates:

```text id="jlwm58"
build/
```

This directory contains the deployable frontend assets.

Example:

```text id="jlwm16"
build/
├── index.html
├── static/
├── assets/
├── js/
└── css/
```

---

# New Deployment Command

Pipeline command becomes:

```bash id="jlwm37"
aws s3 sync build s3://$AWS_S3_BUCKET
```



---

# Command Breakdown

| Part       | Meaning                   |
| ---------- | ------------------------- |
| `aws`      | AWS CLI                   |
| `s3`       | S3 service                |
| `sync`     | Synchronization operation |
| `build`    | Local source directory    |
| `s3://...` | Destination bucket        |

---

# Why `sync` Is Smarter Than `cp`

Using `cp` would require:

```text id="jlwm83"
Manually uploading every file
```

Problematic because frontend builds:

* Generate hashed filenames
* Change asset names between builds
* Produce many nested directories

`sync` handles this automatically.

# Deployment Failure Encountered

Error:

```text id="jlwm98"
The user-provided path build does not exist
```



---

# Root Cause

Very important Jenkins/Docker behavior.

Each Docker agent container may start with:

```text id="jlwm54"
Fresh isolated workspace
```

The build artifacts were created in another workspace/container.

So:

```text id="jlwm71"
build/
```

did not exist inside the AWS CLI container.

---

# Jenkins Workspace Isolation

Without special configuration:

```text id="jlwm29"
Stage A container
≠
Stage B container
```

Each container may have different filesystems/workspaces.

This is a common CI/CD issue.

---

# Solution — `reuseNode true`

The build stage already used:

```groovy id="jlwm47"
reuseNode true
```

This tells Jenkins:

```text id="jlwm14"
Reuse same workspace on same node
```

Now the AWS deployment container can access:

```text id="jlwm88"
build/
```

created earlier. 

---

# Important DevOps Lesson

This demonstrates a major CI/CD concept:

```text id="jlwm32"
Containers are ephemeral and isolated.
```

Artifacts do not automatically persist between stages unless explicitly handled.

---

# Alternative Real-World Solutions

Large CI/CD systems often use:

* Artifact repositories
* Shared workspaces
* Persistent volumes
* Jenkins stash/unstash
* S3 artifact storage

instead of relying only on reused workspaces.

# Important Missing Production Flag

The lecture mentions old files should be removed.

True production synchronization commonly uses:

```bash id="jlwm01"
aws s3 sync build s3://bucket --delete
```

Why?

If local build removes old assets:

```text id="jlwm85"
Old S3 files may remain forever
```

Without `--delete`, stale frontend assets can cause:

* Broken references
* Cache inconsistencies
* Old JS bundles remaining accessible

---

# Why Frontend Builds Often Need Cleanup

Modern frontend frameworks generate hashed assets:

Example:

```text id="jlwm52"
main.a1b2c3.js
main.x9y8z7.js
```

After new deployments:

* Old bundles should usually be removed
* Otherwise bucket accumulates stale assets
