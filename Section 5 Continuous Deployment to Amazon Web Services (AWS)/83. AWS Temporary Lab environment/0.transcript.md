This lecture is explaining how the course-provided AWS lab environment works and how it differs from using your own personal Amazon Web Services account.

## Purpose of the Lab Environment

The labs exist so students can:

* practice AWS hands-on,
* deploy applications,
* use cloud services,
* and follow the CI/CD exercises

without:

* creating a personal AWS account,
* adding payment methods,
* or risking cloud charges.

## How to Know if You Have Lab Access

You have lab access if:

* the lecture interface contains:

  * a **Video** button
  * and a **Practice** button

When clicking **Practice**:

* the AWS lab environment should open successfully,
* instead of showing an access error.

If you do not have access:

* you can skip this lecture,
* because the rest of the section can still be followed using your own AWS account.

## How the Lab Works

When clicking:

* **Open Workspace**

the platform automatically:

* provisions a temporary AWS environment,
* authenticates you automatically,
* and opens the AWS Console.

This means:

* no IAM user creation,
* no manual login,
* no MFA setup,
* and no billing configuration.

## Temporary Environment

The important limitation:

* the environment expires automatically,
* usually after about 60 minutes.

This is common in educational sandbox environments because:

* cloud resources cost money,
* and temporary expiration prevents abuse and excessive spending.

The instructor also notes:

* access may remain slightly longer,
* but should not be relied upon.

Practical implication:

* start a fresh workspace before long hands-on exercises.

## Why the AWS Console Looks Different

The interface may differ because:

* the lab account is centrally managed,
* permissions are restricted,
* some services/features may be hidden,
* and AWS UI changes over time anyway.

But:

* the underlying cloud concepts remain identical.

## Most Important Part: Temporary AWS Credentials

Later, the course uses Jenkins to deploy to AWS automatically.

Normally, in a personal AWS account:

* you would create IAM users,
* generate permanent access keys,
* and use those credentials in Jenkins.

But lab users cannot create IAM users.

So the platform provides temporary credentials instead.

## The Three Credentials

The lab provides:

1. AWS Access Key ID
2. AWS Secret Access Key
3. AWS Session Token

All three are required.

This is critical.

With long-term IAM credentials, usually only:

* Access Key ID
* Secret Access Key

are needed.

But temporary credentials generated through:

* AWS STS (Security Token Service)

also require:

* Session Token.

## AKIA vs ASIA Prefix

The lecture explains a useful AWS detail:

### Long-term IAM credentials

typically begin with:

```text
AKIA...
```

### Temporary STS credentials

typically begin with:

```text
ASIA...
```

This helps identify whether credentials are:

* permanent,
* or temporary session-based credentials.

## Why Session Token Is Required

Temporary credentials work differently internally.

AWS validates:

* the access key,
* the secret key,
* and the temporary session token together.

If the session token is missing:

* authentication fails.

This becomes important later when configuring:

* AWS CLI,
* Jenkins credentials,
* deployment scripts,
* or SDK authentication.

## Real DevOps Relevance

This is actually very close to real-world cloud security practices.

Modern cloud environments increasingly prefer:

* temporary credentials,
* assumed roles,
* federated access,
* short-lived tokens,
* and identity-based sessions

instead of long-lived static IAM keys.

This reduces risk if credentials are leaked.
