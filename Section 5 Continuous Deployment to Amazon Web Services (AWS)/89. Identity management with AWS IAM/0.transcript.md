## Why Root AWS Credentials Should NOT Be Used in Jenkins

When using AWS Command Line Interface inside Jenkins, you should NOT use:

* AWS account email
* AWS root password

Those credentials belong to the root AWS account and provide extremely broad permissions. 

Using them in CI/CD automation is a major security risk.

# IAM Service

AWS Identity and Access Management (IAM) is the AWS service responsible for:

* Users
* Roles
* Permissions
* Policies
* Access control

IAM answers two questions:

```text id="tq6w9x"
Who are you?
```

and

```text id="bxanwb"
What are you allowed to do?
```

---

# Principle of Least Privilege

Very important DevOps/security principle:

```text id="jktw6k"
Give only the minimum permissions required.
```

Example:

If Jenkins only needs to upload files to S3:

* It should NOT:

  * Manage EC2
  * Delete databases
  * Access billing
  * Create IAM users

Only S3 permissions should be granted. 

---

# Creating a Dedicated Jenkins IAM User

Inside IAM:

1. Open:

   ```text
   Users
   ```

2. Click:

   ```text
   Create User
   ```

3. Example username:

   ```text
   Jenkins
   ```

4. Important:

   ```text
   Do NOT enable AWS Management Console access
   ```

Reason:

This user is for programmatic/API access only.

Not for browser login. 

---

# IAM Policies

Permissions in AWS are controlled using policies.

A policy defines:

* Allowed actions
* Denied actions
* Allowed resources

Policies can be attached to:

* Users
* Groups
* Roles

---

# Policy Used in the Course

Policy attached:

```text id="dpfjlwm"
AmazonS3FullAccess
```

This allows the Jenkins user to fully interact with:

Amazon S3

Examples:

* Upload objects
* Delete objects
* List buckets
* Read objects



---

# Important Security Clarification

Even though:

```text id="f2gbb2"
AmazonS3FullAccess
```

is better than root access, it still violates strict least privilege principles somewhat.

Reason:

It grants access to:

```text id="hdtam7"
All S3 buckets
```

not only a specific bucket.

More secure production approach:

```text id="mjlwm7"
Allow only:
- Specific bucket
- Specific actions
```

Example:

* Only upload to:

  ```text
  my-static-site-bucket
  ```
* No deletion
* No access to other buckets

The course simplifies this for learning purposes.


# AWS Access Key Components

Two values are generated.

---

## Access Key ID

Example:

```text id="cjlwmc"
AKIAXXXXXXXXXXXXX
```

Acts similarly to:

```text id="ls9qjs"
Username / identifier
```

---

## Secret Access Key

Example:

```text id="n0yaxr"
wJalrXUtnFEMI/K7MDENG/bPxRfiCY
```

Acts similarly to:

```text id="jlwmga"
Password
```

This value is sensitive and must be protected.


# Jenkins Secret Management

```text id="0lrq5w"
Never store credentials directly in code
```

Bad example:

```groovy id="s4a4u7"

    AWS_SECRET_ACCESS_KEY = 'my-secret'
```

# Correct Jenkins Approach

Use Jenkins Credentials Store.

Architecture:

```text id="wjjlwm"
Jenkins Credentials Store
        ↓
Inject Secrets Into Pipeline
        ↓
AWS CLI Uses Credentials
```

Benefits:

* Encrypted storage
* Access control
* Secret masking in logs
* Centralized management

# Important Operational Best Practices

The lecture mentions several critical real-world practices.

---

## 1. Rotate/Delete Unused Keys

If a key is no longer needed:

* Disable it
* Delete it

Reason:

Old unused credentials are major attack vectors.

---

## 2. Never Expose Secrets

Never:

* Paste secrets into Slack
* Commit secrets to GitHub
* Hardcode secrets
* Print secrets in logs

---

## 3. Minimize Permissions

Instead of:

```text id="x9az1x"
Full access everywhere
```

prefer:

```text id="10jcl6"
Minimal required actions
```

# Production-Grade AWS Authentication

The course uses IAM users + access keys because they are easier to understand initially.

However, in modern enterprise DevOps, preferred approaches are:

* IAM Roles
* EC2 Instance Profiles
* EKS IAM Roles for Service Accounts
* OIDC federation
* Temporary STS credentials

Reason:

```text id="jlwm9y"
Long-lived static credentials are risky
```

---

# Important DevOps Security Lesson

This lecture introduces one of the most important cloud engineering principles:

```text id="3jlwm8"
Authentication and authorization must be isolated, minimal, and auditable.
```

Most real cloud security incidents happen because of:

* Overprivileged accounts
* Leaked credentials
* Hardcoded secrets
* Poor IAM design

Not because AWS itself was insecure.
