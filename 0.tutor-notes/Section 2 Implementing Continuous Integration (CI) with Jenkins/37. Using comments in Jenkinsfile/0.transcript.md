### Using Comments in Jenkinsfile (Practical Dev Workflow Optimization)

---

## 1. Why This Matters

Problem:

```text
Every pipeline run executes ALL stages → slow feedback (~1 min+)
```

Reality:

* While developing pipelines, you usually work on **one stage at a time**
* Running everything is unnecessary

Solution:

* Use **comments to selectively disable parts of the pipeline**

---

## 2. Types of Comments in Jenkinsfile (Groovy)

### Single-line comment

```groovy
// This is a comment
```

Used for:

* Notes
* Temporary explanations

---

### Multi-line (block) comment

```groovy
/*
Line 1
Line 2
*/
```

Used for:

* Disabling entire sections (important use case)

---

## 3. Disabling a Stage (Most Useful Trick)

### Example: Disable Build Stage

```groovy
/*
stage('Build') {
    agent {
        docker {
            image 'node:18-alpine'
            reuseNode true
        }
    }
    steps {
        sh '''
        npm ci
        npm run build
        '''
    }
}
*/
```

### Result:

* Build stage is **completely skipped**
* Pipeline runs faster

---

## 4. Why This Still Works

Even without Build stage:

* `build/` directory still exists (from previous runs)
* Workspace is **not cleaned**
* `npm test` does not strictly require build

So:

```text
Test stage continues to work
```

---

## 5. Disabling Individual Commands (Shell Level)

Inside `sh` block:

```groovy
sh '''
# test -f build/index.html
npm test
'''
```

Key point:

* `#` is **shell comment**, not Groovy
* Only affects commands inside `sh`

---

## 6. What Actually Happens in Execution

With Build stage commented:

Pipeline becomes:

```text
Test → Post
```

Logs will show:

* No Build stage
* Only Test stage execution
* Faster runtime

---

## 7. Critical Rule (Avoid Breaking Pipeline)

❌ Bad practice:

* Commenting partial syntax blocks

Example (wrong):

```groovy
stage('Build') {
    /*
    agent {
```

→ This breaks syntax → pipeline fails

---

✅ Correct approach:

* Comment **entire blocks only**

---

## 8. When to Use This Technique

Use comments when:

* Debugging a specific stage
* Developing new stage logic
* Avoiding long build times
* Isolating failures

---

## 9. When NOT to Use It

Do NOT rely on comments for:

* Permanent pipeline behavior
* Production pipelines

Better alternatives:

* `when` conditions
* Parameters
* Separate pipelines

---

## 10. Better Alternative (Advanced)

Instead of comments:

```groovy
when {
    expression { return false }
}
```

But:

* Comments are faster during learning/debugging
* No logic needed

---

## 11. Key Insight

You are turning this:

```text
Full CI Pipeline → Slow feedback loop
```

Into:

```text
Selective execution → Fast iteration
```

---

## 12. Mental Model

```text
Comments = Temporary pipeline switch
```

* Enable/disable parts instantly
* No deletion
* No rewrite

---

## 13. Real DevOps Practice

Senior engineers:

* Use comments during development
* Remove them later
* Replace with controlled logic

---

## 14. Final Takeaway

* Use `//` and `/* */` → control pipeline structure
* Use `#` → control shell commands
* Always keep syntax valid
* Prefer full block commenting
