# Jenkins Architecture — What Actually Happens Behind the Scenes

At a high level, Jenkins works using a **controller-agent architecture**.

When you run a Jenkins pipeline, the controller coordinates the work, while agents perform the actual execution.

---

# Core Components

## 1. Jenkins Controller

The controller is the central management server.

Its responsibilities include:

* Managing pipeline execution
* Scheduling jobs
* Storing pipeline configuration
* Managing plugins
* Managing credentials
* Assigning work to agents
* Collecting logs and results
* Providing the web UI
* Monitoring agent availability

The controller is effectively the orchestration layer.

It decides:

* What should run
* When it should run
* Where it should run

But ideally:

> The controller should not perform heavy build work itself.

---

## 2. Jenkins Agent (Node)

An agent is the machine that performs the actual execution work.

An agent:

* Receives instructions from the controller
* Downloads source code
* Executes shell commands
* Runs builds/tests/deployments
* Returns logs and results back to the controller

Agents can be:

* Physical servers
* Virtual machines
* Docker containers
* Kubernetes pods
* Cloud instances

# What Happens When You Click “Build”

## Step-by-Step Flow

---

## Step 1 — Job Trigger

A pipeline starts because of something like:

* Manual build
* Git webhook
* Scheduled trigger
* Pull request
* API request

The request reaches the Jenkins controller.

---

## Step 2 — Pipeline Parsing

The controller:

* Reads the `Jenkinsfile`
* Parses stages and steps
* Determines execution order
* Evaluates conditions

Example:

```groovy id="4fr7eu"
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                sh 'mvn package'
            }
        }
    }
}
```

Here the controller understands:

* A stage named `Build`
* A shell command must run
* An agent is required

---

## Step 3 — Agent Allocation

The controller searches for a suitable agent.

Selection may depend on:

* Labels
* Available resources
* Installed tools
* Executor availability

Example:

```groovy id="prrx2k"
agent {
    label 'docker'
}
```

This means:

> Run this pipeline on an agent labeled `docker`.

---

## Step 4 — Workspace Creation

The selected agent creates a workspace directory.

Example:

```text
/var/lib/jenkins/workspace/my-app/
```

This workspace contains:

* Source code
* Build artifacts
* Temporary files

---

## Step 5 — Source Code Checkout

The agent pulls the repository from Git.

Example:

```groovy id="c6bqz9"
checkout scm
```

or internally:

```bash
git clone https://github.com/example/app.git
```

---

## Step 6 — Stage Execution

The agent executes commands defined in the pipeline.

Examples:

```bash
mvn package
npm install
docker build
kubectl apply
terraform apply
```

The actual CPU, RAM, and disk usage happen on the agent machine.

Not on the controller.

---

## Step 7 — Streaming Logs Back

During execution:

* Console output is streamed back to the controller
* The controller updates the UI in real time
* Build status is tracked

Example statuses:

* Running
* Success
* Failed
* Aborted

---

## Step 8 — Result Storage

The controller stores:

* Build history
* Logs
* Test reports
* Artifacts metadata
* Pipeline state

---

# Why Controller and Agent Should Be Separate

In small demos or local installations:

* One machine acts as both controller and agent

This is common for learning.

But in production this becomes problematic.

---

# Problems with Running Builds on the Controller

Heavy workloads may:

* Exhaust CPU
* Consume RAM
* Fill disk space
* Crash Jenkins
* Slow UI responsiveness
* Affect all pipelines

Example:

Running:

```bash
docker build
mvn package
npm install
```

directly on the controller repeatedly can overload it.

---

# Production Best Practice

Modern Jenkins setups usually have:

* 1 controller
* Multiple distributed agents

Example architecture:

```text
                Jenkins Controller
                       |
        --------------------------------
        |              |              |
     Agent 1        Agent 2        Agent 3
   (Docker)        (Maven)        (Kubernetes)
```

This provides:

* Load distribution
* Scalability
* Isolation
* Fault tolerance
* Parallel execution

---

# Executors

Each agent contains one or more executors.

An executor is essentially a slot that can run one job at a time.

Example:

* Agent with 4 executors
* Can run 4 builds simultaneously

---

# Modern Jenkins Agent Patterns

Today agents are often ephemeral.

Instead of permanent servers:

* Jenkins dynamically creates containers or Kubernetes pods
* Executes the pipeline
* Destroys the environment afterward

This improves:

* Isolation
* Resource efficiency
* Reproducibility

Common integrations:

* Docker
* Kubernetes
* Amazon Web Services EC2
* Auto-scaling cloud agents

---

# Important Concept

A Jenkins pipeline itself does not “run inside Jenkins”.

Instead:

* Jenkins orchestrates
* Agents execute

This distinction becomes extremely important in real DevOps environments involving:

* Distributed systems
* Containers
* Kubernetes
* Multi-cloud CI/CD
* Large-scale parallel builds
