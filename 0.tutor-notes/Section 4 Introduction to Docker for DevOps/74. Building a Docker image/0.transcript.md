This lecture explains how and why to build custom Docker images for Jenkins pipelines. The key goal is improving pipeline efficiency and consistency. 

# The Problem With the Current Pipeline

Earlier pipeline stages were doing something like:

```bash id="nzh3wo"
npm install netlify-cli
npm install node-jq
```

during every pipeline run.

This creates several problems.

---

# Problem 1: Repeated Downloads

Every execution:

* downloads packages again
* installs dependencies again
* consumes network bandwidth again

This increases pipeline execution time.

---

# Problem 2: Non-Reproducible Builds

If package versions change upstream:

```bash id="j1z1o8"
npm install
```

may install different versions later.

This can create inconsistent builds.

---

# Problem 3: Runtime Setup Instead of Prebuilt Environment

The pipeline is spending time:

* preparing environment
* installing tools

instead of:

* building
* testing
* deploying

This is inefficient CI/CD design.

---

# Better Approach

Instead of installing tools every run:

> Build a custom Docker image once with everything preinstalled.

Then Jenkins simply uses that image.

This is a foundational DevOps optimization pattern.

---

# What Is a Dockerfile?

A `Dockerfile` is:

> a text file containing instructions for building a Docker image

Docker reads instructions sequentially.

Example:

```dockerfile id="v8y57m"
FROM node:18-alpine

RUN npm install -g netlify-cli node-jq
```

---

# Important Naming Detail

The file name is:

```text id="4ibjmt"
Dockerfile
```

Case-sensitive convention.

Usually placed in:

```text id="i7uhjc"
project-root/
```

because Docker build context matters.

---

# What Is Build Context?

This command:

```bash id="2j5txk"
docker build .
```

uses:

```text id="n6ysmx"
.
```

(current directory)

as the build context.

Docker can only access files inside that context.

This is why the instructor moved the `Dockerfile` to the project root.

Very important Docker concept.

---

# `FROM` Instruction

The lecture introduces the most important Dockerfile instruction:

```dockerfile id="49wj23"
FROM node:18-alpine
```

Meaning:

> Start building from an existing image.

Docker images are layered.

You rarely build completely from scratch.

---

# Layer Concept

Docker images are composed of layers.

Example:

```text id="7l0gfe"
Alpine Linux
    ↓
Node.js
    ↓
Your custom tools
```

Each instruction adds another layer.

Benefits:

* caching
* reuse
* faster builds
* smaller downloads

---

# `RUN` Instruction

Example:

```dockerfile id="4e0mii"
RUN npm install -g netlify-cli node-jq
```

Meaning:

> Execute command during image build.

Important distinction:

| Phase             | Meaning                                |
| ----------------- | -------------------------------------- |
| Build time        | `RUN` executes                         |
| Container runtime | image already contains installed tools |

This is why the tools become permanently available in the image.

---

# Why `-g` Is Used

Without:

```bash id="oz0r1t"
-g
```

npm installs packages locally into project directories.

With:

```bash id="mnkcbz"
npm install -g
```

packages become globally available.

This allows commands like:

```bash id="e8dt9e"
netlify
jq
```

to work anywhere inside the container.

---

# Important Docker Principle

The instructor says:

> “we never start from scratch”

This is mostly true operationally.

Although Docker supports:

```dockerfile id="ct5qfy"
FROM scratch
```

that is advanced usage for ultra-minimal containers.

Most CI/CD images extend existing base images.

---

# Docker Build Command Explained

Command:

```bash id="s86wph"
docker build -t my-playwright .
```

Breakdown:

| Part            | Meaning                         |
| --------------- | ------------------------------- |
| `docker build`  | build image                     |
| `-t`            | assign tag/name                 |
| `my-playwright` | image name                      |
| `.`             | current directory build context |

---

# What Docker Actually Does During Build

Docker processes the Dockerfile step-by-step.

---

## Step 1 — Pull Base Image

```dockerfile id="jijfdv"
FROM node:18-alpine
```

If image not available locally:

Docker downloads it.

---

## Step 2 — Create Intermediate Container

Docker temporarily creates container from base image.

---

## Step 3 — Execute RUN Command

```dockerfile id="8t8xoe"
RUN npm install -g ...
```

Runs inside temporary container.

Changes become part of new image layer.

---

## Step 4 — Commit New Layer

Docker saves filesystem changes.

---

## Step 5 — Final Image Created

Tagged as:

```text id="4yx4st"
my-playwright
```

---

# Why Build Was Fast

The instructor says build was very fast.

Likely reasons:

* base image already cached
* npm packages small
* Docker layer caching

---

# Extremely Important Concept: Docker Cache

Docker caches layers.

If this line remains unchanged:

```dockerfile id="saxn7r"
RUN npm install -g netlify-cli node-jq
```

future builds may reuse cached layer instead of reinstalling.

Huge CI/CD optimization.

---

# Major Real-World Advantage

Now Jenkins pipelines no longer need:

```bash id="k4g5g4"
npm install
```

during execution.

Instead:

```text id="8d6w7j"
Container already contains tools
```

Benefits:

* faster pipelines
* predictable environments
* reduced network dependency
* reduced external failures

# Important Missing Real-World Step

The lecture simplifies things slightly.

In production systems, images are usually:

1. built once
2. pushed to registry
3. reused many times

Example:

```bash id="sx2mha"
docker push my-registry/my-playwright:v1
```

Then Jenkins agents pull prebuilt image.

Otherwise every pipeline rebuilds image repeatedly.

---

# Real CI/CD Pattern

Typical enterprise flow:

```text id="m5w8n7"
Build custom image
    ↓
Push to registry
    ↓
Reuse image in pipelines
```
