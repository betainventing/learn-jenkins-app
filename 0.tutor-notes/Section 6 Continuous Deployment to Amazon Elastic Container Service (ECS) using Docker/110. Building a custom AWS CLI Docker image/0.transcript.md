# Optimizing Jenkins Pipeline Performance

The pipeline was successfully building Docker images, but there was a major inefficiency:

```text id="’wini143"
Docker And jq Were Installed During Every Pipeline Run
```

This added unnecessary overhead.



---

# Performance Observation

Actual Docker image build time:

```text id="’wini144"
~2 seconds
```

Pipeline stage duration after installing software dynamically:

```text id="’wini145"
~53 seconds
```

Most time was wasted on:

* Installing Docker
* Installing jq

during every execution.

---

# Important CI/CD Optimization Principle

Good pipelines avoid:

* Repeated environment setup

Instead:

* Build reusable execution environments once

This is a major DevOps optimization strategy.

---

# Solution — Custom CI Images

The lecture introduces:

* Prebuilt custom Docker images for CI/CD tooling

Instead of:

```text id="’wini146"
Start Generic Container
↓
Install Software Every Run
```

the pipeline becomes:

```text id="’wini147"
Start Preconfigured Container
↓
Everything Already Installed
```

---

# Existing CI Directory Reuse

The repository already had:

```text id="’wini148"
ci/
```

directory.

This now becomes:

* Dedicated CI infrastructure folder

---

# Dockerfile Refactoring

Original Playwright Dockerfile renamed to:

```text id="’wini149"
ci/Dockerfile-playwright
```

This clarifies:

* Purpose of the image

---

# New AWS CLI Dockerfile

A second Dockerfile created:

```text id="’wini150"
ci/Dockerfile-aws-cli
```

Purpose:

* Build reusable AWS deployment container



---

# Base Image

The Dockerfile starts with:

```dockerfile id="’wini151"
FROM amazon/aws-cli
```

This provides:

* AWS CLI preinstalled

---

# RUN Instruction

Next instruction:

```dockerfile id="’wini152"
RUN ...
```

`RUN` executes commands during image build time.

Important distinction:

| Instruction | Timing            |
| ----------- | ----------------- |
| `RUN`       | Image build time  |
| `CMD`       | Container runtime |

---

# Installing Docker + jq Once

The image permanently installs:

* Docker client
* jq

during image creation.

Meaning:

* Future containers already contain required tooling.

---

# Why This Is Faster

Old approach:

```text id="’wini153"
Every Pipeline Run
↓
Install Docker
↓
Install jq
```

New approach:

```text id="’wini154"
Install Once During Image Build
↓
Reuse Forever
```

This dramatically reduces runtime overhead.

---

A dedicated Jenkins job builds:

* CI infrastructure images


Very common in mature CI/CD environments.

The main Jenkins pipeline now switches from:

---

# Resulting Performance Improvement

Earlier:

```text id="’wini157"
~53 seconds
```

Optimized:


Huge reduction in runtime overhead.

# Why Some Overhead Still Exists

The pipeline still:

* Starts containers
* Mounts Docker socket
* Initializes environment

So:

* 0-second startup is unrealistic

But 5 seconds is excellent improvement.

---

# Experimenting With Root Permissions

The lecture then questions whether:

```text id="’wini159"
-u root
```

is still necessary.

This is good engineering practice.

---

# Why Testing Permission Requirements Matters

Pipelines often accumulate:

* Unnecessary privileges
* Legacy configuration
* Old workarounds

Good engineers periodically validate:

* Whether elevated permissions are truly required.

---

# Result — Docker Socket Permission Failure

Removing root caused:

```text id="’wini160"
Permission denied
```

on:

```text id="’wini161"
/var/run/docker.sock
```



---

# Why This Happens

Docker socket access is highly privileged.

Only:

* Root
  OR
* Docker group members

typically can access it.

The container user lacked permission.

---

# Important Security Implication

Access to:

```text id="’wini162"
/var/run/docker.sock
```

effectively grants:

* Host-level Docker control

This is why access is restricted.

---

# Final Permission Decision

## Build Docker Image Stage

Needed:

```text id="’wini163"
-u root
```

because:

* Docker socket access required

---

# Deploy To AWS Stage

Root removed successfully because:

* Only AWS CLI commands executed
* No privileged Docker operations needed

---

# Important DevOps Principle Demonstrated

The lecture demonstrates:

```text id="’wini164"
Use Minimum Necessary Privileges
```

This is:

* Principle of least privilege

A foundational security principle.

# Real-World Relevance

This optimization pattern is extremely common in professional CI/CD systems.

Large organizations typically maintain:

* Internal CI base images
* Standardized tooling images
* Preconfigured deployment environments

because repeatedly installing dependencies during every pipeline run:

* Scales poorly
* Wastes compute resources
* Slows feedback loops drastically.
