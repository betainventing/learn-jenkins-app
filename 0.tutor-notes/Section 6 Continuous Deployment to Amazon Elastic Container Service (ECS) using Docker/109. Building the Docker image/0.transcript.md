# Building the Application Docker Image in Jenkins

The project now has:

* A real application `Dockerfile`

The next step is:

* Build the Docker image automatically inside the Jenkins pipeline.



---

# Pipeline Order Change

Earlier flow:

* Build application
* Deploy to AWS

Now a new required step exists:

```text id="’wini127"
Build Application
   ↓
Build Docker Image
   ↓
Deploy To AWS
```

This order matters because:

* Docker image depends on application build output.

---

# Why Build Must Happen First

The Dockerfile copies:

```text id="’wini128"
build/
```

directory into the image.

That directory only exists AFTER:

* Frontend build process completes

Without the build step:

* Docker build fails

because files are missing.

---

# Reusing Existing Jenkins Logic

The project already had Docker build logic inside:

* `Jenkinsfile.nightly`

Originally used for:

* Playwright CI image

The lecture reuses this logic for:

* Application image builds

---

# Docker Build Command

Core command:

```bash id="’wini129"
docker build -t my-jenkins-app .
```



---

# Understanding the Command

| Part             | Meaning        |
| ---------------- | -------------- |
| `docker build`   | Build image    |
| `-t`             | Tag image      |
| `my-jenkins-app` | Image name/tag |
| `.`              | Build context  |

---

# Extremely Important — Build Context

The trailing dot:

```text id="’wini130"
.
```

is critical.

It defines:

* Build context directory

Meaning:

* Which files Docker can access during build

---

# Why Build Context Matters

The Dockerfile contains:

```dockerfile id="’wini131"
COPY build /usr/share/nginx/html
```

Docker can only copy files that exist INSIDE:

* Build context

If wrong context is used:

* COPY fails

---

# Docker Build Internals

The build process shown in logs had two major stages:

1. Pull base image
2. Copy application files

---

# Step 1 — Pull Base Image

Docker downloads:

```text id="’wini132"
nginx:<version>
```

from registry.

This becomes:

* Base filesystem layer

---

# Step 2 — Copy Application Files

Docker copies:

* Built website files

into:

* Nginx web root

inside the image.

---

# Resulting Image

The final image now contains:

| Component           | Purpose     |
| ------------------- | ----------- |
| Nginx               | Web server  |
| Website build files | Application |
| Linux filesystem    | Runtime     |

---

* AWS CLI
  AND

The existing AWS CLI container image had:

* AWS CLI installed

but NOT:

* Docker client

Error:

```text id="’wini133"

```

* Docker CLI binary absent inside container

# Installing Docker Client

* Install Docker inside the AWS CLI container

Using:

```bash id="’wini134"
amazon-linux-extras install docker
```

---

# Amazon Linux Extras

`amazon-linux-extras` is specific to:

* Amazon Linux

Used for:

* Installing additional software packages

Common for:

* Docker
* Runtime packages
* Updated software streams

---

# Next Failure — Docker Daemon Missing

After installing Docker CLI:

New error:

```text id="’wini135"
Cannot connect to the Docker daemon
```

This is a MUCH deeper Docker concept.

---

# Critical Docker Architecture Concept

Docker consists of TWO major components:

| Component     | Role                                 |
| ------------- | ------------------------------------ |
| Docker Client | Receives commands                    |
| Docker Daemon | Performs actual container/image work |

---

# Docker Client

Examples:

```bash id="’wini136"
docker build
docker run
docker ps
```

The client itself:

* Does not build containers directly

It sends requests.

---

# Docker Daemon

The daemon:

* Builds images
* Starts containers
* Manages networking
* Handles storage
* Runs background container engine

This is the heavy worker.

---

# Why the Error Happened

Inside the AWS CLI container:

* Docker client existed
* Docker daemon did NOT

So commands had nowhere to execute.

---

# Jenkins Host Already Had Docker

The underlying Jenkins environment already had:

* Running Docker daemon

The container simply needed access to it.

---

# Docker Socket Concept

Docker components communicate using:

```text id="’wini137"
/var/run/docker.sock
```

This is:

* Unix socket file

Used for:

* IPC (inter-process communication)

between:

* Docker client
* Docker daemon



---

# Socket Mapping Solution

Docker argument added:

```text id="’wini138"
-v /var/run/docker.sock:/var/run/docker.sock
```

---

# What This Mapping Does

Conceptually:

```text id="’wini139"
Container Docker Client
↓
Uses Host Docker Socket
↓
Communicates With Host Docker Daemon
```

This allows:

* Containerized tooling
  → to control
* Host Docker engine

---

# Important Docker-in-Docker Related Concept

This pattern is often called:

```text id="’wini140"
Docker Outside of Docker
```

or loosely associated with:

* Docker socket mounting

Very common in CI/CD systems.

---

# Why This Is Powerful

The AWS CLI container now gains ability to:

* Build images
* Push images
* Manage Docker

without running its own daemon.

---

# Final Successful Build

After:

1. Installing Docker client
2. Mounting Docker socket

the pipeline successfully:

* Built the application image

---

# Final Jenkins Runtime Architecture

The deployment stage now works like:

```text id="’wini141"
AWS CLI Container
   ↓
Docker Client Installed
   ↓
Mounted Docker Socket
   ↓
Host Docker Daemon
   ↓
Image Build Execution
```

---

# Important Security Implication

Mounting Docker socket gives the container:

* Powerful access to host Docker engine

In production this must be treated carefully because:

* It effectively grants elevated host control.
