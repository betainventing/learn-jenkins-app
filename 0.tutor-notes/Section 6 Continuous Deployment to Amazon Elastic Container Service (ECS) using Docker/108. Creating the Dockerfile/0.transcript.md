# Creating a Docker Image for the Website

The lecture now transitions from:

* Using public container images

to:

* Building your own application image.

This is one of the most important steps in containerized deployments.

---

# What Builds a Docker Image?

A Docker image is created from:

* A `Dockerfile`

Conceptually:

```text id="’wini111"
Dockerfile = Build Instructions For Container Image
```

It acts similarly to:

* A recipe
* A blueprint
* A build script

---

# Existing Dockerfile Problem

The project already had a `Dockerfile`.

But that file was being used for:

* Custom Playwright CI image

not:

* Application deployment image

This introduces an important repository organization issue.

---

# Why Dockerfile Placement Matters

By convention:

```text id="’wini112"
Dockerfile at Repository Root
```

usually means:

* Main application image

If multiple unrelated Dockerfiles exist:

* Confusion increases
* Builds may accidentally use wrong file

---

# CI Dockerfile Refactoring

Solution:

* Move Playwright Dockerfile into:

```text id="’wini113"
ci/Dockerfile
```

This separates:

* CI infrastructure images
  from
* Application deployment images

---

# Why This Is Good Practice

The separation improves:

* Repository clarity
* Maintainability
* Predictability
* Build correctness

Very common in production repositories.

---

# Docker Build Context Problem

Earlier Jenkins build command assumed:

```text id="’wini114"
Dockerfile exists at repository root
```

After moving the file:

* Docker build would fail

unless the file location is explicitly specified.

---

# The `-f` Flag

Docker build supports:

```bash id="’wini115"
docker build -f
```

Purpose:

* Specify alternate Dockerfile path

Example:

```bash id="’wini116"
docker build -f ci/Dockerfile
```

---

# Why This Matters

Without `-f`:

* Docker searches only for:

  * `./Dockerfile`

in current build directory.

---

# Important Docker Build Concept

Docker build has two separate concepts:

| Concept         | Meaning                      |
| --------------- | ---------------------------- |
| Dockerfile path | Build instructions           |
| Build context   | Files available during build |

This distinction becomes important later in advanced Docker usage.

---

# Creating the New Application Dockerfile

Now the repository root receives:

* New `Dockerfile`

This one becomes:

* The real application deployment image.

---

# FROM Instruction

First instruction:

```dockerfile id="’wini117"
FROM nginx:<version>
```

NGINX becomes the base image.

---

# What `FROM` Means

`FROM` defines:

* Base image layer

Conceptually:

```text id="’wini118"
Start Building From Existing Image
```

Most Docker images build on top of:

* Existing images

rather than:

* Starting from scratch

---

# Why Nginx Is a Good Base Image

The application is:

* Static website

Nginx already provides:

* Web server
* HTTP handling
* Static file serving

So instead of creating a web server manually:

* Reuse the official Nginx image

---

# Version Pinning

The lecture specifies:

* Explicit image version

Good practice because:

* Builds remain reproducible
* Prevents unexpected upstream changes

---

# COPY Instruction

Second instruction:

```dockerfile id="’wini119"
COPY build /usr/share/nginx/html
```

Purpose:

* Copy built website files into container

---

# What Gets Copied?

Source:

```text id="’wini120"
build/
```

contains:

* Generated frontend application files

Usually:

* HTML
* CSS
* JavaScript
* Assets

---

# Destination Directory

Destination:

```text id="’wini121"
/usr/share/nginx/html
```

This is the default static web directory used by Nginx.

---

# Important Nginx Behavior

Nginx automatically serves files from:

```text id="’wini122"
/usr/share/nginx/html
```

Meaning:

* No additional configuration required

Once files exist there:

* Nginx serves them immediately

---

# What the Final Image Contains

The built image now includes:

| Component           | Purpose              |
| ------------------- | -------------------- |
| Nginx               | Web server           |
| Website build files | Frontend application |
| Linux runtime       | Base OS layers       |

---

# Resulting Container Behavior

When the container starts:

```text id="’wini123"
Nginx Starts
↓
Serves Files From /usr/share/nginx/html
↓
Website Accessible Over HTTP
```

---

# Important Containerization Principle

The container now becomes:

* Self-contained deployment artifact

Meaning:

* Same image runs everywhere consistently

Examples:

* Developer laptop
* Jenkins pipeline
* ECS
* Kubernetes

---

# Why This Is Powerful

Earlier deployment model:

```text id="’wini124"
Upload Individual Files
```

Now:

```text id="’wini125"
Deploy Entire Runtime Environment
```

This greatly improves:

* Portability
* Reproducibility
* Deployment consistency

---

# Minimal Dockerfile Philosophy

The lecture intentionally keeps the Dockerfile simple.

Only two instructions:

1. `FROM`
2. `COPY`

This demonstrates:

* Containers do not need to be complicated
* Many deployments are extremely small/simple

| Concept              | Purpose                        |
| -------------------- | ------------------------------ |
