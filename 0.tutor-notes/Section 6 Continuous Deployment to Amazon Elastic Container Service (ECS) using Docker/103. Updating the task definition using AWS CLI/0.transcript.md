# Updating ECS Deployments — New Task Definition Revision

At this stage:

* ECS cluster exists
* ECS service exists
* Nginx container is running

The next problem introduced is:

```text id="jlwm21"
How do we deploy a newer container version?
```



---

# Important ECS Deployment Principle

You do NOT create:

* New cluster
* New service

for every deployment.

Instead:

1. Create new task definition revision
2. Update the ECS service to use the new revision

This is how rolling deployments work in ECS. 

---

# ECS Revision Model

Earlier task definition:

```text id="jlwm22"
Revision 1
→ nginx:1.26-alpine
```

New deployment:

```text id="jlwm23"
Revision 2
→ nginx:1.27-alpine
```

ECS versions task definitions automatically.

---

# Why Revisions Matter

Revisions provide:

* Deployment history
* Rollback capability
* Version tracking
* Safer deployments

This is critical in production systems.

---

# Two Ways to Update Task Definitions

AWS allows:

1. UI-based editing
2. JSON-based automation

The lecture intentionally shifts toward:

* Automation using Jenkins + AWS CLI

because manual UI operations do not scale well.


```text id="jlwm25"
Same Infrastructure
Different Container Image Version
```

Containers are immutable deployment artifacts.

# AWS CLI Introduction for ECS

The deployment automation uses the AWS Command Line Interface.

Specifically:

* ECS register task definition command

---

# ECS Registration Command

Core command:

```bash id="jlwm27"
aws ecs register-task-definition
```

Purpose:

* Register new task definition revision in ECS

---

# Using JSON Input

The important CLI flag:

```bash id="jlwm28"
--cli-input-json
```

This tells AWS CLI:

* Read task definition configuration from a JSON file

Example pattern:

```bash id="jlwm29"
aws ecs register-task-definition \
--cli-input-json file://aws/task-definition-prod.json
```



---

# Why `file://` Matters

AWS CLI expects:

* File URI format

Example:

```text id="jlwm30"
file://relative/path/file.json
```

Without it:

* AWS CLI treats value incorrectly

# AWS Credentials Reused

---

# First Pipeline Failure — Empty Environment Block

Jenkins error:

* Empty environment block invalid

This is purely:

* Jenkinsfile syntax issue

Not an AWS problem.

---

# Second Failure — Missing AWS Region

Error:

```text id="jlwm32"
You must specify a region
```

AWS services are regional.

CLI must know:

* Which AWS region to target

---

# Fixing Region Configuration

Environment variable added:

```bash id="jlwm33"
AWS_DEFAULT_REGION=us-east-1
```

This is standard AWS CLI configuration.

---

# Why Region Matters

Without region:

* AWS CLI cannot determine API endpoint

Different regions have different:

* ECS clusters
* Resources
* APIs

---

# Third Failure — Access Denied

New error:

```text id="jlwm34"
AccessDeniedException
```

This introduces another critical cloud concept:

* IAM permissions

---

# Root Cause

The Jenkins IAM user only had permissions for:

* Amazon S3

But now Jenkins is trying to access:

* Amazon Elastic Container Service

AWS denied the operation.

---

# IAM Principle Demonstrated

AWS authorization model:

```text id="jlwm35"
Authenticated User
+
Allowed Policy
=
Successful Action
```

Authentication alone is insufficient.

Authorization is also required.

---

# Fixing ECS Permissions

Solution:

* Attach ECS policy to Jenkins IAM user

Policy added:

```text id="jlwm36"
AmazonECS_FullAccess
```

This grants ECS administrative permissions.



---

# Important Security Note

`AmazonECS_FullAccess` is broader than necessary.

Production systems usually prefer:

* Least privilege policies

But full access simplifies learning and experimentation.

---

After fixing:

* Region
