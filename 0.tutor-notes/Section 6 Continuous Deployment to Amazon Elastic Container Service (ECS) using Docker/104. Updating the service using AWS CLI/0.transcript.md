# Updating the ECS Service — Deploying the New Container Version

The previous step successfully:

* Registered a new ECS task definition revision

But the running application was still using the older container version. 

---

# Important ECS Deployment Principle

Registering a task definition does NOT automatically redeploy containers.

At this stage:

```text id="jlwm41"
New Revision Exists
Running Service Still Uses Old Revision
```

To actually deploy the new version:

* The ECS service must be updated.

---

# ECS Update Flow

Deployment lifecycle now becomes:

```text id="jlwm42"
1. Register Task Definition Revision
2. Update ECS Service
3. ECS Replaces Old Tasks
4. New Containers Start Running
```



---

# AWS CLI Command for Service Update

The deployment uses another AWS Command Line Interface command:

```bash id="jlwm43"
aws ecs update-service
```

Purpose:

* Tell ECS service to use a newer task definition revision

---

# Required Parameters

The update command needs:

| Parameter           | Purpose                        |
| ------------------- | ------------------------------ |
| `--cluster`         | Which ECS cluster              |
| `--service`         | Which ECS service              |
| `--task-definition` | Which task definition revision |

---

# Why `--cluster` Is Important

AWS can contain:

* Multiple clusters

If cluster is omitted:

* ECS assumes the default cluster

That can be dangerous in real environments.

Explicit cluster specification improves:

* Predictability
* Safety
* Deployment clarity



---

# Cluster Name

Example:

```text id="jlwm44"
learn-jenkins-app-cluster-prod
```

---

# Service Name

Example:

```text id="jlwm45"
learn-jenkins-app-service-prod
```

---

# Task Definition Revision

Important syntax:

```text id="jlwm46"
task-definition-name:revision
```

Example:

```text id="jlwm47"
learn-jenkins-app-task-definition-prod:2
```

The `:2` specifies:

* Exact revision number

---

# Why Explicit Revisions Matter

Without explicit revision:

* Behavior may depend on defaults/latest state

Explicit revisions provide:

* Deterministic deployments
* Predictable rollback behavior
* Safer automation

---

# Full Update Command Structure

Conceptually:

```bash id="jlwm48"
aws ecs update-service \
  --cluster <cluster-name> \
  --service <service-name> \
  --task-definition <task-definition>:<revision>
```



---

# Jenkins Pipeline Automation

The Jenkins pipeline now performs BOTH operations:

```text id="jlwm49"
1. Register New Task Definition
2. Update ECS Service
```

This becomes a basic ECS deployment pipeline.

---

# What Actually Happens During Update

When ECS receives the update request:

1. Pull new container image
2. Start new task
3. Verify health
4. Gradually replace old task
5. Remove old container

This is controlled orchestration behavior.

---

# Important Observation — Temporary Multiple Tasks

During deployment ECS briefly shows:

```text id="jlwm50"
2/1 tasks running
```

This confuses many beginners initially.

---

# Why Two Tasks Exist Temporarily

Old task:

* Still serving traffic

New task:

* Starting and validating

This avoids downtime.

Conceptually:

```text id="jlwm51"
Old Container Stays Alive
Until
New Container Is Ready
```

This is a rolling deployment strategy.



---

# Old vs New Task

Old task:

```text id="jlwm52"
nginx:1.26
```

New task:

```text id="jlwm53"
nginx:1.27
```

ECS gradually transitions between them.

---

# Zero-Downtime Deployment Principle

The deployment demonstrates a core orchestration goal:

```text id="jlwm54"
Deploy New Version
Without Taking Application Offline
```

This is foundational in:

* ECS
* Kubernetes
* Modern CI/CD systems

---

# ECS Deployment Behavior

Eventually:

* Old task stops
* New task becomes primary running task

Desired state returns to:

```text id="jlwm55"
1/1 tasks running
```

---

# Important Networking Observation

Each new Fargate task may receive:

* Different public IP address

Meaning:

* Public endpoint changes after redeployment



---

# Why Dynamic IPs Are a Problem

Users cannot reliably access applications if:

* Public IP changes constantly

Production systems solve this using:

* Load balancers
* DNS
* Service discovery

---

# Typical Production Architecture

Production ECS commonly uses:

```text id="jlwm56"
Internet
   ↓
Load Balancer
   ↓
ECS Service
   ↓
Fargate Tasks
```

The load balancer provides:

* Stable endpoint
* Traffic distribution
* Health checks
