This section explains one of the most fundamental concepts in Linux, Jenkins, CI/CD, automation, and DevOps:

# Exit Codes

Jenkins does not magically understand whether a command succeeded or failed.

It relies on the operating system's process exit status.

---

# What Is an Exit Code?

Every Linux process returns a numeric status code after execution.

This value is called:

* exit code
* return code
* process status

---

# Standard Convention

| Exit Code | Meaning                      |
| --------- | ---------------------------- |
| 0         | Success                      |
| 1–255     | Failure or special condition |

---

# Important Rule

```text id="gk1s3l"
0 = success
non-zero = failure
```

This convention is used across:

* Linux
* Bash
* Jenkins
* Docker
* Kubernetes
* Git
* Terraform
* Ansible
* Maven
* npm
* CI/CD systems

---

# How Jenkins Detects Failure

When Jenkins executes:

```groovy id="lwl6m7"
sh 'some-command'
```

Jenkins waits for the command to finish.

Then it checks the exit code.

Conceptually:

```text id="snr7jg"
Command → returns exit code → Jenkins evaluates result
```

---

# Successful Command Example

```bash id="cjlwmj"
mkdir build
```

If successful:

```text id="xhbj4f"
exit code = 0
```

Jenkins interprets this as:

```text id="4dh1dq"
Everything is fine, continue pipeline
```

---

# Failed Command Example

```bash id="59n20e"
test -f build/computer.txt
```

If the file does not exist:

```text id="ax3jpd"
exit code = 1
```

Jenkins interprets this as:

```text id="f3vylg"
Failure detected, stop pipeline
```

---

# Why `test` Prints No Error Message

The instructor highlights something important:

The command did not print:

```text id="q6g6jo"
File missing
```

or:

```text id="6gclll"
Error occurred
```

because many Linux utilities are intentionally silent.

They communicate primarily through exit codes.

This is normal Unix philosophy.

---

# Jenkins Pipeline Failure Flow

The pipeline behavior is:

```text id="j8q1mu"
Command executes
    ↓
Non-zero exit code returned
    ↓
Jenkins marks stage failed
    ↓
Pipeline stops
    ↓
Remaining stages skipped
```

---

# Example from the Lecture


inside the build stage.

# What `exit 2` Means

`exit` is a shell builtin command.

Example:

```bash id="v7mqgh"
exit 2
```

means:

```text id="p74fyj"
Terminate current shell immediately with exit code 2
```

---

# Pipeline Result

Jenkins receives:

```text id="fzt6bg"
exit code 2
```

Since it is non-zero:

* build stage fails
* remaining stages are skipped

Jenkins outputs:

```text id="ccx7mt"
Stage "Test" skipped due to earlier failure
```

---

# Why Jenkins Stops the Pipeline

This behavior protects CI/CD systems.

If one critical step fails:

* subsequent stages may become invalid
* deployment may become dangerous
* artifacts may become corrupted

Example:

```text id="jnnxrp"
Build failed
↓
No point deploying broken application
```

So Jenkins aborts further execution.

# Reading Jenkins Logs

The instructor explains a critical debugging workflow:

When you see:

```text id="0a4w0f"
script returned exit code X
```

you should:

## Step 1

Find the last executed command.

Example:

```bash id="bx5y1n"
exit 2
```

---

## Step 2

Understand what that command does.

---

## Step 3

Determine why it returned non-zero status.

This is standard Jenkins debugging methodology.

---

# Important Linux Debugging Principle

The actual failure is usually:

```text id="82y15x"
BEFORE the exit code message
```

The exit code is only the symptom indicator.

The real problem is generally:

* invalid command
* missing file
* network issue
* permission issue
* failed test
* application crash
* dependency failure

# Important Shell Behavior

In shell scripting:

```bash id="mjlwmr"
exit 0
```

means success.

---

```bash id="w8r8lt"
exit 1
```

means generic failure.

---

```bash id="ep8m6j"
exit 2
```

usually indicates misuse or custom failure condition.

But technically any non-zero code signals failure to Jenkins.

---

# CI/CD Reliability Principle

Automated pipelines depend heavily on exit codes.

This allows automation systems to make decisions programmatically.

Without exit codes:

* Jenkins could not detect failures
* pipelines would continue incorrectly
* deployments would become unsafe
