This section moves from merely verifying that a file exists to validating the actual contents of the artifact.

This is a major CI/CD concept:

# Artifact Validation

A successful build is not enough.

You must verify that the produced artifact contains the expected data.

---

# Problem with `test -f`

Previously:

```bash id="1pxbba"
test -f build/computer.txt
```

only verified:

```text id="a8njlwm"
Does the file exist?
```

It did NOT verify:

* file contents
* correctness
* completeness
* integrity

A file can exist and still be completely wrong.

---

# Why `cat` Is Not Enough

The instructor mentions:

```bash id="rm1pf4"
cat build/computer.txt
```

`cat` only prints file contents.

It does not validate anything.

If the file is empty:

```bash id="8lnx8m"
cat empty.txt
```

there is no failure.

The command still exits successfully.

---

# Enter `grep`

The correct validation tool here is:

```bash id="i9n7s2"
grep
```

`grep` searches text for matching patterns.

---

# Basic `grep` Syntax

```bash id="jlwm1o"
grep "text" file.txt
```

Meaning:

```text id="mcsdx0"
Search for "text" inside file.txt
```

---

# Example from the Pipeline

```bash id="d65gya"
grep "mainboard" build/computer.txt
```

This checks whether the file contains:

```text id="npr0q8"
mainboard
```

---

# Important `grep` Behavior

If text is found:

* matching line is printed
* exit code = 0

If text is NOT found:

* nothing printed
* exit code = 1

This makes `grep` extremely useful for CI/CD testing.

---

# Jenkins + `grep`

Pipeline example:

```groovy id="bjlwm5"
stage('Test') {
    steps {
        sh '''
        test -f build/computer.txt
        grep "mainboard" build/computer.txt
        '''
    }
}
```

Pipeline behavior:

```text id="ix7a9d"
grep succeeds → pipeline continues
grep fails → pipeline stops
```

# Intentionally Breaking the Build

The instructor comments out:

```bash id="y6v8iu"
echo "mainboard" >> build/computer.txt
```

Now the build artifact no longer contains:

```text id="a1wbza"
mainboard
```

The test stage fails correctly.

This is exactly what automated testing should do.

# Incorrect Comment Syntax

The instructor first tries:

```bash id="0v8p79"
// comment
```

This causes:

```text id="4zjlwm"
Permission denied
```

because:

```text id="l0rhl0"
//something
```

is NOT a valid shell comment.

Shell interprets it as a command path.

---

# Correct Bash Comment Syntax

Correct syntax:

```bash id="g4p5vl"
# comment
```

This is standard shell scripting syntax.

# Important Jenkins Detail

The displayed artifacts are:

```text id="m1jjlwm"
Last successful artifacts
```

NOT artifacts from failed builds.

This is very important operationally.

To inspect failed build outputs:

you must open:

```text id="j5vjlwm"
Build Number → Workspace
```

not the general artifact view.

# Refactoring Safety

Good automated tests allow you to:

* optimize builds
* refactor pipelines
* remove unnecessary steps
* improve performance

without fear of silently breaking functionality.

---

# Why `touch` Was Unnecessary

Because:

```bash id="jlwm8i"
echo "mainboard" >> build/computer.txt
```

automatically creates the file if it does not already exist.

So:

```bash id="jlwmx4"
touch build/computer.txt
```

was redundant.

Without tests, removing it would feel risky.

With tests, the pipeline proves correctness automatically.
