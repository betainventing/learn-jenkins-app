This section introduces one of the most important concepts in Jenkins pipelines and automation in general: variables and environment variables.

The problem in the original pipeline was duplication.

The filename `computer.txt` was repeated many times throughout the pipeline:

* build stage
* test stage
* shell commands
* validation commands

If the filename changes, every occurrence must be updated manually.

That creates:

* maintenance problems
* configuration drift
* human error

So instead of hardcoding values repeatedly, we store them in variables.

---

# Jenkins Environment Variables

In Declarative Pipelines, global variables are commonly defined inside an `environment` block.

Example:

```groovy
pipeline {
    agent any

    environment {
        BUILD_FILE_NAME = "laptop.txt"
    }

    stages {

    }
}
```

---

# Naming Convention

Conventionally:

* uppercase letters
* underscore separators

Example:

```text
BUILD_FILE_NAME
DATABASE_URL
DOCKER_IMAGE
AWS_REGION
```

This resembles Linux environment variables.

---

# Variable Scope

This variable:

```groovy
BUILD_FILE_NAME = "laptop.txt"
```

is available:

* throughout the entire pipeline
* across all stages
* inside `sh` commands
* inside Jenkins pipeline steps

It behaves similarly to a system environment variable.

---

# Using Variables in Jenkins Pipeline Steps

Inside Jenkins Groovy syntax:

```groovy
echo "${BUILD_FILE_NAME}"
```

or

```groovy
echo "$BUILD_FILE_NAME"
```

works only with double quotes.

---

# Why Single Quotes Failed

This failed:

```groovy
echo '$BUILD_FILE_NAME'
```

because single quotes create a literal string.

Jenkins does not interpolate variables inside single quotes.

Result:

```text
$BUILD_FILE_NAME
```

instead of:

```text
laptop.txt
```

---

# Why Double Quotes Work

This works:

```groovy
echo "$BUILD_FILE_NAME"
```

because double quotes allow string interpolation.

Result:

```text
laptop.txt
```

---

# Why No Quotes Failed

This fails:

```groovy
echo $BUILD_FILE_NAME
```

with errors like:

```text
No such property
```

because:

* `echo` is a Groovy pipeline step
* Groovy expects a string argument
* without quotes, it interprets the variable incorrectly

---

# Important Distinction

There are two execution contexts here:

| Context              | Interpreter    |
| -------------------- | -------------- |
| `echo` pipeline step | Jenkins Groovy |
| `sh` step            | Linux shell    |

This distinction is critical.

---

# Variables Inside `sh`

Inside shell commands:

```groovy
sh '''
echo $BUILD_FILE_NAME
'''
```

works normally because:

* Linux shell handles environment variables using `$VARIABLE`
* Jenkins exports pipeline environment variables into the shell environment

This is standard shell behavior.

---

# Example Pipeline

```groovy
pipeline {
    agent any

    environment {
        BUILD_FILE_NAME = "laptop.txt"
    }

    stages {

        stage('Build') {
            steps {
                sh '''
                    mkdir -p build
                    echo "mainboard" > build/$BUILD_FILE_NAME
                    echo "display" >> build/$BUILD_FILE_NAME
                '''
            }
        }

        stage('Test') {
            steps {
                sh '''
                    test -f build/$BUILD_FILE_NAME
                    grep "mainboard" build/$BUILD_FILE_NAME
                    grep "display" build/$BUILD_FILE_NAME
                '''
            }
        }

        stage('Print') {
            steps {
                echo "$BUILD_FILE_NAME"

                sh '''
                    echo $BUILD_FILE_NAME
                '''
            }
        }
    }
}
```

# Why This Matters in Real DevOps

Variables are used everywhere in CI/CD:

| Usage                   | Example           |
| ----------------------- | ----------------- |
| Docker image names      | `IMAGE_NAME`      |
| AWS regions             | `AWS_REGION`      |
| Kubernetes namespaces   | `NAMESPACE`       |
| Artifact names          | `BUILD_FILE_NAME` |
| Credentials             | `DB_PASSWORD`     |
| Deployment environments | `ENVIRONMENT`     |

Without variables:

* pipelines become rigid
* updates become dangerous
* duplication increases
* maintenance becomes difficult

---

# Core Principle

This is essentially the DRY principle:

> Don't Repeat Yourself

Instead of:

```text
computer.txt
computer.txt
computer.txt
computer.txt
```

you define:

```groovy
BUILD_FILE_NAME = "laptop.txt"
```

and reference it everywhere.

# Important Real-World Observation

The instructor also demonstrated something important:

Even if automated tests pass:

* manual verification is still valuable after major pipeline changes

Why?

Because:

* tests may miss edge cases
* cached artifacts may mislead you
* UI may show stale data
* configuration changes can introduce unexpected behavior

This is very common in production CI/CD systems.

# Key Takeaways

| Concept          | Meaning                          |
| ---------------- | -------------------------------- |
| `environment {}` | Define global pipeline variables |
| `$VARIABLE`      | Access variable                  |
| Single quotes    | Literal string                   |
| Double quotes    | Variable interpolation           |
| `sh` step        | Executed by Linux shell          |
| `echo` step      | Executed by Jenkins Groovy       |
| DRY principle    | Avoid duplication                |

---

# Most Important Concept Here

The biggest lesson is not syntax.

It is understanding execution layers:

```text
Jenkins Groovy Layer
        ↓
Shell Layer
        ↓
Linux Commands
```

Many Jenkins debugging problems happen because people confuse:

* Groovy interpolation
* shell expansion
* Jenkins environment variables

Understanding which layer interprets the variable is fundamental for advanced Jenkins pipelines.
