# 1. Forking a Repository

On GitHub, a **fork** creates your own copy of another repository.

Original repository:

```text id="9gw7lp"
Instructor Repository
```

After forking:

```text id="bf5lsr"
Your GitHub Account
└── Your Copy of Repository
```

This allows:

* independent experimentation
* personal commits
* safe learning
* pull requests later if needed

The fork still remembers its original source.

That is why GitHub shows:

```text id="z4l3m5"
forked from ...
```

---

# 2. Why Forking Is Common

In real projects:

* developers rarely start from zero
* most work happens on existing repositories

Typical workflow:

1. Obtain repository access
2. Clone/fork repository
3. Understand application
4. Run application locally
5. Modify code
6. Commit changes
7. Push changes
8. Create pull requests

# 3. Branches and `main`

The course mentions:

> “main is the main development branch”

In Git:

```text id="x79tgc"
Repository
├── main
├── feature-login
├── feature-api
└── bugfix-auth
```

A branch is an independent line of development.

`main` usually represents:

* stable development code
* primary integration branch

CI pipelines commonly monitor the `main` branch.

# 4. GitHub Codespaces

GitHub provides **Codespaces**, which are cloud-based development environments.

A Codespace includes:

* Linux environment
* terminal
* VS Code interface
* Git support
* programming runtimes
* internet access

Effectively:

```text id="hbrn5y"
Browser + Cloud VM + VS Code
```

This removes the need to install everything locally.

# 9. Warnings vs Errors

The instructor correctly explains:

Warnings are common.

Important distinction:

## Warning

Application may still work.

## Error

Execution usually stops.

In CI pipelines:

* warnings may be tolerated
* errors usually fail the build

# 10. Running the Application

Command:

```bash id="vhr50d"
npm start
```

This launches the application locally.

Usually:

* starts development server
* opens port `3000`
* serves web application

Example:

```text id="08u7lj"
http://localhost:3000
```

or in Codespaces:

* a public forwarded URL

---

# 11. Development Server

When `npm start` runs:

* a process stays active
* watches file changes
* rebuilds application dynamically

Stopping it:

```text id="6o6q3e"
CTRL + C
```

This sends an interrupt signal to terminate the process.

# 12. Why This Matters for Jenkins

This is the key DevOps lesson:

Before automation:

* humans must understand the process manually.

You cannot automate:

* unknown workflows
* unknown commands
* unknown dependencies

The manual workflow discovered here becomes the future Jenkins pipeline.

---

# 13. Future CI Pipeline Mapping

Manual process:

```bash id="epm6nk"
npm install
npm start
```

Future Jenkins pipeline:

```groovy id="1pn8fi"
stage('Install') {
    steps {
        sh 'npm install'
    }
}

stage('Run') {
    steps {
        sh 'npm start'
    }
}
```

This is the core idea behind CI automation.
