### Jenkins + Docker Execution Flow (Behind the Scenes)

---

### 1. High-Level Architecture

Components:

* **Controller (Master)** → Orchestrates pipeline
* **Agent (Worker Node)** → Executes stages
* **Docker** → Provides isolated runtime environment

---

### 2. End-to-End Execution Flow

#### Step 1: Job Trigger

* You click **Build Now** (or webhook triggers)
* Controller schedules pipeline execution

---

#### Step 2: Agent Selection

* Controller finds an **agent** that:

  * Is available
  * Has Docker capability

---

#### Step 3: Source Code Checkout

* Controller (or agent, depending on config) runs:

```bash
git clone <repo>
```

* Files stored in:

```bash
$WORKSPACE
```

---

#### Step 4: Docker Container Startup

Agent runs something equivalent to:

```bash
docker run ...
```

Key behavior:

* Starts container from image (e.g., `node:18-alpine`)
* Mounts workspace into container

Example (conceptual):

```bash
docker run -v /jenkins/workspace:/workspace node:18-alpine
```

---

### 3. Critical Concept: Workspace Mounting

This is the most important part.

#### Without Mount:

* Container cannot see project files
* Build fails

#### With Mount:

* Container sees:

```bash
/workspace (inside container) == Jenkins workspace (host)
```

Effects:

1. **Read access** → container uses project files
2. **Write persistence** → generated files survive container deletion

---

### 4. Inside the Container

Commands executed:

```bash
npm ci
npm run build
```

What happens:

* `node_modules/` created
* `build/` created

These are written to:

```bash
/workspace  (mounted volume)
```

So they persist outside container.

---

### 5. Container Lifecycle

#### Start:

```bash
docker run
```

#### Execute:

```bash
sh steps...
```

#### Stop:

```bash
docker stop
```

#### Cleanup:

```bash
docker rm
```

After this:

* Container = **gone**
* Files = **still in workspace**

---

### 6. Jenkins Logs (What You Actually See)

Sequence in logs:

1. Git clone
2. Stage start
3. Docker container launch
4. Command execution
5. Container stop + cleanup

Example pattern:

```bash
Cloning repository...

[Pipeline] stage (Build)

docker run ...

+ npm ci
+ npm run build

docker stop ...
docker rm ...
```

---

### 7. Why Docker is Used in Jenkins

Without Docker:

* Dependency on agent environment
* Version conflicts
* Non-reproducible builds

With Docker:

* Controlled environment
* Specific versions (Node 18, etc.)
* Reproducibility across builds

---

### 8. Key Insight (Non-Negotiable)

> Container is **temporary**, workspace is **persistent**

If workspace is not mounted:

* Build output is lost after container stops

---

### 9. Real DevOps Interpretation

This design ensures:

| Concern                 | Solution              |
| ----------------------- | --------------------- |
| Environment consistency | Docker image          |
| File persistence        | Workspace mount       |
| Isolation               | Container runtime     |
| Cleanup                 | Container termination |

---

### 10. Common Mistake

Wrong assumption:

```bash
"Container holds my build output"
```

Correct:

```bash
"Workspace holds my build output"
```

---

### 11. Mental Model

Think of it like this:

```bash
Jenkins Workspace = Shared Disk
Docker Container = Temporary Worker
```

* Worker comes → does job → leaves
* Disk remains → holds results

---

### 12. Final Summary Flow

```bash
Trigger → Agent → Clone Repo → Start Container
→ Mount Workspace → Run Commands → Stop Container
→ Continue Pipeline
```
