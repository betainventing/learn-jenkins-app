--------------------------------------------------------------------------------

**Linting** = static analysis of source code to detect issues **without executing it**.

It checks for:

* Syntax errors (missing brackets, invalid constructs)
* Code style violations (formatting, naming conventions)
* Potential bugs (unused variables, unreachable code)
* Best practices (security rules, anti-patterns)

Examples:

* JavaScript → ESLint
* Python → flake8 / pylint
* Java → Checkstyle / PMD

---

## Why linting matters in a Jenkins pipeline

In CI/CD, linting is a **fast, early quality gate**.

Key properties:

* Runs **without build/compile/runtime dependencies**
* Executes **very quickly**
* Fails fast before wasting resources

---

## Where linting fits in pipeline design

Typical pipeline order:

```
Checkout → Lint → Build → Test → Package → Deploy
```

### Purpose in this flow

* Catch trivial issues early
* Prevent bad code from entering expensive stages (build/test)
* Enforce team-wide coding standards automatically

---

## Parallel vs Sequential decision (your actual question)

### 1. Run linting in parallel — when?

Use parallel execution if:

* Multiple languages/tools exist (e.g., frontend + backend)
* Lint jobs are independent
* You want to reduce total pipeline time

Example:

```
stage: Lint
  parallel:
    - frontend-lint (ESLint)
    - backend-lint (flake8)
```

**Implication:**

* Faster feedback
* Slightly more complex pipeline
* Failures from any branch fail the stage

---

### 2. Run linting sequentially — when?

Use sequential execution if:

* Single codebase / single linter
* You want strict fail-fast before any parallel fan-out
* Simpler pipeline design is preferred

Example:

```
Checkout → Lint → (if success) → Parallel Build/Test
```

**Implication:**

* Clean gate before heavy work
* Slightly slower overall pipeline if lint could have overlapped

---

## Practical Jenkins strategy (what actually works well)

For most real CI pipelines:

### Recommended pattern

```
Stage 1: Checkout
Stage 2: Lint (sequential, fail fast)
Stage 3: Parallel:
    - Build
    - Unit Tests
Stage 4: Integration Tests
Stage 5: Package/Deploy
```

### Why this design

* Lint is cheap → run early
* Avoid wasting compute on bad code
* Parallelization reserved for expensive stages

---

## When teams do it differently

Some advanced setups:

* Run lint **inside pre-commit hooks** → reduces CI load
* Run lint **in parallel with build** → if build is also fast and independent
* Split lint into multiple granular jobs for large monorepos

---

## Bottom line

* Linting = **static code quality gate**
* In Jenkins:

  * Usually **early stage**
  * Usually **sequential (fail-fast)**
  * Can be **parallelized** when multiple independent lint tasks exist

If you're designing pipelines, the rule is simple:

> If it’s cheap and can block bad code → run it early
> If it’s expensive → parallelize it later
