# Troubleshooting Jenkins + Docker Pipelines

This section explains a very common real-world CI/CD problem:

> Jenkins itself works, but Docker-based pipelines suddenly fail.

This is extremely common when using:

* Docker Desktop
* Docker Compose
* containerized Jenkins environments

Especially after:

* system restarts
* Docker Desktop restarts
* improper container shutdowns

---

# 1. Symptoms of the Problem

Typical behavior:

## Non-Docker Pipelines Still Work

Example:

* simple `echo`
* shell commands
* basic Jenkins jobs

These succeed because they run directly inside Jenkins.

---

## Docker-Based Pipelines Fail

Pipelines using:

```groovy id="9l5h4s"
agent {
    docker {
        image 'node:18-alpine'
    }
}
```

start failing with errors like:

```text id="yrm80x"
error during connect
```

or:

* Docker daemon unavailable
* Cannot connect to Docker socket
* Container startup failure
* Docker API errors

---

# 2. Why This Happens

The root issue is usually:

> Jenkins container is running, but Docker environment is incomplete or disconnected.

In the course setup:

* Jenkins itself runs inside Docker
* Docker Compose manages multiple containers

Typically:

* one Jenkins container
* one Docker-in-Docker container (`dind`)

Both are required.

---

# 3. Understanding the Docker Compose Architecture

The setup usually looks like:

```text id="i6h1ov"
Docker Compose Project
├── jenkins
└── docker-in-docker (dind)
```

---

## Jenkins Container

Runs:

* Jenkins UI
* pipelines
* plugins

---

## Docker-in-Docker Container

Provides:

* Docker daemon
* container execution capability

This is what allows Jenkins to launch:

* build containers
* pipeline containers
* Docker agents

---

# 4. Common Failure Scenario

After rebooting:

* only Jenkins container restarts
* Docker daemon container may remain stopped

Result:

```text id="cs4d1y"
Jenkins is alive
Docker functionality is broken
```

So:

* UI works
* login works
* basic jobs work
* Docker pipelines fail

---

# 5. Recognizing the Problem in Docker Desktop

Inside Docker Desktop:

Healthy state:

```text id="z0w5ou"
2/2 running
```

Broken state:

```text id="3o6k9y"
1 running
1 exited
```

or:

* containers outside compose group
* orphan containers
* exited `dind` container

---

# 6. Why “Orphan” Containers Are Dangerous

Sometimes users manually start Jenkins containers independently.

This creates:

* duplicated containers
* networking inconsistencies
* volume conflicts
* Docker socket issues

You should remove unintended containers.

---

# 7. Correct Recovery Procedure

The instructor demonstrates the correct operational recovery flow.

---

## Step 1 — Navigate to Compose Directory

Must be inside directory containing:

```text id="x2g7lw"
docker-compose.yml
```

or:

```text id="6nm9qx"
compose.yaml
```

Otherwise commands will fail.

---

## Step 2 — Stop Everything Cleanly

Command:

```bash id="zh7k2q"
docker compose down
```

Purpose:

* stop containers
* remove networks
* reset compose-managed environment

This ensures:

* clean shutdown
* consistent restart

---

## Step 3 — Start Environment Again

Command:

```bash id="a6v9fe"
docker compose up -d
```

Meaning:

* recreate/start containers
* detached mode (`-d`)

Now both containers should start.

---

# 8. Why This Usually Fixes the Problem

This re-establishes:

* Docker networking
* shared volumes
* daemon connectivity
* container dependencies

Essentially rebuilding the runtime environment.

---

# 9. Relationship Between Jenkins and Docker

In this architecture:

```text id="61kwdx"
Jenkins
   ↓
Docker API
   ↓
Docker Daemon
   ↓
Pipeline Containers
```

If Docker daemon disappears:

* Jenkins cannot create containers
* Docker agents fail
* pipeline stages fail

---

# 10. Key DevOps Lesson — Infrastructure State Matters

CI/CD pipelines depend on:

* runtime infrastructure
* container health
* daemon availability
* networking
* storage mounts

Many “pipeline issues” are actually:

* infrastructure issues

not:

* pipeline syntax problems
