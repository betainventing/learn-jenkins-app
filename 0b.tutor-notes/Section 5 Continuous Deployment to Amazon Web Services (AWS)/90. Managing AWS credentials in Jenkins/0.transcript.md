## Storing AWS Credentials in Jenkins

After creating the IAM access keys in AWS Identity and Access Management, the next step is securely storing them inside Jenkins. 

The lecture demonstrates the standard Jenkins credential management workflow.

---

# Jenkins Credentials Store

Inside Jenkins:

```text id="x5a3rz"
Dashboard
   ↓
Manage Jenkins
   ↓
Credentials
   ↓
System
   ↓
Global credentials
```

This is Jenkins’ built-in secret management system.

It stores:

* Passwords
* Tokens
* SSH keys
* API keys
* Username/password pairs

securely and separately from pipeline code.

---

# Why Credentials Must NOT Be Hardcoded

Bad practice:

```groovy id="n6x1r4"
environment {
    AWS_ACCESS_KEY_ID = 'AKIA...'
    AWS_SECRET_ACCESS_KEY = 'secret'
}
```

Problems:

* Secrets leak into Git
* Secrets leak into Jenkinsfiles
* Secrets may appear in logs
* Difficult credential rotation
* Security audit failures



---

# AWS Credentials Mapping in Jenkins

AWS provides:

| AWS Term          | Jenkins Mapping |
| ----------------- | --------------- |
| Access Key ID     | Username        |
| Secret Access Key | Password        |

Even though AWS does not literally call them username/password, Jenkins can store them that way.

# Jenkins `withCredentials`

Jenkins provides a helper step:

```groovy id="8l7r0l"
withCredentials(...)
```

Purpose:

```text id="jlwm5r"
Temporarily inject secrets into environment variables
```

This is the preferred secure pattern.

Selected binding:


# Generated Pipeline Example

Resulting pipeline block:

```groovy id="lhq7lr"
withCredentials([
    usernamePassword(
        credentialsId: 'my-aws',
        usernameVariable: 'AWS_ACCESS_KEY_ID',
        passwordVariable: 'AWS_SECRET_ACCESS_KEY'
    )
]) {
    sh '''
        aws --version
        aws s3 ls
    '''
}
```



---

# Why Commands Must Be INSIDE the Block

Important scope rule:

```text id="jlwm1k"
Credentials exist only inside withCredentials block
```

Meaning:

This works:

```groovy id="2z4xci"
withCredentials(...) {
    sh 'aws s3 ls'
}
```

This fails:

```groovy id="t2rk7v"
withCredentials(...) {
    sh 'aws --version'
}

sh 'aws s3 ls'
```

because the environment variables disappear after the block ends.

# Authentication Flow

What happens internally:

```text id="jlwm0n"
Jenkins Credentials Store
        ↓
withCredentials injects env vars
        ↓
AWS CLI reads env vars
        ↓
AWS authenticates IAM user
        ↓
S3 API request succeeds
```

# Jenkins Secret Masking

One important Jenkins security feature shown in logs:

```text id="jlwm8b"
Masking supported pattern matches
```

Meaning:

If pipeline accidentally prints:

```bash id="jlwm7m"
echo $AWS_SECRET_ACCESS_KEY
```

Jenkins masks the output.

Instead of real secret:

```text id="5jlwm2"
****************
```

appears in logs. 

---

# Important Limitation of Masking

Masking improves security but is NOT perfect protection.

Examples of possible leaks:

* Base64 encoding secrets
* Writing secrets to files
* Sending secrets externally
* Printing transformed secrets

So masking is helpful, but secure pipeline design is still required.

# Why Environment Variables Are Common in CI/CD

Most DevOps tools automatically support credentials through environment variables.

Examples:

| Tool       | Common Env Vars         |
| ---------- | ----------------------- |
| AWS CLI    | `AWS_ACCESS_KEY_ID`     |
| Terraform  | `AWS_SECRET_ACCESS_KEY` |
| Docker     | `DOCKER_AUTH_CONFIG`    |
| Kubernetes | `KUBECONFIG`            |
| GitHub CLI | `GITHUB_TOKEN`          |

This makes secret injection standardized across pipelines.

---

# Security Advantage of `withCredentials`

Benefits:

* Temporary secret exposure
* Scoped access
* Automatic cleanup
* Log masking
* Centralized management

Compared to hardcoding secrets, this is dramatically safer.

This lecture teaches a core CI/CD security model:

```text id="jlwm2n"
Secrets should be injected at runtime,

```

This principle applies everywhere:

* Jenkins
* GitHub Actions
* GitLab CI
* Kubernetes
* Terraform
* Docker Compose

# Real Production Evolution

In advanced environments, teams often move beyond static access keys entirely.

Instead of:

```text id="jlwm3z"
Access Key ID + Secret Key
```

they use:

* IAM Roles
* OIDC federation
* STS temporary credentials
* Vault integrations
* Workload identity systems

because long-lived secrets remain operational risks.
