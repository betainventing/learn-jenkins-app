From the AWS CLI documentation, commands follow this structure:

```bash id="53k7tp"

```


Breakdown:

Command:

---

# Why `aws --version` Works But `aws s3 ls` Fails

This is a very important distinction.

---

## `aws --version`

Command:

```bash id="4rqrlu"
aws --version
```

This is a **local command**.

It only checks:

* Installed CLI binary
* Local package metadata

No AWS API call happens.

No authentication required.

---

## `aws s3 ls`

Command:

```bash id="lnrzec"
aws s3 ls
```

This command makes a **real AWS API request**.

AWS must verify:

* Who you are
* Whether you are authenticated
* Whether you are authorized

So credentials are required.

---

# Error Encountered

Pipeline error:

```text id="gj7j2g"
Unable to locate credentials
You can configure credentials by running "aws configure"
```

This is expected behavior.

---

# Why This Error Is Actually Good

If AWS allowed unauthenticated users to run:

```bash id="t3b88r"
aws s3 ls
```

then anyone on the internet could:

* See your buckets
* Access cloud resources
* Enumerate infrastructure

That would be a catastrophic security problem.

So AWS blocks requests unless credentials are provided.

---

# Authentication Concept

AWS CLI needs identity information.

Specifically:

```text id="u8f05j"
Who are you?
```

and

```text id="50jlwm"
What are you allowed to do?
```

This is handled through:

* Access keys
* Secret keys
* IAM users
* IAM roles
* Temporary credentials

---

# Why `aws configure` Is Not Suitable For Jenkins

Interactive command:

```bash id="ckhbof"
aws configure
```

asks for:

* Access key ID
* Secret access key
* Region
* Output format

This works on a developer laptop.

But Jenkins pipelines are:

```text id="4t4csy"
Non-interactive
```

So manually typing credentials is not practical.

---

# Proper DevOps Approach

Instead of interactive login, CI/CD pipelines use:

* Jenkins credentials
* Environment variables
* IAM roles
* Secret injection
* Temporary tokens

Typical architecture:

```text id="e8txz9"
Jenkins
   ↓
Inject AWS Credentials
   ↓
AWS CLI Uses Credentials
   ↓
AWS API Access Granted
```

---

# Important Security Principle

Authentication and authorization are separate concepts.

---

## Authentication

```text id="ptv5bk"
Who are you?
```

AWS verifies identity using credentials.

---

## Authorization

```text id="0l1jku"
What can you do?
```

AWS IAM policies determine permissions.

Example:

* Can list S3 buckets
* Can upload objects
* Can delete objects
* Can create EC2 instances

---

# Real DevOps Best Practice

Modern production environments avoid permanent access keys whenever possible.

Preferred methods:

* IAM Roles
* OIDC federation
* Temporary STS credentials

However, for learning Jenkins + AWS basics, courses usually begin with:

```text id="5ziz52"
Access Key ID
+
Secret Access Key
```

because it is simpler to understand initially.

---

# Important AWS Security Warning

Never hardcode credentials like this:

```groovy id="v7kvta"
sh 'aws configure'
```

or:

```groovy id="1zkxj7"
environment {
    AWS_SECRET_ACCESS_KEY = 'abc123'
}
```

inside source-controlled Jenkinsfiles.

Reasons:

* Credentials leak into Git
* Credentials leak into logs
* Major security risk

Instead use:

* Jenkins Credentials Store
* Secret bindings
* IAM roles
