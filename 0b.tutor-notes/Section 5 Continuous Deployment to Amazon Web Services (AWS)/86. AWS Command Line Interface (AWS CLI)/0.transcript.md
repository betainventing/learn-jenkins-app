## Using AWS CLI From Jenkins

To automate interaction with Amazon Web Services services such as Amazon S3, Jenkins needs a non-GUI method of communication.

That method is the AWS Command Line Interface. 

---

# Why Jenkins Needs AWS CLI

Jenkins pipelines are automated and non-interactive.

Jenkins cannot:

* Open browsers
* Click buttons in AWS Console
* Upload files manually through UI

Instead, Jenkins executes shell commands.

Example workflow:

```text
Jenkins Pipeline
       ↓
AWS CLI Commands
       ↓
AWS APIs
       ↓
S3 Upload / Cloud Operations
```

This is the standard DevOps automation model. 

---

# AWS CLI

The AWS CLI exposes a command called:

```bash
aws
```

General syntax:

```bash
aws <service> <operation> [options]
```

Examples:

```bash
aws s3 ls
aws s3 cp file.txt s3://mybucket
aws ec2 describe-instances
```

---

# Using AWS CLI Inside Docker

Instead of installing AWS CLI directly on the Jenkins server, the course uses the official Docker image from [Docker Hub](https://hub.docker.com/r/amazon/aws-cli?utm_source=chatgpt.com). 

Official image:

```text
amazon/aws-cli
```

Benefits:

* No manual installation
* Consistent environment
* Easy version control
* Reproducible pipelines
* Cleaner Jenkins agents

# Jenkins Pipeline Example

Initial pipeline stage:

```groovy
stage('AWS') {
    agent {
        docker {
            image 'amazon/aws-cli'
        }
    }

    steps {
        sh 'aws --version'
    }
}
```

Goal:

```bash
aws --version
```

This prints the AWS CLI version. 

---

# Problem Encountered

The pipeline hangs indefinitely.

Reason:

The Docker image defines its own ENTRYPOINT.

The Jenkins Docker agent expects to run commands differently.

Error meaning:

```text
Container started but didn't run the expected command
```

This happens because the image automatically launches AWS CLI behavior instead of behaving like a generic shell container. 

---

# Docker ENTRYPOINT Concept

In Docker:

* `ENTRYPOINT` defines the executable started automatically
* `CMD` defines default arguments

Example conceptual behavior:

```dockerfile
ENTRYPOINT ["aws"]
```

Meaning:

Whenever container starts:

```bash
aws
```

is already running internally.

This works locally for direct CLI usage, but conflicts with Jenkins Docker agent execution model.

---

# Solution: Override ENTRYPOINT

Jenkins Docker agent allows passing extra Docker arguments.

Corrected pipeline:

```groovy
stage('AWS') {
    agent {
        docker {
            image 'amazon/aws-cli'
            args '--entrypoint=""'
        }
    }

    steps {
        sh 'aws --version'
    }
}
```



---

# What `--entrypoint=""` Does

It removes the image's predefined ENTRYPOINT.

Result:

* Container behaves like a normal Linux container
* Jenkins can execute shell commands normally
* `sh 'aws --version'` works correctly

---

# Successful Output

Example output:

```text
aws-cli/2.15.53 Python/3.x Linux/5.x exe/x86_64
```

This confirms:

* Container started successfully
* AWS CLI is available
* Jenkins can execute AWS commands

# Versioning Best Practice

Two approaches were discussed.

---

## Option 1 — Use `latest`

```groovy
image 'amazon/aws-cli'
```

Equivalent to:

```text
amazon/aws-cli:latest
```

Advantages:

* Always newest version

Disadvantages:

* Breaking changes possible
* Non-deterministic builds
* Future incompatibilities

---

## Option 2 — Pin Specific Version (Recommended)

Example:

```groovy
image 'amazon/aws-cli:2.15.53'
```

Advantages:

* Stable pipelines
* Reproducible builds
* Easier debugging
* Safer CI/CD

Recommended in production DevOps pipelines.
