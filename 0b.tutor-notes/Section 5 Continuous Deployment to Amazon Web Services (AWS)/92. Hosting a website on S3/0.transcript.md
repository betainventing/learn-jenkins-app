# Converting an S3 Bucket Into a Static Web Server

This lecture configures Amazon S3 to serve files publicly as a static website. 

At this point:

* Jenkins already uploads files to S3
* `index.html` already exists in the bucket

Now the bucket itself must be configured to behave like a web server.

---

# Three Required Steps

The lecture correctly identifies three separate requirements:

| Step | Purpose                                   |
| ---- | ----------------------------------------- |
| 1    | Enable static website hosting             |
| 2    | Allow public access                       |
| 3    | Add bucket policy permitting object reads |

All three are required.

---

# Step 1 — Enable Static Website Hosting

Inside bucket:

```text id="jlwm91"
Properties
   ↓
Static website hosting
   ↓
Enable
```



---

# What “Static Website Hosting” Means

Static hosting means:

* No backend processing
* No server-side code
* No database execution
* No application runtime

Only static assets are served:

* HTML
* CSS
* JavaScript
* Images
* Fonts

Example architecture:

```text id="jlwm12"
Browser
   ↓
S3 Bucket
   ↓
Static Files
```

---

# Index Document

Important configuration:

```text id="jlwm31"
index.html
```

This defines the default webpage served when users open the website root URL.

Equivalent concept exists in:

* Apache
* Nginx
* IIS

Example:

```text id="jlwm84"
https://example.com/
```

internally serves:

```text id="jlwm56"
index.html
```



---

# Generated Website Endpoint

After enabling hosting, AWS generates a website URL.

Example structure:

```text id="jlwm40"
http://bucket-name.s3-website-region.amazonaws.com
```

This is a special S3 website endpoint.

---

# Why 403 Forbidden Happens Initially

Immediately after enabling hosting:

```text id="jlwm73"
403 Forbidden
```

appears.

This is expected.

Reason:

```text id="jlwm25"
Hosting enabled ≠ public permissions enabled
```

S3 buckets remain private by default.

---

# Step 2 — Disable “Block Public Access”

Inside:

```text id="jlwm67"
Permissions
   ↓
Block Public Access
   ↓
Edit
```

Disable:

```text id="jlwm49"
Block all public access
```



---

# Why AWS Blocks Public Access By Default

This is a major AWS security protection.

Most S3 buckets should NOT be public because they may contain:

* Backups
* Logs
* Customer data
* Secrets
* Internal assets

Public exposure of S3 buckets has caused many real-world data breaches.

So AWS intentionally makes public access difficult.

---

# Important Distinction

Disabling block public access does NOT automatically make files public.

It only removes the protection mechanism.

You still need explicit allow policies.

---

# Step 3 — Add Bucket Policy

Inside:

```text id="jlwm05"
Permissions
   ↓
Bucket Policy
```

A policy is required that allows public reads.



---

# Policy Structure

AWS policies are written in JSON.

Policies define:

* Effect
* Principal
* Action
* Resource

---

# Important Policy Elements

---

## Effect

```json id="jlwm19"
"Effect": "Allow"
```

Meaning:

```text id="jlwm62"
Permit access
```

---

## Principal

```json id="jlwm44"
"Principal": "*"
```

Meaning:

```text id="jlwm28"
Any user on the internet
```

This makes the policy public.

---

## Action

```json id="jlwm80"
"Action": "s3:GetObject"
```

Meaning:

```text id="jlwm38"
Allow reading/downloading objects
```

Important:

This grants read-only access.

Not:

* Upload
* Delete
* Modify

---

## Resource

Example:

```json id="jlwm95"
"Resource": "arn:aws:s3:::my-bucket/*"
```

Meaning:

```text id="jlwm53"
All objects inside this bucket
```

The trailing:

```text id="jlwm71"
*
```

means:

```text id="jlwm16"
Every object
```

inside the bucket.

---

# Understanding ARN

ARN = Amazon Resource Name.

General structure:

```text id="jlwm35"
arn:partition:service:region:account-id:resource
```

For S3:

```text id="jlwm88"
arn:aws:s3:::bucket-name/*
```

uniquely identifies S3 objects.



---

# Final Effective Policy

Conceptually:

```json id="jlwm27"
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-bucket/*"
}
```

Meaning:

```text id="jlwm46"
Anyone may read any object in this bucket
```

---

# Why `GetObject` Specifically Matters

Static websites only require:

```text id="jlwm58"
Read access
```

because browsers only need to:

* Request files
* Download files

No upload permissions are needed publicly.

---

# Result After All Three Steps

Now:

```text id="jlwm10"
Website endpoint
   ↓
S3 serves index.html
   ↓
Browser displays webpage
```

The uploaded file:

```html id="jlwm92"
Hello S3
```

becomes publicly visible in browser.



---

# Important Security Implication

This configuration intentionally creates a public bucket.

That is acceptable for:

* Static websites
* Public frontend assets

But dangerous for sensitive data.

---

# Real Production Best Practice

Modern production architectures usually place:

Amazon CloudFront in front of S3.

Architecture:

```text id="jlwm24"
Browser
   ↓
CloudFront CDN
   ↓
Private S3 Bucket
```

Benefits:

* HTTPS
* CDN caching
* DDoS protection
* Better performance
* Private bucket architecture

In many modern setups, the S3 bucket itself is not public at all.

---

# Important Technical Distinction

S3 website hosting endpoint:

```text id="jlwm65"
s3-website
```

is different from standard S3 REST API endpoints.

Website endpoint behavior supports:

* Default index documents
* Error documents
* Browser-style website behavior
