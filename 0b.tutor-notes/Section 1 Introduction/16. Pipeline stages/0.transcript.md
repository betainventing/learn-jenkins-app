This section introduces one of the most important concepts in CI/CD:

# Automated Testing in Pipelines

Up to this point, the workflow was:

1. Modify pipeline
2. Run build
3. Open artifact manually
4. Verify files manually

That approach does not scale.

In real DevOps environments:

* builds happen continuously
* deployments are frequent
* hundreds of pipeline executions may run daily

Manual verification becomes impossible.

---

# Purpose of a Test Stage

The instructor adds a new pipeline stage:

```groovy id="l8uvzj"
stage('Test') {
    steps {
        echo 'Testing the new laptop'
    }
}
```

This introduces the CI/CD principle:

```text id="h0m5hb"
Build → Test → Deploy
```

A pipeline should automatically validate output before deployment.

---

# Jenkins Pipeline Structure

The pipeline now contains multiple stages:

```groovy id="l7j2me"
stages {
    stage('Build') {
        steps {
            ...
        }
    }

    stage('Test') {
        steps {
            ...
        }
    }
}
```

Each stage represents a logical phase.

Typical enterprise pipelines may contain:

* Checkout
* Build
* Unit Test
* Integration Test
* Security Scan
* Package
* Publish Artifact
* Deploy
* Smoke Test

---

# Stage Visualization in Jenkins

When multiple stages exist:

Jenkins visualizes them separately.

You can:

* click a stage
* inspect only that stage's logs
* isolate failures faster

This becomes critical in large pipelines.

# Meaning of `test -f`

```bash id="3w5xw6"
test -f file.txt
```

checks:

```text id="8e6qzj"
Does this regular file exist?
```

If the file exists:

* command succeeds

If not:

* command fails

---

# Jenkins Test Stage Example

The pipeline likely becomes:

```groovy id="8r4zzi"
stage('Test') {
    steps {
        sh 'test -f build/computer.txt'
    }
}
```

This automatically verifies artifact existence.

---

# Why This Matters

Instead of manually checking:

```text id="j5l45g"
Did computer.txt get created?
```

the pipeline validates it automatically.

This is the foundation of automated quality gates.

# Important CI/CD Concept: Failing Fast

# Linux Exit Codes

Every Linux command returns an exit code.

Convention:

| Exit Code | Meaning |
| --------- | ------- |
| 0         | Success |
| Non-zero  | Failure |

---

# Example

Successful test:

```bash id="f5q1h6"
test -f computer.txt
```

returns:

```text id="m77kt2"
0
```

Failed test:

```bash id="bwwzqj"
test -f missing.txt
```

returns:

```text id="6q1g5x"
1
```

---

# How Jenkins Uses Exit Codes

Jenkins interprets:

```text id="wz6k0t"
exit code 0 → stage success
exit code != 0 → stage failure
```

This is fundamental Jenkins behavior.

---

# Why No Error Message Appears

The `test` command is intentionally silent.

It communicates success/failure using only exit codes.

So this:

```bash id="2q6s3d"
test -f file.txt
```

produces no output when successful.

This is normal Linux behavior.

# Real DevOps Relevance

Automated testing stages are essential because they:

* prevent broken deployments
* catch failures early
* eliminate manual validation
* improve reliability
* enable continuous delivery
* provide reproducible verification

Without automated testing, CI/CD pipelines become unreliable manual workflows rather than true automation systems.
