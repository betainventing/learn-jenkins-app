# Why the File Kept Growing Across Builds

What you observed is a very important behavior in Jenkins pipelines:

> Jenkins reuses the same workspace between builds unless you explicitly clean it.

That is why your file kept accumulating data.

---

# What `touch` Actually Does

A common misunderstanding is thinking:

```bash id="mxh38d"
touch file.txt
```

always creates a brand-new empty file.

That is not true.

`touch` behaves like this:

| Situation           | Behavior              |
| ------------------- | --------------------- |
| File does not exist | Create empty file     |
| File already exists | Update timestamp only |

So when:

```bash id="7i9ymn"
build/computer.txt
```

already existed from a previous build:

```bash id="fh1v0n"
touch build/computer.txt
```

did not clear the file.

It simply updated the modification time.

The contents remained intact.

---

# Why the File Was Reused

Because Jenkins stores build files inside a **workspace**.

A Jenkins workspace is essentially:

> A directory assigned to a job where builds execute and files are stored.

Typical contents include:

* Source code
* Build artifacts
* Temporary files
* Dependency caches
* Logs
* Generated outputs

---

# What Happened Internally

First build:

```text id="67ij4q"
computer.txt
└── mainboard
```

Second build:

```text id="n8d5oa"
computer.txt
└── mainboard
└── mainboard
```

Third build:

```text id="5o3ndn"
computer.txt
└── mainboard
└── mainboard
└── mainboard
```

Because this command:

```bash id="80cc88"
echo mainboard >> build/computer.txt
```

uses:

```bash id="5d7u6j"
>>
```

which means:

> Append to file.

It never overwrites existing content.

---

# Important Jenkins Workspace Behavior

By default:

> Jenkins does NOT automatically wipe the workspace after every build.

This is intentional.

Why?

Because some builds benefit from cached files:

* Maven dependencies
* npm packages
* Gradle caches
* Docker layers
* compiled artifacts

Reusing workspaces can improve performance.

But it also introduces risks:

* Stale files
* Unexpected artifacts
* Cross-build contamination
* Non-reproducible builds

---

# Why This Is Dangerous in CI/CD

A pipeline should ideally be:

* Predictable
* Repeatable
* Isolated

If old files remain:

* Builds may behave differently
* Tests may pass incorrectly
* Deployments may include outdated artifacts

This creates flaky pipelines.

---

# Two Ways to Solve the Problem

---

# Option 1 — Manual Cleanup

Explicitly delete files/directories yourself.

Example:

```groovy id="1kt00f"
sh 'rm -rf build'
```

before starting the build.

This works, but becomes difficult in large projects.

---

# Option 2 — Clean the Entire Workspace

This is the better Jenkins-native solution.

You used:

```groovy id="v4w90f"
post {
    always {
        cleanWs()
    }
}
```

This tells Jenkins:

> After the pipeline finishes, delete everything in the workspace.

---

# Understanding the `post` Section

The `post` block defines actions executed after stages complete.

Structure:

```groovy id="t0dr1w"
pipeline {
    stages {
        ...
    }

    post {
        ...
    }
}
```

Important:

* `post` is at the same hierarchy level as `stages`
* It belongs directly under `pipeline`

---

# Why `always` Matters

Inside `post`:

```groovy id="j9khcr"
always {
    cleanWs()
}
```

means:

> Execute this regardless of build result.

Even if:

* build fails
* tests fail
* deployment fails

the workspace still gets cleaned.

Other common conditions include:

| Condition | Meaning                |
| --------- | ---------------------- |
| success   | Only if build succeeds |
| failure   | Only if build fails    |
| unstable  | For unstable builds    |
| changed   | Build status changed   |

---

# What `cleanWs()` Does

`cleanWs()` removes:

* Files
* Directories
* Generated artifacts
* Temporary build outputs

Essentially:

```text id="k2nfxf"
workspace/
└── everything deleted
```

after the pipeline finishes.

---

# Why the Workspace Link Disappeared

After cleanup:

* Jenkins removed the physical workspace directory
* Therefore the workspace UI link disappeared

That confirmed cleanup succeeded.

---

# What Happened in the Next Build

Now the next build starts with:

```text id="z3ttc8"
empty workspace
```

So:

```bash id="9qj2y2"
mkdir -p build
touch build/computer.txt
```

create fresh resources again.

Result:

```text id="qyl14x"
mainboard
display
keyboard
```

without duplicates.

---

# Important Real-World CI/CD Principle

What you implemented is actually a production-grade concept:

> Clean builds.

Modern CI/CD systems strongly prefer isolated clean environments.

This is why many systems use:

* Ephemeral containers
* Temporary Kubernetes pods
* Disposable virtual machines

instead of persistent workspaces.

The idea is:

```text id="bm9pkn"
Create environment
Run pipeline
Destroy environment
```

This guarantees reproducibility.

# Key Concepts You Just Learned

| Concept              | Meaning                                 |
| -------------------- | --------------------------------------- |
| Workspace            | Directory where Jenkins executes builds |
| Persistent workspace | Files survive across builds             |
| `touch`              | Creates file only if absent             |
| `>>`                 | Appends instead of overwriting          |
| `post`               | Actions after pipeline execution        |
| `always`             | Execute regardless of result            |
| `cleanWs()`          | Delete entire workspace                 |
| Clean builds         | Avoid stale artifacts                   |

Many CI/CD problems in real production systems are caused by:

* stale files
* reused artifacts
* hidden workspace state
* cache contamination

Understanding workspace lifecycle early is extremely important for debugging Jenkins pipelines professionally.
