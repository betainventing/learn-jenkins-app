# What a Jenkins Pipeline Actually Is

A **pipeline** in Jenkins is simply:

> A sequence of automated steps that build, test, package, and deploy software.

It is the software equivalent of an industrial assembly line.

---

# Assembly Line Analogy

Physical manufacturing:

```text id="3f3wl5"
Add components → Assemble → Test → Package → Ship
```

Software delivery:

```text id="dxs6md"
Pull code → Build → Test → Package → Deploy
```

The core idea is identical:

* Break work into stages
* Execute them in order
* Automate repetitive tasks
* Ensure consistent output

---

# Pipeline Structure

A Jenkins pipeline is usually divided into:

* Stages
* Steps

---

# Stage

A stage represents a major phase of work.

Examples:

```text id="yce9p9"
Build
Test
Package
Deploy
```

---

# Step

A step is an individual command executed inside a stage.

Examples:

```bash id="nyn7f6"
mkdir
touch
echo
npm install
mvn package
docker build
```

# Important Jenkins Concept

Inside Jenkins pipelines:

> Most actual work is performed using shell commands.

Jenkins itself is not magically assembling software.

It orchestrates commands executed on the agent machine.

That is why you repeatedly use:

```groovy id="2j6yjs"
sh 'command'
```

The `sh` step means:

> Execute this command inside a Linux shell.

# Why `mkdir` Failed

You encountered:

```text id="m8n4mg"
mkdir: cannot create directory 'build': File exists
```

Because Jenkins workspaces persist between builds unless cleaned.

The previous run already created:

```text id="mec5zy"
build/
```

So the next build failed when trying to recreate it.

---

# The Fix

```groovy id="gprn3u"
sh 'mkdir -p build'
```

The `-p` flag means:

> Create the directory only if it does not already exist.

This is called an **idempotent operation**.

Idempotency is extremely important in DevOps.

An idempotent command can run repeatedly without causing failures.

---

# Why `mainboard` Appeared Multiple Times

You observed:

```text id="u7sm7k"
mainboard
mainboard
mainboard
```

This happened because:

```bash id="1b5slr"
>>
```

appends data instead of replacing the file.

Every pipeline execution added another line.

The workspace was reused between builds.

---

# Important Jenkins Workspace Concept

By default, Jenkins does not fully clean the workspace after every run.

So artifacts remain unless explicitly removed.

Typical production pipelines often include cleanup:

```groovy id="p6t2ul"
sh 'rm -rf build'
```

or:

```groovy id="2fv2qn"
cleanWs()
```

using the Workspace Cleanup plugin.

# Why `cat` Was Useful

```groovy id="94h7b7"
sh 'cat build/computer.txt'
```

`cat` displays file contents.

This helped debug and verify pipeline behavior through Jenkins console logs.

In real CI/CD pipelines, logs are one of the primary debugging tools.

# Why Pipelines Matter in DevOps

Without pipelines:

* Developers manually run commands
* Human error increases
* Builds become inconsistent
* Deployments become unreliable

Pipelines provide:

* Repeatability
* Automation
* Traceability
* Standardization
* Scalability

That is why pipelines are central to modern CI/CD systems.
