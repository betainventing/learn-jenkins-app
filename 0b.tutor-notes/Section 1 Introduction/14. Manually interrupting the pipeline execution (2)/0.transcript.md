This section explains how Jenkins handles long-running or stuck jobs and how to manually stop them.

### Normal Pipeline Execution

Earlier jobs completed very quickly:

* Build duration: ~2 seconds
* Artifact creation: ~105 ms

In real environments, builds are often much longer because they may include:

* Source code checkout
* Dependency downloads
* Compilation
* Unit/integration testing
* Docker image builds
* Kubernetes deployments
* Security scanning
* Artifact publishing

---

# Simulating a Long-Running Job

The instructor adds the Linux command:

```bash
sleep 600
```

inside the pipeline.

`sleep` pauses execution for a specified number of seconds.

So:

```bash
sleep 600
```

means:

```text
Pause execution for 10 minutes
```

The pipeline is not frozen or crashed. Jenkins is actively waiting for the command to finish.

---

# Observing a Running Pipeline

After clicking **Build Now**, Jenkins shows:

* Build progress
* Elapsed execution time
* Current stage being executed

Clicking the progress bar opens the **Console Output**.

In the console:

```text
......
```

indicates the process is still running.

At this point the `sleep` command is consuming the build time.

---

# Why Long Jobs Matter

Sometimes a process:

* hangs
* deadlocks
* waits forever
* loses network connectivity
* waits for unavailable resources
* gets stuck in an infinite loop

Examples:

```bash
npm install
docker pull
terraform apply
kubectl rollout status
mvn test
```

may stall indefinitely under certain conditions.

If Jenkins keeps waiting forever:

* executors remain occupied
* other jobs cannot run
* build queues grow
* CI/CD throughput decreases

---

# Jenkins Executors

Jenkins uses **executors** to run builds.

An executor is essentially a worker slot.

Example:

```text
Executor count = 2
```

means Jenkins can run:

* 2 builds simultaneously

If more jobs arrive:

* they enter the build queue

---

# Build Queue

When all executors are busy:

```text
New jobs → Queue
```

The instructor demonstrates this by:

1. Running multiple long pipelines
2. Starting another fast pipeline
3. Seeing Jenkins place it into the queue

This is a common production scenario.

---

# Manually Stopping a Pipeline

Jenkins allows forcefully stopping a running build.

The instructor clicks the:

```text
X
```

button beside the running job.

This sends an interrupt signal to the running process.

Conceptually similar to Linux:

```bash
CTRL+C
```

or:

```bash
kill -SIGINT <pid>
```

Jenkins tells the process:

```text
Stop execution immediately
```

---

# Result of Aborting

After interruption:

* build stops
* queue clears
* executors become free again

The pipeline status changes to:

```text
Aborted
```

or:

```text
Cancelled
```

Console output shows:

```text
Aborted by <user>
```

No artifacts are produced because the pipeline never completed successfully.

---

# Important CI/CD Operational Concept

In real DevOps environments, monitoring stuck pipelines is critical.

Common operational practices include:

## 1. Timeout Configuration

Instead of manual stopping, pipelines often define automatic timeouts.

Example in Jenkins Pipeline:

```groovy
timeout(time: 10, unit: 'MINUTES') {
    sh 'sleep 600'
}
```

If execution exceeds 10 minutes:

* Jenkins aborts automatically

---

## 2. Resource Protection

Preventing stuck jobs protects:

* CPU
* memory
* disk
* executors
* agent nodes

---

## 3. Queue Management

Large organizations may run:

* hundreds
* thousands

of builds daily.

A few stuck pipelines can delay the entire CI/CD system.
