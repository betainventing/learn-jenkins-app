This lecture introduces a very important Jenkins pipeline capability:

# Sharing Dynamic Runtime Data Between Stages

The core problem is:

some values are only known during pipeline execution.

Example from your Netlify workflow:

```text id="jlwma1"
Staging deploy URL
```

does not exist before deployment runs. 

So it cannot be hardcoded beforehand.

---

# Static vs Dynamic Data

## Static Data

Known before pipeline starts.

Examples:

```groovy id="jlwma2"
NODE_ENV=production
PORT=3000
NETLIFY_SITE_ID=abc123
```

These can be declared normally.

---

# Dynamic Data

Generated during execution.

Examples:

* staging URLs
* timestamps
* artifact IDs
* Docker image digests
* Kubernetes pod names
* deployment IDs

These must be computed at runtime.

---

# Why Simple Shell Variables Don’t Work

The instructor says:

> we cannot use a shell script to set that variable and pass it over

This is extremely important.

Many beginners misunderstand this.

---

# Important Pipeline Isolation Concept

Each Jenkins shell step:

```groovy id="jlwma3"
sh '...'
```

runs in its own shell process.

Example:

```groovy id="jlwma4"
sh 'MYVAR=hello'
sh 'echo $MYVAR'
```

Second step will NOT see the variable.

Because processes are isolated.

---

# Why This Happens

Conceptually:

```text id="jlwma5"
Step 1 shell starts
    ↓
Variable created
    ↓
Shell exits
    ↓
Variable destroyed
```

Then:

```text id="jlwma6"
Step 2 starts completely new shell
```

So shell-local variables do not persist between steps/stages.

---

# Solution: Jenkins Environment Object

Instead they use:

```groovy id="’winiwa7"
env.MY_VAR = value
```

This stores data in Jenkins pipeline environment context.

That environment becomes accessible across stages.

---

# Why `script {}` Is Required

The instructor introduces:

```groovy id="jlwma8"
script {
    ...
}
```

This is extremely important in Declarative Pipelines.

---

# Declarative vs Scripted Pipeline

Declarative pipeline syntax is intentionally restrictive.

Example declarative syntax:

```groovy id="jlwma9"
steps {
    sh 'npm test'
}
```

Simple and structured.

---

# But Dynamic Logic Needs Groovy

When you need:

* loops
* conditions
* variable manipulation
* runtime computation
* custom logic

you need:

```groovy id="jlwmb0"
script { }
```

which allows raw Groovy execution.

---

# Important Architectural Detail

Inside:

```groovy id="jlwmb1"
script { }
```

you temporarily switch from:

# Declarative Pipeline DSL

to:

# Groovy scripting

This is a major Jenkins concept.

---

# Setting Variable Example

Example:

```groovy id="’winiwb2"
script {
    env.MY_VAR = "hello"
}
```

Now `MY_VAR` becomes globally accessible later.

---

# Accessing Variable Later

They use:

```groovy id="’winiwb3"
echo "${env.MY_VAR}"
```

---

## `${}`

Groovy string interpolation.

Means:

```text id="’winiwb4"
Insert value dynamically
```

---

# `env`

Refers to Jenkins environment namespace.

---

Access environment variable named:

```text id="’winiwb5"
MY_VAR
```

# Dynamic Command Execution

The instructor then replaces hardcoded value with:

```bash id="’winiwb6"
date
```

Very important evolution.

---

# Why `date` Is Useful Example

Because every execution produces different output.

Meaning:

```text id="’winiwb7"
Truly runtime-generated value
```

---

# Running Shell Commands Inside Groovy

They use:

```groovy id="’winiwb8"
sh(
    script: 'date',
    returnStdout: true
)
```

This is one of the most important Jenkins pipeline patterns.

---

# Important Distinction

Normally:

```groovy id="’winiwb9"
sh 'date'
```

only prints output to logs.

But:

```groovy id="’winiwc0"
returnStdout: true
```

captures output into a variable.

---

# STDOUT Concept

The lecture explains:

# Standard Output (STDOUT)

In Linux/Unix processes:

| Stream | Purpose       |
| ------ | ------------- |
| STDOUT | normal output |
| STDERR | error output  |
| STDIN  | input         |

---

# Example

Command:

```bash id="’winiwc1"
date
```

writes current date to STDOUT.

Normally terminal displays it.

But Jenkins can capture it programmatically.

---

# What `returnStdout: true` Does

Conceptually:

```text id="’winiwc2"
Run shell command
    ↓
Capture stdout
    ↓
Return as string
```

instead of merely printing.

---

# Final Dynamic Assignment

Conceptually:

```groovy id="’winiwc3"
script {
    env.MY_VAR = sh(
        script: 'date',
        returnStdout: true
    ).trim()
}
```

(Usually `.trim()` is also added in real pipelines.)

---

# Why `.trim()` Often Matters

Shell output usually includes newline:

```text id="’winiwc4"
\n
```

Without trimming:

variables may contain hidden line breaks.

This often breaks:

* URLs
* Docker tags
* comparisons
* API calls

Very common real-world issue.

---

# Why This Is Powerful

The instructor correctly says:

> this is super powerful

Because now pipelines can dynamically exchange runtime information.

# Real-World Examples

This pattern is used constantly in DevOps.

---

# Example: Kubernetes Endpoint

```groovy id="’winiwc6"

```

---

# Example: Netlify Deploy URL

Your exact use case:

```groovy id="’winiwc7"
env.STAGING_URL = sh(
    script: "node-jq -r '.deploy_url' deploy-output",
    returnStdout: true
)
```

Then later:

```groovy id="’winiwc8"
CI_ENVIRONMENT_URL = env.STAGING_URL
```

for Playwright tests.

# Major CI/CD Principle

This lecture demonstrates:

# Pipelines are stateful workflows

Stages can exchange runtime-generated metadata dynamically.

That capability is foundational for sophisticated CI/CD systems.

# Biggest Conceptual Takeaway

This lecture teaches how Jenkins pipelines move from:

```text id="’winiwc9"
Static predefined automation
```

to:

```text id="’winiwd0"
Dynamic runtime-aware orchestration
```

by computing values during execution, storing them in the pipeline environment, and reusing them across stages automatically.
