This lecture evolves the pipeline from:

```text id="r10q4e"
Direct production deployment
```

to:

```text id="lrmj0f"
Pre-production deployment validation
```

using temporary staging deployments created automatically by Netlify.



---

# Main Concept

The instructor is implementing:

# Ephemeral Staging Environments

Meaning:

temporary environments dynamically created for validation/testing.

Instead of manually creating:

```text id="y8yjlwm"
staging.myapp.com
```

Netlify automatically generates a temporary deployment URL.

---

# Two Possible Approaches

The lecture compares two strategies.

---

# Option 1 — Permanent Staging Site

Create another Netlify site manually:

```text id="jlwm1x"
production-site
staging-site
```

Then deploy separately to each.

This is common in enterprise systems.

---

# Option 2 — Temporary Preview Deployments

Instead of manually managing another site:

```text id="jlwm2y"
netlify deploy
```

without production flag creates:

# Draft/Preview Deployment

Netlify automatically generates a temporary URL.

The instructor chooses this approach because it demonstrates more advanced deployment workflows.

---

# Key Insight

The production deployment command already existed:

```bash id="9jlwm3"
netlify deploy --dir=build --prod
```

The staging deployment is almost identical:

```bash id="jlwm4z"
netlify deploy --dir=build
```

The only difference:

# removing `--prod`

---

# Why This Works

Netlify CLI behavior changes depending on the presence of:

```bash id="jlwm5a"
--prod
```

---

# With `--prod`

Deployment becomes:

```text id="jlwm6b"
Live production release
```

Updates public production website.

---

# Without `--prod`

Deployment becomes:

```text id="jlwm7c"
Draft/preview deployment
```

Netlify creates:

* temporary environment
* unique URL
* isolated deployment version

without replacing production.

---

# Extremely Important Deployment Principle

This demonstrates:

# Same artifact, different target environment

The exact same build artifacts are used:

```text id="jlwm8d"
build/
```

Only deployment destination changes.

This is ideal CI/CD design.

---

# Why This Is Valuable

Now pipeline becomes:

```text id="jlwm9e"
Build
   ↓
Deploy to staging
   ↓
Validate staging
   ↓
Deploy to production
```

instead of:

```text id="0jlwmf"
Build
   ↓
Deploy directly to production
```

This greatly reduces deployment risk.

---

# Draft URL

The logs show something like:

```text id="1jlwmg"
Draft URL:
https://random-id--site.netlify.app
```

This is an automatically generated preview deployment.

---

# Why Random URLs Exist

Netlify uses unique identifiers to isolate deployments.

This allows:

* multiple preview deployments
* independent testing
* temporary environments
* deployment history

without overwriting production.

---

# Important Observation

The instructor says:

> "It is publicly accessible, but only we know it"

Meaning:

these are not truly private environments.

They are:

# Security-through-obscurity preview URLs

Anyone with the URL can access them.

But the URLs are difficult to guess.

---

# Important Real-World Caveat

In enterprise systems, true staging environments usually add:

* authentication
* VPN
* IP restrictions
* SSO
* private networking

because obscurity alone is not sufficient security.

---

# Why The Commands Are Nearly Identical

This is intentional.

A major DevOps best practice is:

# Keep deployment workflows identical across environments

Meaning:

```text id="2jlwmh"
same build
same scripts
same deployment tooling
same infrastructure patterns
```

Only configuration changes.

This minimizes:

* environment drift
* deployment surprises
* staging/production inconsistencies

# Important CI/CD Architecture

At this point pipeline is becoming:

# Multi-environment deployment pipeline

# Critical Remaining Problem

The instructor identifies an important issue.

Even though staging exists:

```text id="6jlwml"
deploy staging
```

still only verifies:

* deployment command succeeded
* upload completed
* no CLI errors occurred

It does NOT yet verify:

* correct application deployed
* functionality works
* UI behaves correctly
* expected version running

---

# Example Failure Scenario

Imagine:

```text id="7jlwmm"
Wrong build directory
Wrong branch
Corrupted assets
Incorrect application
```

Deployment may still succeed technically.

Meaning:

```text id="8jlwmn"
Deployment success
≠
Application correctness
```

This is extremely important.

---

# What Is Missing

The missing piece is:

# Automated staging validation

Meaning:

```text id="9jlwmo"
Deploy staging
    ↓
Run E2E tests against staging
    ↓
If tests pass:
    deploy production
Else:
    stop pipeline
```

This is likely what upcoming lectures will implement.

---

# This Is Approaching Real Deployment Gating

The pipeline is evolving toward:

# Deployment Gates

A deployment gate is:

```text id="0jlwmp"
Condition that must pass before promotion
```

Example gates:

* unit tests
* security scans
* integration tests
* staging E2E tests
* approvals

Only after passing gates can software reach production.

---

# Important DevOps Principle

Production deployment should be:

# The final step, not the testing step.

Staging exists to reduce uncertainty before public release.

---

# Ephemeral Environments

This lecture also introduces another modern DevOps concept:

# Ephemeral Infrastructure

Meaning:

temporary environments dynamically created and discarded.

This is common with:

* preview deployments
* Kubernetes namespaces
* PR environments
* review apps
* feature branch deployments

---

# Real-World Advanced Pattern

Modern platforms often create:

```text id="1jlwmq"
One temporary environment per pull request
```

allowing:

* QA testing
* stakeholder review
* isolated validation

before merge/deployment.

Platforms commonly used:

* Netlify
* Vercel
* Kubernetes
* Heroku Review Apps
* GitLab Review Apps

---

# Biggest Conceptual Takeaway

This lecture teaches a critical deployment evolution:

# Instead of testing after production deployment, deploy first to a production-like temporary environment and validate there before releasing publicly.

That is one of the foundational safety mechanisms in mature CI/CD systems.
