# Core Deployment Command

The important command becomes:

```bash id="m8ulsi"
netlify deploy --dir=build --prod
```

This is the heart of the deployment stage.

---

# Breaking Down the Command

## 1. `netlify deploy`

This tells the Netlify CLI:

```text id="r7zj4q"
Upload and deploy a website
```

Internally this triggers API communication with Netlify servers.

---

# 2. `--dir=build`

This is extremely important.

```bash id="9xkgpb"
--dir=build
```

means:

> deploy the contents of the `build/` directory

Netlify does NOT build your application automatically in this pipeline.

The build already happened earlier.

Typically:

```bash id="o3kjy7"
npm run build
```

generated static files into:

```text id="4l2r5v"
build/
```

Examples inside build directory:

```text id="8k2gqg"
index.html
static/js/*
static/css/*
assets/*
```

These are production-ready frontend artifacts.

---

# Why Netlify Needs `--dir`

Netlify CLI cannot guess:

* which folder contains production assets
* whether you use:

  * build/
  * dist/
  * out/
  * public/
  * target/

Different frameworks use different output directories.

Examples:

| Framework             | Output Directory |
| --------------------- | ---------------- |
| React                 | build            |
| Vue                   | dist             |
| Angular               | dist             |
| Next.js static export | out              |
| Vite                  | dist             |

So the deploy command must explicitly specify the artifact location.

---

# Relative Path vs Absolute Path

They wrote:

```bash id="zqj4qf"
--dir=build
```

This is a relative path.

Inside Jenkins workspace it becomes something like:

```text id="r26of0"
/var/lib/jenkins/workspace/project/build
```

The CLI resolves the relative path automatically based on current working directory.

---

# 3. `--prod`

This flag is also critical.

```bash id="teajhc"
--prod
```

means:

> deploy directly to the production website

Without this flag, Netlify usually creates:

* preview deploy
* draft deploy
* temporary deployment URL

instead of replacing the live site.

---

# Difference Between Preview vs Production Deployments

| Deployment Type | Purpose             |
| --------------- | ------------------- |
| Preview         | testing/review      |
| Production      | live public website |

---

Without:

```bash id="4mkr8j"
--prod
```

you might get:

```text id="j4qmqw"
random-preview-url.netlify.app
```

With:

```bash id="wmy3of"
--prod
```

the real production domain updates.

# Important CI/CD Principle

This lecture demonstrates:

# Artifact-Based Deployment

Meaning:

```text id="5tnt6h"
Source Code
    ↓
Build Stage
    ↓
Artifacts Generated
    ↓
Deploy Artifacts
```

This is a major industry pattern.

Production systems usually deploy:

* compiled binaries
* containers
* static assets
* immutable artifacts

NOT raw source code.

---

# What Happens Internally During Deployment

Conceptually:

```text id="g61j29"
Jenkins pipeline starts
        ↓
npm build generates build/
        ↓
Jenkins injects Netlify token
        ↓
Netlify CLI authenticates
        ↓
CLI scans build/ directory
        ↓
CLI uploads files to Netlify CDN
        ↓
Netlify processes deployment
        ↓
Production site updated
```

# Why Static Deployments Are Fast

Frontend frameworks often produce static assets.

Netlify can then:

* cache globally
* distribute via CDN
* serve directly from edge locations
* avoid backend runtime execution

This makes deployments:

* cheap
* scalable
* fast

# Why Pipelines Can Succeed Even When App Is Broken

A deployment tool only checks:

* upload succeeded
* API returned success
* files transferred

It does NOT guarantee:

* frontend renders
* API endpoints work
* JS bundle valid
* runtime logic correct

This distinction is extremely important in DevOps.
