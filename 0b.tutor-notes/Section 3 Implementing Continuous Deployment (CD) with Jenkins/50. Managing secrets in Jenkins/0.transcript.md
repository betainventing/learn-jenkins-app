This section is about **authentication and secret management** in CI/CD.

The instructor is solving this problem:

* Jenkins can run the `netlify` CLI.
* Jenkins knows *which* Netlify site to deploy to (`NETLIFY_SITE_ID`).
* But Jenkins still has **no permission** to deploy.

Because identifying a site and authenticating to an account are two different things.

---

# Core Concept

Deployment requires **authorization**.

Without authentication, anyone who knows your Site ID could attempt deployments.

So Netlify requires proof that:

* the request is coming from an authorized account
* the CLI has permission to act on behalf of that account

That proof is the **Personal Access Token (PAT)**.

---

# Why Use a Token Instead of Username/Password

The instructor compares the token to a temporary password.

That is mostly correct conceptually, but technically:

* a token is usually an API credential
* designed specifically for automation and programmatic access

In CI/CD systems, tokens are preferred because:

| Username/Password          | Token                      |
| -------------------------- | -------------------------- |
| Designed for humans        | Designed for automation    |
| Often broad account access | Can be scoped/limited      |
| Harder to rotate safely    | Easy to revoke/regenerate  |
| May require MFA            | CLI can use token directly |
| Dangerous in scripts       | Standard for CI/CD         |

---

# Security Principle Being Applied

This lecture demonstrates a major DevOps principle:

## Never hardcode secrets into source control

That means:

* no passwords in Git
* no tokens in Jenkinsfile
* no API keys in Dockerfiles
* no secrets in environment files committed to GitHub

Because:

* repositories are copied everywhere
* pipelines expose logs
* contributors may gain access
* leaked secrets can compromise infrastructure

---

# Why Environment Variables Alone Are Not Enough

Earlier they stored:

```bash
NETLIFY_SITE_ID
```

as an environment variable.

That is NOT sensitive.

A Site ID only identifies the target site.

It does not authorize deployments.

Think of it like:

| Item    | Purpose              |
| ------- | -------------------- |
| Site ID | Which site           |
| Token   | Permission to deploy |

---

# What the Netlify Token Actually Does

The generated token allows:

```bash
netlify deploy
```

to authenticate with Netlify servers.

Internally, the CLI sends the token with API requests.

Netlify validates:

* token exists
* token not expired
* token belongs to valid account
* token has required permissions

If valid:
deployment proceeds.

If invalid:
deployment denied.

---

# Why Expiration Matters

The instructor recommends 30–60 day expiration.

This is part of:

# Credential Rotation

Meaning:

* old credentials regularly expire
* compromised credentials become useless after some time
* reduces long-term attack surface

This is standard security practice.

# Important Jenkins Concept

The instructor says:

> "Secrets have their own place in Jenkins"

This is extremely important.

---

# Jenkins Credentials Store

Jenkins has a dedicated encrypted credential system.

Location:

```text
Manage Jenkins
→ Credentials
```

This is separate from:

* Jenkinsfile
* build logs
* Git repository
* environment configs

---

# Why Not Store Secret in Jenkinsfile

This would be bad:

```groovy
environment {
    NETLIFY_TOKEN = "abcd1234"
}
```

Because:

* Jenkinsfile is usually committed to Git
* everyone with repo access sees it
* logs may expose it
* pull requests may expose it
* attackers scanning GitHub can steal it

This is a very common real-world breach source.

---

# Why "Secret Text"

Jenkins supports multiple credential types:

| Type              | Use Case     |
| ----------------- | ------------ |
| Username/Password | Login pairs  |
| SSH Key           | Git SSH auth |
| Secret File       | Certificates |
| Secret Text       | API tokens   |

Netlify token is just a string.

So:

```text
Secret Text
```

is the correct choice.

---

# Scope = Global

They selected:

```text
Global
```

Meaning:

all Jenkins jobs/pipelines can access this credential.

Alternative scopes may restrict visibility.

---

# Credential ID

They used:

```text
netlify-token
```

(or similar)

This ID is critical.

Because pipelines reference credentials using this ID.

Example:

```groovy
environment {
    NETLIFY_AUTH_TOKEN = credentials('netlify-token')
}
```

Jenkins then:

* securely injects secret into runtime
* masks it in logs
* avoids exposing raw value

---

# Very Important Security Behavior

The instructor mentions:

> the value cannot be revealed later

This is intentional.

Jenkins stores secrets encrypted and masked.

Even admins often cannot directly read them from UI.

This reduces accidental exposure.

---

# What Happens During Deployment

Typical flow:

```text
Developer pushes code
        ↓
Jenkins pipeline starts
        ↓
Jenkins retrieves token from credentials store
        ↓
Injects token into runtime environment
        ↓
Netlify CLI uses token
        ↓
Netlify API validates token
        ↓
Deployment succeeds
```

---

# Typical Jenkins Pipeline Example

This is usually what comes next:

```groovy
pipeline {
    agent any

    environment {
        NETLIFY_SITE_ID = 'xxxx'
        NETLIFY_AUTH_TOKEN = credentials('netlify-token')
    }

    stages {
        stage('Deploy') {
            steps {
                sh 'netlify deploy --prod'
            }
        }
    }
}
```

# Important Distinction

There are two different categories of variables now:

| Variable           | Sensitive? | Storage Location     |
| ------------------ | ---------- | -------------------- |
| NETLIFY_SITE_ID    | No         | Environment variable |
| NETLIFY_AUTH_TOKEN | Yes        | Jenkins Credentials  |

This separation is extremely common in DevOps.
