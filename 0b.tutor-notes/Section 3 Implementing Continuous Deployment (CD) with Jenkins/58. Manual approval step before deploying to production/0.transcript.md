This lecture introduces another major CI/CD deployment control mechanism:

# Manual Approval Gates

The problem being solved is:

Even after:

* automated build
* automated tests
* staging deployment
* staging validation

organizations may still want:

# Human verification before production deployment



---

# Why Manual Approval Exists

Sometimes deployment is technically correct but still requires business approval.

Examples:

* manager review
* stakeholder signoff
* QA acceptance
* compliance verification
* scheduled release windows
* marketing coordination
* legal approval

So pipelines sometimes intentionally pause before production.

---

# Deployment Gate Concept

This lecture introduces:

# Approval Gates

Meaning:

```text id="jlwm0a"
Pipeline pauses
    ↓
Human decides:
    proceed OR abort
```

This is extremely common in enterprise CI/CD.

---

# Important Engineering Lesson

The instructor recommends creating tiny experimental pipelines.

This is valuable because production pipelines often:

* take long time
* contain many dependencies
* are hard to debug
* are expensive to run

Small isolated experiments improve understanding much faster.

This is good DevOps workflow design.

# Jenkins `input` Step

The core feature used is:

```groovy id="jlwm2c"
input
```

This creates an interactive pause in the pipeline.

Example:

```groovy id="jlwm3d"
input message: 'Ready to deploy?'
```

---

# What Happens Internally

Pipeline execution flow becomes:

```text id="jlwm4e"
Build stage executes
      ↓
Pipeline enters WAITING state
      ↓
Jenkins UI displays approval dialog
      ↓
User chooses:
   Proceed OR Abort
```

---

# Important Architectural Detail

The pipeline is not finished.

It is:

# Suspended

Jenkins persists pipeline execution state internally.

This is one advantage of Jenkins Pipeline architecture.

---

# Pipeline Persistence

Modern Jenkins pipelines can survive:

* pauses
* restarts
* waiting states
* human interaction

because pipeline state is serialized internally.

This is much more advanced than simple shell scripts.

---

# Proceed vs Abort

The UI offers:

| Option  | Result            |
| ------- | ----------------- |
| Proceed | continue pipeline |
| Abort   | stop pipeline     |

---

# Abort Behavior

The instructor highlights something important:

Aborted pipeline is NOT marked failed.

Status becomes:

```text id="jlwm5f"
ABORTED
```

instead of:

```text id="jlwm6g"
FAILED
```

This distinction matters operationally.

---

# Why Aborted ≠ Failed

Failure means:

```text id="jlwm7h"
Something broke unexpectedly
```

Abort means:

```text id="jlwm8i"
Human intentionally stopped execution
```

These are different operational states.

---

This is extremely important in enterprise environments.

Because organizations often require:

* deployment accountability

* approval history

Especially in:

# Important Operational Problem

The instructor then identifies a major issue:

Without limits:

```text id="1jlwml"
Pipeline waits forever
```

This is bad operationally.

---

# Why Infinite Waiting Is Dangerous

Suspended pipelines consume resources:

* executor state
* pipeline metadata
* queue complexity
* operational confusion

Additionally:

* deployments may become stale
* approvals forgotten
* outdated builds accidentally deployed later

---

# Solution: Timeout

The instructor wraps input inside:

```groovy id="2jlwmm"
timeout(...)
```

This is another important Jenkins construct.

---

# Timeout Concept

Meaning:

```text id="3jlwmn"
Wait only limited amount of time
```

Example:

```groovy id="4jlwmo"
timeout(time: 1, unit: 'HOURS') {
    input ...
}
```

---

# Execution Flow With Timeout

Now pipeline becomes:

```text id="5jlwmp"
Enter approval stage
      ↓
Wait for approval
      ↓
If approved before timeout:
    continue
Else:
    abort automatically
```

---

# Why This Is Better

This prevents:

* abandoned deployments
* hanging pipelines
* stale approvals
* forgotten execution states

This is much safer operationally.

---

# Important Readability Advice

The instructor recommends:

```groovy id="6jlwmq"
unit: 'MINUTES'
```

instead of relying on implicit defaults.

This is excellent advice.

---

# Why Explicit Configuration Matters

Bad:

```groovy id="7jlwmr"
timeout(time: 1)
```

Unclear meaning later.

Good:

```groovy id="8jlwms"
timeout(time: 1, unit: 'MINUTES')
```

Self-documenting.

This is maintainability-oriented pipeline design.

---

# What Happens On Timeout

If timeout expires:

* pipeline aborts automatically
* deployment never occurs
* logs show timeout interruption

This protects production.

# Important Real-World CI/CD Pattern

This lecture introduces:

# Controlled Promotion

Meaning:

```text id="9jlwmt"
Build artifact
      ↓
Validated in staging
      ↓
Human approves
      ↓
Promoted to production
```

This is extremely common in enterprise delivery systems.

---

# Typical Enterprise Pipeline

Real pipelines often resemble:

```text id="0jlwmu"
Build
   ↓
Unit Tests
   ↓
Integration Tests
   ↓
Security Scans
   ↓
Deploy Staging
   ↓
E2E Tests
   ↓
Manual Approval
   ↓
Deploy Production
```

---

# Important DevOps Tradeoff

Fully automated deployment is not always the goal.

Sometimes organizations intentionally prefer:

# Continuous Delivery

instead of:

# Continuous Deployment

Difference:

| Model                 | Production Deployment       |
| --------------------- | --------------------------- |
| Continuous Deployment | automatic                   |
| Continuous Delivery   | manual approval before prod |

---

# Why Enterprises Often Prefer Approval Gates

Reasons include:

* risk management
* compliance
* release coordination
* human oversight
* business timing
* rollback planning

---

# Important Scaling Observation

As organizations mature, approvals often move from:

```text id="1jlwmv"
Click button in Jenkins
```

to more advanced systems:

* GitOps approvals

* ChatOps approvals

But conceptually the idea remains the same.

---

# Biggest Conceptual Takeaway

This lecture teaches that mature CI/CD pipelines are not merely about automation.

They are also about:

# Controlled release management

where deployments can be intentionally paused, reviewed, approved, timed out, and promoted safely before reaching production.
