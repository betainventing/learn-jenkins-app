This lecture completes the implementation of a:

# Production Deployment Approval Gate

inside the real Jenkins CI/CD pipeline.

The final deployment flow now becomes:

```text id="jlwmz1"
Build
   ↓
Test
   ↓
Deploy Staging
   ↓
Manual Approval
   ↓
Deploy Production
```

This is a major step toward enterprise-style release management.

---

# Stage Placement Is Important

The instructor correctly inserts:

```groovy id="jlwmz2"
stage('Approval')
```

between:

```text id="jlwmz3"
Deploy Staging
```

and:

```text id="jlwmz4"
Deploy Production
```

This positioning matters because staging must already exist before humans review it.

---

# What The Approval Stage Is Doing

Core logic:

```groovy id="jlwmz5"
input(
    message: 'Do you wish to deploy to production?',
    ok: 'Yes, I am sure'
)
```

This causes Jenkins to:

* suspend pipeline execution
* wait for human interaction
* present approval dialog in UI

---

# Important Operational Meaning

At this point the pipeline has already:

* built application
* tested application
* deployed staging version

So reviewers can now:

* open staging site
* validate behavior
* inspect UI
* verify business requirements
* decide whether production deployment is acceptable

This is exactly the purpose of staging environments.

---

# Why The Message Matters

The instructor uses:

```text id="jlwmz6"
Danger approving this will result in deployment to production
```

This is actually good operational design.

Production deployment prompts should be explicit because production actions are high impact.

Good pipelines reduce accidental approvals.

---

# Important Pipeline State

When approval stage is reached:

```text id="jlwmz7"
Pipeline pauses
```

The pipeline is neither:

* failed
* completed

It is:

# Waiting for input

Internally Jenkins persists pipeline state.

# Timeout Implementation

The instructor then improves the design by adding:

```groovy id="jlwmz8"
timeout(time: 15, unit: 'MINUTES')
```

around the input block.

Final structure conceptually becomes:

```groovy id="jlwmz9"
timeout(time: 15, unit: 'MINUTES') {
    input(
        message: 'Do you wish to deploy to production?',
        ok: 'Yes, I am sure'
    )
}
```

---

# Why Timeout Wraps Input

This is critical structurally.

Correct:

```text id="0jlwza"
timeout {
    input
}
```

Meaning:

```text id="1jlwzb"
Input must complete within timeout window
```

---

# Wrong Structure

If timeout and input are separate:

```text id="2jlwzc"
timeout
input
```

the timeout does not control the approval wait.

So nesting matters.

---

# Important Jenkins Syntax Concept

Jenkins Pipeline is heavily block-oriented.

Meaning indentation and nesting determine execution behavior.

The instructor emphasizes this correctly.

---

# Why 15 Minutes

The timeout defines:

# Approval validity window

After 15 minutes:

* pipeline aborts automatically
* production deployment canceled
* stale deployments prevented

---

# Important Operational Reasoning

This prevents situations like:

```text id="3jlwzd"
Friday evening deployment waiting
    ↓
Nobody approves
    ↓
Monday morning someone accidentally deploys outdated build
```

Timeouts reduce stale-release risk.

---

# Explicit Units Matter

The instructor intentionally changes:

```groovy id="4jlwze"
unit: 'HOURS'
```

to:

```groovy id="5jlwzf"
unit: 'MINUTES'
```

instead of relying on defaults.

This is excellent maintainability practice.

---

# Why Explicit Configuration Is Better

Future engineers reading:

```groovy id="6jlwzg"
timeout(time: 15)
```

may not know:

* seconds?
* minutes?
* hours?

Explicit units remove ambiguity.

# Important Enterprise CI/CD Pattern

The pipeline now effectively implements:

# Promotion-Based Deployment

Meaning:

```text id="7jlwzh"
Artifact promoted from staging → production
```

instead of directly deploying from source changes.

---

# What “Promotion” Means

The already-tested artifact becomes eligible for production release.

This is much safer than rebuilding separately for production.
