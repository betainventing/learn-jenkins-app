# Why manual approval steps exist

A manual approval stage is essentially a controlled checkpoint before production deployment.

Typical Jenkins example:

```groovy id="s8p43n"
stage('Approval') {
    steps {
        input 'Deploy to production?'
    }
}
```

Pipeline pauses until:

* a user approves
* or rejects/cancels deployment

# 1. Quality assurance (QA)

Even with automated testing:

* some issues are difficult to validate automatically.

Examples:

* UI alignment problems
* branding mistakes
* incorrect marketing text
* visual regressions
* accessibility issues
* broken layouts on specific devices
* incorrect pricing/content

Automated tests are typically very good at:

* functional validation
* API validation
* regression detection

But weaker at:

* business correctness
* visual judgment
* customer perception

Example:

```text
all tests pass
but homepage banner shows wrong promotion
```

Technically:

```text
system is functionally correct
business outcome is incorrect
```

# 2. Risk management

Production deployments always carry operational risk.

Possible impacts:

* downtime
* payment failures
* broken login systems
* degraded performance
* customer churn
* revenue loss

Manual approval acts as:

```text
a deliberate operational pause
```

Purpose:

* confirm readiness
* verify monitoring
* confirm rollback availability
* ensure support teams are informed
* verify deployment timing

Example:

```text
do not deploy during peak sales hours
```

Very common in:

* banking
* telecom
* healthcare
* e-commerce

* separation of duties

# Continuous Delivery

The transcript defines the current pipeline as:

```text
fully automated pipeline with optional human release approval
```

This is:

## Continuous Delivery

Definition:

```text
software is always deployable
```

Meaning:

* build is automated
* testing is automated
* deployment process is automated
* release requires approval

Key characteristic:

```text
production-ready artifact always exists
```

Deployment can happen:

```text
immediately with minimal effort
```

but still requires:

```text
human decision
```

Pipeline flow:

```text
commit
→ build
→ test
→ deploy staging
→ validate
→ approval
→ production
```

---

# Continuous Deployment

Continuous Deployment removes the approval gate.

Pipeline flow:

```text
commit
→ build
→ test
→ deploy automatically to production
```

No human intervention.

Requirement:

```text
extremely high confidence in automation
```

This requires:

* strong automated testing
* monitoring
* observability
* rollback systems
* deployment safety mechanisms

---

# Important distinction

Many people confuse these:

| Practice              | Production deployment |
| --------------------- | --------------------- |
| Continuous Delivery   | Manual trigger        |
| Continuous Deployment | Automatic             |

Core difference:

```text
human approval exists or not
```

# Safeguards required for Continuous Deployment

The transcript mentions rollback mechanisms.

This is critical.

Continuous Deployment requires safety systems such as:

## 1. Rollbacks

If deployment fails:

```text
automatically revert previous version
```

Examples:

* Kubernetes rollout undo
* blue-green rollback
* artifact redeployment

---

## 2. Canary deployments

Deploy to:

```text
small subset of users first
```

If healthy:

```text
expand rollout
```

---

## 3. Feature flags

Deploy code:

```text
without enabling feature
```

Then enable gradually.

Very common in modern SaaS systems.

---

## 4. Health monitoring

Systems automatically check:

* latency
* errors
* crash rates
* CPU/memory
* business KPIs

---

## 5. Automatic deployment halting

If metrics degrade:

```text
stop rollout automatically
```

# Core DevOps philosophy shown here

The transcript demonstrates an important DevOps principle:

```text
deployment frequency increases as deployment risk decreases
```

To reduce risk:

* automate validation
* standardize releases
* improve observability
* improve rollback capability
* reduce deployment size
* increase confidence

Eventually:

```text
deployments become routine instead of stressful
```

That is one of the central goals of mature DevOps engineering.
