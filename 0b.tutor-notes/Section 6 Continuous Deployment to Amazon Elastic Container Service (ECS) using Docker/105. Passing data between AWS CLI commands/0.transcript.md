# Eliminating Manual ECS Revision Management

The previous pipeline still had an important weakness:

```text id="jlwm58"
Task Definition Revision Had To Be Updated Manually
```

Example:

```bash id="jlwm59"
--task-definition my-task:2
```

Hardcoding revision numbers creates operational problems:

* Error-prone
* Difficult to maintain
* Poor automation design



---

# The Core Problem

Each time a new task definition is registered:

```text id="jlwm60"
Revision Number Increases Automatically
```

Example progression:

| Deployment | Revision |
| ---------- | -------- |
| First      | 1        |
| Second     | 2        |
| Third      | 3        |
| Fourth     | 4        |

Manually tracking this inside Jenkins is fragile.

---

# Goal of the Improvement

The lecture improves automation by:

```text id="jlwm61"
Read New Revision Automatically
↓
Store In Variable
↓
Use Variable In update-service Command
```

This removes manual revision synchronization entirely.

---

# Key Observation

The command:

```bash id="jlwm62"
aws ecs register-task-definition
```

returns a JSON response.

Inside that JSON:

* ECS already provides the revision number.



---

# Example JSON Structure

Conceptually:

```json id="jlwm63"
{
  "taskDefinition": {
    "revision": 4
  }
}
```

The revision information already exists.
The pipeline only needs to extract it.

---

# Introducing JQ

The solution uses jq.

`jq` is a command-line JSON parser frequently used in:

* DevOps
* Shell scripting
* CI/CD automation
* API response processing

---

# Why JQ Is Important

Modern cloud tooling frequently returns:

* JSON responses

Examples:

* AWS CLI
* Kubernetes APIs
* Terraform outputs
* REST APIs

`jq` is one of the standard tools for processing that data.

---

# Installing JQ

The container image uses:

* Amazon Linux

So package installation uses:

```bash id="jlwm64"
yum install jq -y
```



---

# Yum Package Manager

`yum` is common in:

* Red Hat Enterprise Linux
* CentOS
* Amazon Linux

Equivalent idea to:

* `apt`
* `dnf`

for RPM-based distributions.

---

# Why `-y` Is Used

The flag:

```bash id="jlwm65"
-y
```

automatically answers:

* Yes

to installation prompts.

Important for:

* Non-interactive CI/CD pipelines

---

# Piping AWS Output into JQ

The AWS CLI JSON output is piped into jq:

```bash id="jlwm66"
| jq '.taskDefinition.revision'
```

This extracts:

```text id="jlwm67"
taskDefinition → revision
```

from the JSON structure.



---

# Understanding the JQ Query

Expression:

```bash id="jlwm68"
.taskDefinition.revision
```

means:

1. Go into `taskDefinition`
2. Read `revision`

Very similar to object traversal in programming languages.

---

# Command Substitution

The lecture then introduces shell command substitution:

```bash id="jlwm69"
$(command)
```

This executes:

* The command inside parentheses

and returns:

* Its output

---

# Variable Assignment

The revision gets stored in a variable:

```bash id="jlwm70"
LATEST_TD_REVISION=$(...)
```

Now the pipeline dynamically knows:

* Which revision was just created

without hardcoding numbers.

---

# Debugging with Echo

Temporary debugging step:

```bash id="jlwm71"
echo $LATEST_TD_REVISION
```

Useful for:

* Verifying pipeline behavior
* Troubleshooting shell scripts

---

# Dynamic Service Update

Now the ECS update command becomes:

```bash id="jlwm72"
--task-definition my-task:$LATEST_TD_REVISION
```

The deployment becomes fully dynamic.

---

# Major Automation Improvement

Earlier approach:

```text id="jlwm73"
Manual Revision Tracking
```

New approach:

```text id="jlwm74"
Automatic Revision Discovery
```

This is much closer to real CI/CD pipeline design.

# First Failure — Permission Denied

The pipeline initially failed installing jq.

Error:

```text id="jlwm75"
You need to be root
```

because package installation requires elevated privileges.



---

# Why Root Was Required

Installing packages modifies:

* System binaries
* Package database
* OS filesystem

Normal users cannot perform these operations.

---

# Fix — Run Container as Root

Docker argument added:

```text id="jlwm76"
-u root
```

This runs the container process as:

* Root user

allowing package installation.

---

# Why This Was Acceptable Here

The lecture notes:

* Workspace ownership was not critical
* No file permission side effects mattered

So temporary root usage was acceptable.

---

# Successful Pipeline Behavior

After the fix:

1. jq installed
2. Task definition registered
3. Revision extracted dynamically
4. Service updated automatically

Pipeline now works end-to-end.

---

# Example Result

Pipeline logs showed:

```text id="jlwm77"
Latest revision = 4
```

Then ECS service update used:

* Revision 4 automatically

without modifying the Jenkinsfile.
