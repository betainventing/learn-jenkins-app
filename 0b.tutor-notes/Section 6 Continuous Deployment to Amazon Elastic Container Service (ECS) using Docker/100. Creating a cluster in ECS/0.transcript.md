# First ECS Deployment Example — Running Nginx

This lecture introduces the first practical use of Amazon Elastic Container Service using a very simple containerized application:

* NGINX

The goal is not to build a complex application yet.
The goal is to understand ECS fundamentals first.

---

# Why Nginx Is Used

Nginx is extremely popular in production systems.

Common uses:

* Web server
* Reverse proxy
* Load balancer
* Static file server
* API gateway

Even though the default Nginx page looks simple, Nginx itself is heavily used across modern infrastructure.

---

# Docker Hub Usage

The lecture uses an existing Nginx container image from Docker Hub.

Docker Hub is a public container registry.

It stores:

* Prebuilt Docker images
* Versioned application containers

Instead of building a custom image immediately, the course uses:

* Official Nginx image

This simplifies initial ECS learning.

---

# Why This Matters

Because the image already exists:

```text id="z5y5f9"
No Dockerfile
No Build Step
No Custom Packaging
```

You can focus entirely on:

* ECS concepts
* Container deployment flow

---

# ECS Starting Point

At this stage:

* ECS cluster exists
* No workloads running

Meaning:

```text id="3x2xvv"
Cluster Infrastructure Exists
But No Containers Are Executing
```

---

# Creating the ECS Cluster

The first operational step is:

* Create Cluster

Example cluster name:

```text id="9yzbko"
learn-jenkins-app-cluster-prod
```

---

# Naming Convention Importance

The naming convention demonstrates a real-world practice.

Components of the name:

| Part                | Meaning             |
| ------------------- | ------------------- |
| `learn-jenkins-app` | Application/project |
| `cluster`           | Resource type       |
| `prod`              | Environment         |

This becomes important in large organizations managing:

* Multiple applications
* Multiple environments
* Multiple AWS accounts

---

# Environment Separation

The lecture briefly introduces an important DevOps principle:

## Separate Environments

Typical environments:

| Environment | Purpose                   |
| ----------- | ------------------------- |
| Dev         | Developer experimentation |
| Test        | Validation/testing        |
| Stage       | Pre-production            |
| Prod        | Real users                |

Using separate ECS clusters improves:

* Isolation
* Security
* Stability
* Operational safety

---

# Why Shared Clusters Can Be Risky

If testing and production share the same cluster:

* Resource contention may occur
* Testing failures may affect production
* Accidental deployments become more dangerous

Production isolation is a standard operational practice.

---

# Infrastructure Selection

The cluster uses:

* AWS Fargate

instead of EC2-backed ECS.

---

# Why Fargate Is Chosen

Fargate simplifies:

* Provisioning
* Capacity management
* Infrastructure maintenance

You do NOT manage:

* EC2 servers
* Docker hosts
* OS patching

This accelerates learning and deployment.

---

# Cluster Creation Simplicity

Cluster creation only requires:

1. Cluster name
2. Infrastructure type

Then:

* Create cluster

This simplicity is intentional.

AWS abstracts away most infrastructure complexity.

---

# Important Architectural Observation

After creation:

```text id="k3l2hg"
Cluster Exists
But Nothing Runs Yet
```

An ECS cluster alone does not consume significant runtime resources if:

* No tasks are running

This is important financially.

---

# ECS Resource Lifecycle

ECS architecture flow:

```text id="48kjlwm"
Cluster
   ↓
Task Definition
   ↓
Task
   ↓
Running Container
```

At this stage only:

* Cluster exists

The application deployment has not happened yet.

---

# What Is Missing Now?

The cluster still needs:

* Task definition
* Container configuration
* Runtime execution

Only after tasks run:

* Containers execute
* CPU/memory are consumed
* Billing increases

---

# Real Infrastructure Analogy

Think of the cluster like:

```text id="tqjlwm"
An Empty Factory Building
```

The building exists, but:

* No workers
* No machines
* No production

Tasks are what actually perform work.

---

# Key Learning Objective

This lecture isolates one important ECS idea:

```text id="n2r6c1"
Infrastructure Environment First
Application Execution Second
```

That separation is foundational in container orchestration platforms.

---

# Practical DevOps Relevance

This deployment pattern mirrors real production systems:

```text id="bjlwm4"
Container Image
→ Registry
→ ECS Cluster
→ Task Definition
→ Running Service
```

These same architectural ideas later appear in:

* Kubernetes
* EKS
* OpenShift
* Nomad
* Docker Swarm

ECS is often one of the easiest entry points into container orchestration concepts.
