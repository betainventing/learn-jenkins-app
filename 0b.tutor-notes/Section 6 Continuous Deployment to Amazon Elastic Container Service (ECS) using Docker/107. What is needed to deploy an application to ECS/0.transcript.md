# Transition from Public Images to Your Own Application

Until now, the ECS deployment used:

* Public NGINX container image from Docker Hub.

That helped simplify learning:

* ECS concepts
* Services
* Task definitions
* Deployments

But real deployments usually require:

* Your own application image

Amazon Elastic Container Service only runs:

* Docker container images

It cannot directly deploy:

* Loose website files
* Source code folders
* Build artifacts alone

---

# Important Architectural Shift

Earlier deployment:

```text id="jlwm100"
Static Files → S3
```

Current deployment:

```text id="jlwm101"
Docker Image → ECS
```

This is a major transition from:

* File deployment
  to
* Container deployment

---

# Why ECS Requires Docker Images

ECS is a container orchestration platform.

It expects:

* Immutable container images

not:

* Raw application files

A container image contains:

* Application
* Runtime
* Dependencies
* Web server
* Startup configuration

all bundled together.

---

# Step 1 — Create a Dockerfile

The first new requirement:

* Create a `Dockerfile`

A Dockerfile defines:

* How the image should be built

Conceptually:

```text id="jlwm102"
Dockerfile = Recipe For Building Container Image
```

---

# What a Dockerfile Usually Defines

Typical contents:

* Base image
* File copying
* Dependency installation
* Port exposure
* Startup commands

For a static website:

* Nginx may still be used internally
* Website files copied into Nginx image

---

# Step 2 — Build the Docker Image

After creating the Dockerfile:

```bash id="’wini103"
docker build
```

creates:

* Docker image

based on:

* Dockerfile instructions

---

# Important Container Concept

The built image is NOT:

* Zip file
* Tar archive
* Simple binary

A Docker image is:

* Layered container artifact
* Managed by Docker runtime

This is why deployment differs from S3 uploads.

---

# Why You Cannot Upload Images Directly to ECS

ECS does not store images itself.

Instead ECS:

1. Pulls images from registries
2. Starts containers from those images

So a registry is required.

---

# Container Registry Concept

A container registry stores:

* Docker images

similar to how:

* GitHub stores Git repositories

Examples:

* Docker Hub
* Amazon ECR
* GitHub Container Registry
* GitLab Registry

---

# Docker Hub

Docker Hub is:

* Public container registry

Commonly used for:

* Open-source/public images

Examples:

* Nginx
* Redis
* MongoDB
* Ubuntu

---

# Public vs Private Images

## Public Image

Anyone can:

* Pull
* Download
* Use

Example:

```text id="’wini104"
nginx:latest
```

---

# Private Image

Restricted access.

Used for:

* Proprietary applications
* Internal systems
* Enterprise deployments

---

# Why Private Registries Matter

Real company applications often contain:

* Proprietary code
* Internal APIs
* Sensitive business logic

Publishing them publicly would be a security risk.

---

# Amazon ECR

Amazon Elastic Container Registry is AWS’s container registry service.

Purpose:

* Store private Docker images

---

# Why ECR Is Important

ECR integrates naturally with:

* ECS
* IAM
* AWS networking
* AWS permissions

This simplifies:

* Authentication
* Image pulls
* Deployment workflows

---

# ECS + ECR Relationship

Deployment architecture becomes:

```text id="’wini105"
Docker Build
   ↓
Docker Image
   ↓
Push To ECR
   ↓
ECS Pulls Image
   ↓
Run Container
```

---

# Why ECR Is Better Than Docker Hub for AWS

Advantages:

* Native AWS integration
* IAM-based permissions
* Private by default
* Simplified ECS authentication
* Better enterprise workflows

---

# New CI/CD Pipeline Direction

The Jenkins pipeline is evolving from:

```text id="’wini106"
Build → Upload Files
```

to:

```text id="’wini107"
Build
↓
Docker Build
↓
Push Image To ECR
↓
Update ECS Deployment
```

This is much closer to modern production systems.

---

# Important DevOps Workflow Introduced

The lecture introduces the standard cloud-native deployment lifecycle:

```text id="’wini108"
Source Code
   ↓
Dockerfile
   ↓
Container Image
   ↓
Registry
   ↓
Container Orchestrator
   ↓
Running Application
```

---

# Why Container Registries Exist

Registries provide:

* Central image storage
* Versioning
* Distribution
* Deployment source of truth

Very similar to how:

* Git repositories manage source code

---

# Immutable Deployment Principle

Once an image is built:

* It should not change

Instead:

* New image versions are built

Example:

```text id="’wini109"
app:v1
app:v2
app:v3
```

This creates:

* Predictable deployments
* Rollback capability
* Stable release history
