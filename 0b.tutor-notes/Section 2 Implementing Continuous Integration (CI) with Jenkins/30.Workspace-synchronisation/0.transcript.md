This explanation is describing how Jenkins handles **workspace isolation** when using Docker agents in a Pipeline.

# Core Concept

A Jenkins pipeline stage can run in two different execution environments:

1. Directly on the Jenkins agent machine
2. Inside a Docker container started by the agent

That changes how Jenkins handles the workspace directory.

---

# Case 1: Stage Without Docker

Example:

```groovy
stage('Without Docker') {
    steps {
        sh '''
            echo "without docker"
            ls -la
            touch container-no.txt
        '''
    }
}
```

## What happens internally

Flow:

```text
Jenkins Controller
        ↓
Finds available Agent
        ↓
Agent executes commands directly on host machine
        ↓
Workspace used:
 /var/jenkins_home/workspace/job-name
```

Commands run directly on the agent OS.

The file:

```text
container-no.txt
```

is created in the normal Jenkins workspace.

---

# Case 2: Stage With Docker

Example:

```groovy
stage('With Docker') {
    agent {
        docker {
            image 'node:18'
        }
    }

    steps {
        sh '''
            echo "docker"
            ls -la
            touch container-yes.txt
        '''
    }
}
```

## What happens internally

Flow:

```text
Jenkins Controller
        ↓
Finds agent capable of running Docker
        ↓
Agent pulls Docker image if needed
        ↓
Agent starts temporary container
        ↓
Commands execute INSIDE container
        ↓
Container stops after stage finishes
```

---

# Important Difference: Workspace Behavior

Without additional configuration:

## Non-Docker stage workspace

```text
/var/jenkins_home/workspace/test-space-npm
```

## Docker stage workspace

```text
/var/jenkins_home/workspace/test-space-npm@2
```

Notice:

```text
@2
```

That means Jenkins created a completely separate workspace.

---

# Why Jenkins Does This

Docker stages are isolated intentionally.

Jenkins creates another workspace to avoid:

* file conflicts
* permission issues
* concurrent build corruption
* container mount problems

So the Docker stage does NOT automatically see files created by earlier non-Docker stages.

---

# Result Observed in Logs

First stage:

```bash
touch container-no.txt
```

Second stage:

```bash
ls -la
```

But:

```text
container-no.txt
```

does not exist there.

Because the Docker stage is using another workspace.

---

# Workspace Layout

You observed:

## Workspace 1

```text
test-space-npm/
└── container-no.txt
```

## Workspace 2

```text
test-space-npm@2/
└── container-yes.txt
```

Two isolated workspaces.

---

# Solution: Share Same Workspace

Jenkins provides:

```groovy
reuseNode true
```

Example:

```groovy
stage('With Docker') {
    agent {
        docker {
            image 'node:18'
            reuseNode true
        }
    }

    steps {
        sh '''
            ls -la
        '''
    }
}
```

---

# What `reuseNode true` Does

It tells Jenkins:

```text
Do NOT create another workspace.
Use the current node and current workspace.
```

So now both stages use:

```text
/var/jenkins_home/workspace/test-space-npm
```

---

# Result After Enabling `reuseNode true`

Now:

```bash
ls -la
```

inside the Docker stage shows:

```text
container-no.txt
```

because both stages share the same workspace.

Final workspace:

```text
test-space-npm/
├── container-no.txt
└── container-yes.txt
```

---

# Practical Importance

This matters heavily in CI/CD pipelines.

Typical dependency flow:

```text
Stage 1 → build artifacts
Stage 2 → run tests
Stage 3 → package app
Stage 4 → deploy
```

If workspaces are isolated:

* artifacts disappear between stages
* dependencies become inaccessible
* builds fail unexpectedly

---

# Common Real-World Example

Without shared workspace:

```groovy
stage('Build') {
    steps {
        sh 'mvn package'
    }
}

stage('Test in Docker') {
    agent {
        docker {
            image 'maven:3.9'
        }
    }

    steps {
        sh 'ls target/'
    }
}
```

Possible failure:

```text
target/: No such file or directory
```

because Docker stage got another workspace.

---

# Correct Version

```groovy
stage('Test in Docker') {
    agent {
        docker {
            image 'maven:3.9'
            reuseNode true
        }
    }

    steps {
        sh 'ls target/'
    }
}
```

Now the build artifacts are visible.

---

# Key Takeaway

Default behavior:

| Stage Type         | Workspace                 |
| ------------------ | ------------------------- |
| Normal agent stage | Main workspace            |
| Docker stage       | Separate workspace (`@2`) |

With:

```groovy
reuseNode true
```

both stages use the same workspace.

That is called workspace synchronization/shared workspace behavior in Jenkins pipelines.
