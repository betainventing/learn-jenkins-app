### Pipeline Design Principles (How to Structure Stages Properly)

---

## 1. There Is No Fixed Order

Typical pipeline:

```text
Build → Test → E2E → Deploy
```

But:

* This is **not a rule**
* Structure depends on:

  * Technology
  * Dependencies
  * Performance goals 

---

## 2. Principle #1 — Understand Dependencies

### Types of Dependencies

#### 1. Direct Dependency

Example:

```text
Build → E2E Test
```

* E2E needs:

  * `build/` artifacts
* Cannot run before build

---

#### 2. Indirect Dependency

Example:

```text
Build → installs dependencies (node_modules)
Unit Test → needs dependencies
```

* Unit test depends on **dependencies**, not build output

---

### Key Rule

```text
If A depends on B → A must run AFTER B
```

---

### Example Decision

| Stage     | Depends on   | Can run parallel?  |
| --------- | ------------ | ------------------ |
| Unit Test | node_modules | ✅ Yes              |
| E2E Test  | build output | ❌ No (needs build) |

---

## 3. Principle #2 — Fail Fast

Goal:

```text
Detect failures as early as possible
```

---

### Bad Approach

```text
Build (1 min)
→ E2E (5 min)
→ Unit Test fails ❌
```

Problem:

* Wasted ~6 minutes

---

### Better Approach

```text
Unit Test (15 sec)
→ Fail ❌ → STOP
```

Saved:

* Time
* Compute resources

---

## 4. Trade-off: Parallel vs Sequential

### Case 1: Parallel Execution

```text
Unit Test (15s)
E2E Test (5min)
```

Run in parallel:

```text
Total = 5 min
```

---

### Problem

If Unit Test fails at 15s:

* E2E still runs → waste

---

### Better Strategy

```text
Unit Test → pass?
    YES → run E2E
    NO  → stop pipeline
```

---

## 5. Principle #3 — Don’t Parallelize Blindly

Just because you *can*:

```groovy
parallel { ... }
```

Does NOT mean you *should*

---

### Consider:

* Execution time difference
* Failure probability
* Resource usage

---

## 6. Example Optimized Pipeline

```text
Lint (fast)
↓
Unit Test (fast)
↓
Build
↓
Parallel:
    ├── E2E Test (slow)
    └── Other long tests
```

---

## 7. Linting (Very Important Early Step)

What is linting?

* Static code analysis
* Detects:

  * Syntax issues
  * Style violations
  * Bad practices

---

### Why Run First?

```text
Lint fails in 2 sec
→ Stop pipeline early
```

Instead of:

```text
Build → Test → E2E → Lint fails ❌
```

→ Massive waste

---

## 8. Real Pipeline Strategy

Think in this order:

### Step 1: Fast checks first

```text
Lint → Unit Tests
```

---

### Step 2: Medium cost

```text
Build
```

---

### Step 3: Expensive checks

```text
E2E / Integration Tests
```

---

### Step 4: Deployment

```text
Deploy (only if all pass)
```

---

## 9. Key Trade-off Model

You are balancing:

```text
Speed vs Resource Usage vs Failure Probability
```

---

## 10. Practical Insight

From your pipeline:

* Unit test:

  * Fast
  * High failure probability

* E2E test:

  * Slow
  * Lower failure probability

👉 So:

```text
Run Unit Test FIRST (fail fast)
Then run E2E
```

---

## 11. Common Mistakes

❌ Running expensive stages too early
❌ Ignoring dependencies
❌ Overusing parallel execution
❌ Running linting late
❌ Not optimizing failure path

---

## 12. Final Mental Model

```text
1. What depends on what?
2. What fails most often?
3. What is slow vs fast?
```

Use these to design pipeline.

---

## 13. Key Takeaway

You are not just writing a pipeline.

You are designing:

```text
A failure detection system + execution optimizer
```
