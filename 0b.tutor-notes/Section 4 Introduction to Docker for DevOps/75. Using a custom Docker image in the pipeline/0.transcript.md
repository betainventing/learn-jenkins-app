This lecture demonstrates the main operational benefit of custom Docker images in Jenkins pipelines:

> Prebuilding dependencies dramatically reduces pipeline execution time.

The instructor is now replacing runtime setup work with a preconfigured container image.

---

# What Changed in the Pipeline

Previously the deploy stages used a base Playwright image and then installed tools dynamically.

Earlier approach:

```bash id="2f0p6j"
npm install netlify-cli
npm install node-jq
```

during every pipeline run.

Now the tools are already baked into the custom image:

```text id="gz6wgr"
my-playwright
```

So the deploy stages simply use that image directly.

# Why `node_modules/.bin` Was Removed

Previously:

```bash id="7q4yrq"
./node_modules/.bin/netlify
```

was required because packages were locally installed inside project dependencies.

After global installation:

```bash id="n1ngh5"
npm install -g netlify-cli
```

the executable becomes available system-wide in the container `PATH`.

So commands can now simply be:

```bash id="54mln4"
netlify status
```

This is because npm creates symbolic links in global executable directories.

---

# Important Linux PATH Concept

Inside Linux containers:

```text id="u6ab61"
PATH
```

contains directories searched for executables.

Globally installed npm binaries are typically placed into paths like:

```text id="p8p9c2"
/usr/local/bin
```

So shell commands can find them automatically.

# Why Pipeline Time Improved So Much

The deployment stage dropped roughly from:

```text id="meb3ks"
1m 23s
```

to:

```text id="6y4bbv"
34s
```

Main reasons:

* no npm installation
* no package downloads
* no dependency resolution
* fewer filesystem writes

npm installation can be surprisingly expensive.

# Important Enterprise Principle

This pattern is extremely common in enterprise CI/CD systems.

Organizations create:

* standardized CI images
* prebuilt toolchain containers
* organization-wide build images

Example:

```text id="x2zjtz"
company-ci-node18:v5
```

containing:

* Node.js
* AWS CLI
* kubectl
* jq
* Terraform
* internal tools

Then all Jenkins pipelines reuse that image.

---

# Another Major Advantage: Consistency

Without prebuilt images:

Two pipeline runs may install:

* slightly different package versions
* updated transitive dependencies
* incompatible binaries

With prebuilt images:

Environment is fixed and reproducible.

# Important Missing Production Improvement

The instructor is building image during the pipeline itself for learning purposes.

Real production systems usually do NOT rebuild the CI image every run.

Typical production architecture:

```text id="5y7wyx"
Build CI image separately
    ↓
Push to registry
    ↓
Pipelines reuse prebuilt image
```

Otherwise:

* image build time repeats
* caching becomes inconsistent
* scalability suffers

# Example Production Setup

## CI Image Repository

```dockerfile id="p8r71d"
FROM node:18-alpine

RUN npm install -g \
    netlify-cli \
    node-jq
```

Built once:

```bash id="2w0h55"
docker build -t company/playwright-ci:v1 .
docker push company/playwright-ci:v1
```

Then Jenkins uses:

```groovy id="n4d8r2"
image 'company/playwright-ci:v1'
```

Very common enterprise pattern.

# Another Important Benefit: Cleaner Jenkins Agents

Instead of installing tools directly on Jenkins servers:

* agents remain minimal
* environments remain isolated
* upgrades become easier

This avoids “snowflake servers”.

A snowflake server is:

> a manually customized server nobody fully understands anymore

DevOps tries to eliminate this problem.

---

# Hidden Docker Optimization Here: Layer Reuse

Since:

```dockerfile id="m0gksr"
RUN npm install -g ...
```

rarely changes, Docker caches it efficiently.

Future builds become very fast unless dependencies change.
