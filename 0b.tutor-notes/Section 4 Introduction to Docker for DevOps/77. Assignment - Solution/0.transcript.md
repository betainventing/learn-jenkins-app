This lecture explains an extremely important CI/CD engineering concept:

> There is a difference between one-time image build cost and repeated pipeline runtime cost.

The instructor is helping you understand the tradeoff properly.

---

# The Actual Problem

The custom image:

```text id="4c5z1d"
my-playwright
```

initially contained:

* Playwright
* Netlify CLI
* node-jq

But the local E2E stage also needed:

```text id="khx61w"
serve
```

because Playwright tests require a local web server.

Since `serve` was missing:

```bash id="lmr0zc"
npm install serve
```

was still being executed during pipeline runtime.

That defeats part of the optimization.

---

# The Fix

Add `serve` during image build:

```dockerfile id="4ifq0u"
RUN npm install -g netlify-cli node-jq serve
```

Now all required tools exist inside the image itself.

---

# Why `npm install` Was Removed

Previously pipeline runtime looked like:

```text id="t9z8j8"
Start container
    ↓
Install serve
    ↓
Run tests
```

After optimization:

```text id="t3m5qt"
Start container
    ↓
Run tests immediately
```

This is the desired CI/CD architecture.

---

# Why `node_modules/.bin/serve` Was Removed

Previously:

```bash id="h4r1az"
./node_modules/.bin/serve
```

worked because `serve` was installed locally.

After global installation:

```bash id="7v81t6"
npm install -g serve
```

the executable is available globally via Linux `PATH`.

Now you simply use:

```bash id="18t7wm"
serve
```

This simplifies scripts significantly.

# Why This Is Still Better

Because image build is usually:

* cached
* reusable
* infrequent

while pipeline execution happens constantly.

---

# Extremely Important DevOps Concept

This is basically:

> amortizing setup cost

Meaning:

Instead of paying setup cost every run:

```text id="jtw3mx"
10s + 10s + 10s + 10s + 10s ...
```

you pay:

```text id="3j48lf"
60s once
```

and reuse afterward.

This is much more efficient at scale.

---

# Docker Layer Caching Is Critical Here

The first build took:

```text id="4m1y8r"
~1 minute
```

because Docker needed to:

* download layers
* install packages
* create filesystem changes

But future builds are usually much faster if Docker cache remains valid.

---

# Why Future Builds Become Faster

Docker caches layers based on instruction hashes.

Example:

```dockerfile id="5i9g5q"
RUN npm install -g netlify-cli node-jq serve
```

If this line does not change:

Docker can reuse cached layer.

Then rebuild becomes almost instant.

# Hidden Infrastructure Principle

Your CI environment is becoming:

> immutable infrastructure

Meaning:

Instead of dynamically modifying environments:

```bash id="7n8crn"
npm install ...
apt install ...
curl ...
```

you prebuild everything.

Containers become disposable runtime units.

---

# Another Important Benefit

Global installations inside image reduce:

* external npm requests
* dependency resolution
* registry outages
* transient installation failures

This improves CI reliability significantly.

---

# Important Real-World Warning

In production:

Avoid installing too many unnecessary tools into one image.

Otherwise images become:

* bloated
* insecure
* harder to maintain

There is always a tradeoff between:

| Smaller Images         | Larger Utility Images |
| ---------------------- | --------------------- |
| faster pulls           | more tools available  |
| reduced attack surface | easier pipelines      |
| minimal runtime        | convenience           |

DevOps engineering often balances these concerns.

---

# Key Lesson From This Lecture

The most important takeaway is:

> Optimized CI/CD pipelines move environment preparation into reusable container images.

Instead of repeatedly configuring environments during execution:

* tools are preinstalled
* environments are standardized
* pipelines become faster
* builds become more reliable

This is one of the foundational operational advantages of containerized CI/CD systems.
