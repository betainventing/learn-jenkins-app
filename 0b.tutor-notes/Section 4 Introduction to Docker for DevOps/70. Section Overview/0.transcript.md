This section is explaining why Docker became essential for modern CI/CD pipelines and why Jenkins pipelines often run inside containers.

## The Original Problem

Earlier software delivery models were very different.

Typical flow:

1. Developers built a large monolithic application
2. QA tested the full application
3. Operations team deployed the full application
4. Releases happened slowly (monthly releases were common)
5. Small changes required redeploying the entire system

### Problems with Monoliths

A monolith is a single large application where everything is tightly coupled.

Example:

* Authentication
* Payments
* Notifications
* Reporting
* Inventory

...all packaged into one deployable unit.

Implications:

* One bug can affect the entire application
* Scaling is difficult
* Deployments are risky
* Rollbacks are painful
* Release cycles become slow
* Teams block each other

---

## Shift to Microservices

Modern systems are usually split into smaller independent services.

Example:

* User service
* Payment service
* Email service
* Product service

Each service can:

* be developed independently
* be tested independently
* be deployed independently
* scale independently

This enables:

* faster deployments
* smaller blast radius
* continuous delivery
* multiple deployments per day

---

## Why Docker Became Important

Docker solved a major operational problem:

> “How do we package an application with everything it needs so it runs the same everywhere?”

Before Docker:

* “Works on my machine” problems were common
* Different servers had different dependencies
* Manual setup caused inconsistencies

Docker packages:

* application code
* runtime
* libraries
* system dependencies
* tools

...into a container image.

That image behaves consistently across:

* developer laptops
* Jenkins agents
* test environments
* production servers

---

## Why This Matters in Jenkins Pipelines

The transcript is transitioning into a very important CI/CD concept:

> Jenkins build environments should be isolated and reproducible.

### Problem Without Docker

Suppose your Jenkins server runs:

* Java projects
* Python projects
* Node.js projects
* Go projects

Each project may need:

* different runtimes
* different package managers
* different CLI tools
* different versions

If everything is installed directly on Jenkins:

* dependency conflicts happen
* upgrades break builds
* pipelines become inconsistent
* maintenance becomes difficult

Example:

Project A needs:

* Node.js 18

Project B needs:

* Node.js 22

Project C needs:

* Python 3.12

Project D needs:

* Maven + Java 21

Installing all of this globally on Jenkins becomes messy.

No.

# Correct Approach

Instead of modifying one shared Jenkins machine endlessly:

Use project-specific Docker images.

Example:

## Python Project

Use:

```dockerfile
FROM python:3.12
```

Install only Python-related tools.

---

## Node.js Project

Use:

```dockerfile
FROM node:22
```

Install npm tools only.

---

## Java/Maven Project

Use:

```dockerfile
FROM maven:3.9-eclipse-temurin-21
```

---

# Core DevOps Principle Here

The build environment itself becomes versioned and reproducible.

Instead of documenting:

> “Install these 27 packages on Jenkins”

you define:

```dockerfile
FROM node:22

RUN npm install -g node-jq
```

Benefits:

* reproducible
* portable
* isolated
* easy onboarding
* easier debugging
* easier scaling
* fewer “works on my machine” issues

---

# Why Docker Fits Jenkins Extremely Well

Jenkins can:

* start temporary containers
* run builds inside them
* destroy them after completion

This gives:

* clean environments every run
* no leftover dependencies
* consistent builds
* safer parallel execution

Example Jenkins pipeline:

```groovy
pipeline {
    agent {
        docker {
            image 'node:22'
        }
    }

    stages {
        stage('Build') {
            steps {
                sh 'npm ci'
                sh 'npm test'
            }
        }
    }
}
```

Jenkins will:

1. pull the image
2. create container
3. execute pipeline inside container
4. remove container after completion

---

# Important Concept: Ephemeral Build Environment

Containers used in CI/CD are usually temporary.

Meaning:

* create
* use
* destroy

This is critical because:

* every build starts clean
* builds become deterministic
* hidden state is avoided

Without this, builds can accidentally pass because:

* old files exist
* cached dependencies exist
* tools remain from previous builds

---

# Another Major Benefit: Pipeline Portability

If your Jenkins server crashes:

You can move the pipeline elsewhere easily because:

* build logic is in Jenkinsfile
* environment is in Dockerfile

Infrastructure becomes replaceable.

This is a foundational DevOps idea.
